# 飞书通道：在飞书里给数字员工派活

## 已定的决策
- **一条平台级通道**：用户建 1 个飞书自建应用；群里 @员工名 路由，私聊默认派给秘书（崔老三）。
- **第一版就上进度卡片**：收到指令回可更新的互动卡片（排队→进行中→完成/失败），拍板按钮后置。
- 接入方式用**飞书长连接**（WebSocket），不需要公网/HTTPS，契合班底只听 127.0.0.1 的形态。
- 参考 Multica（同类产品）：私聊连续消息同一段对话、群只响应 @、长连接模式均与我们一致；它的进度卡片是未完成的 issue，我们做出来即超出它。

## 配置与存储
- `<dataDir>/feishu.json`（0600，`BANDI_FEISHU` 环境变量覆盖供测试）：`{ appId, appSecret, enabled, allowOpenIds }`。密钥纪律照 `imagegen.mjs`：API 只回掩码、留空不覆盖、不进日志。
- `<dataDir>/feishu-links.json`（非密）：`chat_id → { conversationId, personaId }`，让连续消息续接同一段班底会话（Multica 行为）。
- 凭据**不进 SQLite**（store/ 是 SQL 专属、密钥不进库是明文纪律）。

## 长连接协议（零依赖手写，~250 行）
Node 22 全局 WebSocket + fetch，协议照官方 `larksuite/node-sdk` 的 `ws-client/` 目录逐字段实现（已核对源码）：
1. `POST {域名}/callback/ws/endpoint`，body `{AppID, AppSecret}` → 返回 `URL` + `ClientConfig{PingInterval, ReconnectCount, ReconnectInterval, ReconnectNonce}`（秒×1000）。
2. 连 `URL`；帧为 pbbp2：`headers` 是 `[{key,value}]` 数组（折叠成对象），payload 按 `message_id/sum/seq` 分片合并。
3. 收到事件帧回 ack（`{code:0}` + `biz_rt` 头），不回服务端会重推；ping/pong 心跳按服务端下发的间隔；收到 pong 刷新配置。
4. 重连：代计数器使旧循环失效 + closed 标志防复活 + 随机抖动（学 SDK，退避值用服务端下发的）。
- 模块头注释写明「此处为何破例用 WebSocket 客户端」（仓库现状是刻意不用 WS，见 docs/形态决策.md §十二——那是入站架构决策，出站客户端不冲突）。
- 依赖注入点供测试：`start({ fetchImpl, WSCtor })` 之类，仿 `schedules.mjs` 的 `tick({actions})`。

## 消息流
1. 收 `im.message.receive_v1`（先过 `allowOpenIds` 白名单，空=不限制）。
2. **群聊**：只响应 @ 消息；`@员工名` 按 `store.listPersonas()` 名字匹配（复用 `dispatch.parseMentions` 的按名字长度倒序思路防"@李"吃掉"@李俊"）；没 @ 或没匹配到就忽略。
3. **私聊**：默认派给秘书（`secretary.mjs` 的 `SECRETARY_ID`，常量已导出）。
4. 派活完全照 `persona-task.mjs` 的现成形状：`ensureConversationForPersona(personaId)`（或 links 里的既有会话）→ `dispatchToThread(convId, 文本)`，返回 `{run}`。撞闸 `err.code==='busy'` 时卡片提示忙碌、消息不丢（改用 `dispatchEventToThread` 进队等补派）。
5. 回发用 chat_id 统一收发。

## 进度卡片
- 收到指令立即发交互卡片：员工名 + 指令摘要 + 状态行，记下 message_id。
- 更新驱动：每 run 一个 3–5 秒定时器轮询 `store.listRunEvents(runId, afterSeq)`，阶段归约照抄 `apps/web/js/run-progress.mjs`（思考中/调工具/写回话/收尾中/出错了）→ `PATCH /open-apis/im/v1/messages/:message_id` 更新卡片；状态不变不刷、有变化节流 ≥3 秒。
- 终态挂 `runs.onRunFinish`（server.mjs 已有三个钩子，加第四个）：完成 → 卡片置「已完成」+ `run.done.finalText`；失败 → 「失败」+ 原因。

## 用户侧要做的（写进文档）

## 测试
`smoke-feishu.mjs` 两层（仿 smoke-schedules）：① 单元层——import 前设 `BANDI_FEISHU/BANDI_DATA` 指临时目录；配置存取/掩码/留空保留；@路由与私聊兜底；注入假 WebSocket 构造器 + 假 fetch 验证连接、ack、心跳、重连、卡片发送/PATCH、busy 处理。② HTTP 层——spawn 真 server（仿 smoke-connectors）验接口。登记进 `tools/run-smokes.mjs` 的 RUN 清单（不登记会 exit 2）。

1. 设置页填凭据 → 状态变「已连接」。2. 飞书私聊发指令 → 秘书开始干活，卡片状态推进，完成后显示最终回复。3. 群里 @员工名 → 对应员工接到活。4. 断网重连自动恢复。5. `node tools/run-smokes.mjs` 全绿。
