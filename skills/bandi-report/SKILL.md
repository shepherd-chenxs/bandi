# 班底 · 汇报（结论先行）

你是给**忙碌的雇主**汇报，不是写工作日志。他读第一句就要知道三件事之一：
**做完没有？卡在哪？要他做什么？** 下面的写法是为了让他读一行就能决定，不用从过程里扒结论。

> **与平台契约的分工（2026-11-19 收口）**：契约每轮都在，里面已经写死了四条硬口径 ——
> 第一行=三态结论（第 1 条）、必须交代归谁动手（第 2 条）、依据默认不写（第 3 条）、
> 交付标记单独一行（第 6 条）、不空转 / "Next:" 不算收尾（第 8 条）、过程决策不上抛（第 11 条）。
> **凡契约写了的，这里不再重复一遍。** 原因很实在：同一句话写两处，模型会同时读到两个版本，
> 改一处漂一处（实报：「先报数再列清单」在人设和技能里各一份，两处都没写"只有一项时别列"，
> 于是寒暄也要凑一行清单）。这个技能只补契约不管的三件事：
> **汇报的形状、什么时候不该用、以及照着改的例子。**

> 方法来自 Barbara Minto 的《金字塔原理》，技能形态参考并改写自两个 MIT 开源 agent skill
>（[minto-pyramid](https://github.com/millwright-labs/minto-pyramid-skill)、
> [pyramid-principle-for-operators](https://github.com/wilsonwu-ai/pyramid-principle-for-operators)）；
> 这里只保留"写汇报"这一面，并换成班底语境（卡号 / 运行 id / 群 / 拍板）。

## 什么时候用 / 不用

**用**：进度汇报、验收结论、请示/拍板、方案建议、坏消息通知 —— 凡是"要读者接受一个判断或做一个决定"的。

**不用**（硬套会坏事）：事故时间线、操作手册、教程、排查笔记、纯数据回执 —— 这些按时间/结构组织本来就是对的。

判断办法：**这段话要读者做决定吗？** 要 → 用这套形状；只是告知或记录 → 按事本身的顺序写。

## 形状：结论 → 动作 → 归谁

```
【结论】一句话：顺利（**直接说结果**，别挂「不用你动」）/ 有问题（我处理，你等）/ 卡住（要你做什么）
这一轮已做：…（真的做了的）
在等 / 待拍板：…（等什么、为什么只能你定）
依据（可选，一行）：…（只在契约第 3 条的三种情况写）
```

三行各自的**判据在契约里**（第 1/2/3 条），这里只说形状上容易被忽略的两点：

- **「不用你动」不是结语，是例外**（2026-11-19 用户实报：「为什么总是有'不用你动'这句话，很奇怪」）：
  只在**他可能以为这活得他自己干**时说一句；答"换了 / 已通过 / 已完成"这类结果句时挂它 = 噪音。
  一轮最多一次，能不说就不说 —— 他没问、也没打算动手，这句话对他没有信息。

- **中间那行是"已做"不是"打算"**：建了哪张卡、派给谁、把哪张退回「待办」、重跑了哪张、@ 了谁 ——
  读者要的是进展。写成"我准备 / 我接着会"就是把活留到下一轮。
- **最后一行不是必填**：没有在等的东西就不写这一行，别用"暂无需拍板"占位。

> 2026-11-12 口径变更：原「2–4 条理由 + 每条必带证据」改成现在这样。用户实报「每个人回复都是
> 一大堆，讲什么依据」「我要依据有个屁用」。依据降为兜底；结论改三态 —— 他问进度时唯一想知道
> 的是"要不要我出手"。

## 模板（直接抄）

```
【结论】换完了，已生效。
这一轮已做：…

【结论】有问题：X 连不上，我来处理，稍等。
这一轮已做：…
在等：…

【结论】卡住了：我没有部署权限，你给我开一下。
需要你拍板：…
```

## 技能层补充（契约没写、但汇报时容易翻车的）

1. **一屏能读完**：群消息 ≤ 150 字，数据放卡/附件；别把整段工具输出倒给雇主。
2. **报告对象是雇主，不是同事**：没 @ 你的群消息不用汇报；回执、验收、结论按上面三段走。
3. **证据的抓取口径**：只能用你这一轮真看到的（卡、运行、文件、回话）；源里没有就写"缺数据"，
   拿不准写"未验证" —— 不写"应该 / 可能 / 大概"当证据。要写依据时，点名 `pt-…` / `r-…` /
   文件:行 / 时间 / 谁说的；拿不准就只写文件 + 函数名。
4. **问答类不套这套形状**：问「谁 / 哪个 / 能不能 / 归谁 / 为什么」→ 第一行直接答（多问拆成逐问，
   每问一句），一屏简报只留给做事类交付。这条与契约第 1 条同一个口径，技能里只提醒"别把汇报体
   用在回答问题上"。

## 放在坏例与好例旁边看

**坏（叙述式，结论在最后，且停住）**
> 我先看了时区问题，DB 存的是 UTC，前端切原始串慢 8 小时，嘉辉那张卡 apply_patch 找不到行挂了，
> 杜衡那张 QA 也是工具报错。Next: 把两张失败卡退「待办」重跑。

**好（同一件事，结论先行，动作已做，依据收起来）**
> 【结论】时区问题未修完：2 张执行卡跑挂，已退「待办」并重跑，等新一轮结果。
> 这一轮已做：pt-xxx（嘉辉）、pt-yyy（杜衡）退回「待办」并重跑。
> 在等：两张卡新运行出结果，我按结论汇报。

（他追问"为什么挂的"再补一行：工具层报错，跟改法无关，已在重跑里绕过。）

**坏**：只写"5 张卡已建完"（没卡号、没谁在办、没说下一步）。
**好**：结论 + 每张卡的卡号与执行人 + 哪个在跑、哪个等拍板。

## 常见错误

| 错误 | 改法 |
|---|---|
| 结论在最后一段 | 搬到第一句；过程最多留一句背景 |
| 结论后面挂一串依据 | 依据默认不写；他追问、或原因会改变他的决定，才附一行 |
| 把过程当结论（"我先查了…"） | 结论先行；过程不进正文 |
| 用"应该/可能/大概"当判断 | 给出判断的必要条件，或明说不确定 + 怎么确认 |
| 把 "Next:" 当收尾 | 这一轮先做完；做不了的写「需要你拍板 / 在等」 |
| 删掉风险、依赖、等待项 | 单独放"在等 / 风险"一行，别当理由删掉 |
| 把工具输出整段贴出来 | 只留结论所需要的那一个证据（卡号/报错原文一行） |
| 寒暄也凑一行清单（"在吗"→ 一句话 + 一条要点） | 一句说完就一句；清单只在真有两项以上时才用 |

## 配什么一起用
