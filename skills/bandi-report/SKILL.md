# 班底 · 汇报（结论先行）

你是给**忙碌的雇主**汇报，不是写工作日志。他读第一句就要知道三件事之一：
**做完没有？卡在哪？要他做什么？** 下面的写法是为了让他读一行就能决定，不用从过程里扒结论。

> 方法来自 Barbara Minto 的《金字塔原理》，技能形态参考并改写自两个 MIT 开源 agent skill
>（[minto-pyramid](https://github.com/millwright-labs/minto-pyramid-skill)、
> [pyramid-principle-for-operators](https://github.com/wilsonwu-ai/pyramid-principle-for-operators)）；
> 这里只保留"写汇报"这一面，并换成班底语境（卡号 / 运行 id / 群 / 拍板）。

## 什么时候用 / 不用

**用**：进度汇报、验收结论、请示/拍板、方案建议、坏消息通知 —— 凡是"要读者接受一个判断或做一个决定"的。

**不用**（硬套会坏事）：事故时间线、操作手册、教程、排查笔记、纯数据回执 —— 这些按时间/结构组织本来就是对的。

## 形状：答案 → 理由 → 证据

```
【结论】一句话：做完没有 / 卡在哪 / 要你拍板什么
   ├─ 依据 1（带证据）
   ├─ 依据 2（带证据）
   └─ 依据 3（带证据，最多 4 条）
这一轮已做：…（真的做了的）
在等 / 待拍板：…（等什么、为什么只能你定）
```

**第一层：结论。** 先给判断，不给过程。没做完就直说"任务未完成：…"，
别把它藏在一段过程叙述的最后。要人拍板的，结论里就写"需要你拍板：…"。

**第二层：理由（2–4 条）。** 同一类东西、互不重叠、合起来回答读者会问的
（成本 / 风险 / 时间 / 替代方案 / 谁来做）。两条真覆盖得住，就别硬凑三条；
真需要第四条就写第四条。这个数字由逻辑决定，不是排版要求。

**第三层：证据。** 每条理由下面必须有能点名的东西 —— **卡号（pt-…）、运行 id（r-…）、
字段名、文件:行、时间、谁说的**。没有证据的理由就是意见。

**收尾：动作，不是待办清单。** 只写**这一轮已经做完**的：建了哪张卡、派给谁、
把哪张退回「待办」、重跑了哪张、改派给谁、取消了哪张、@ 了谁。
**"Next:" 不是留给自己下一轮做事的清单。** 你这轮能做的动作，**先做完再回话**；
实在做不了的写成「需要你拍板：…（为什么只能你定）」或「在等：…（等什么、
下一轮你会盯什么）」，不许默默收尾。

## 模板（直接抄）

```
【结论】…（做完 / 未完成：卡在哪 / 需要你拍板：…）

依据：
1. …（卡 pt-xxx，运行 r-xxx，字段 createdAt=…）
2. …（文件:行 / 谁说的 / 什么时候）
3. …

这一轮已做：退「待办」并重跑 pt-xxx/r-xxx；改派 pt-yyy 给杜衡。
在等：高进那张还在跑（run r-xxx），出结果我把结论带回。
```

## 硬规则

1. **第一句就是结论**，不从"我先看了一下/我查了一下"讲起。
2. **不编数字**：证据只能来自你这一轮真看到的东西（卡、运行、文件、回话）；源里没有就不写，写"缺数据"。
3. **不拿"应该/可能/大概"当证据**；不确定就写不确定在哪、怎么确认。
4. **一屏能读完**：群消息 ≤ 150 字，数据放卡/附件；别把整段工具输出倒给雇主。
5. **没做完不要收尾**：先把这一轮能推进的推进完（改卡/退待办/重跑/改派/取消/建卡派活），
   再按"已做 / 在等 / 待拍板"三行收。收尾的"Next"只能指向**雇主**能做的决定，不能指向你自己还没做的事。
6. **报告对象是雇主，不是同事**：没 @ 你的群消息不用汇报；回执、验收、结论都按上面三段走。
7. **交回结论先写标记**：在办班底的任务卡 / 流程步骤时，回话**第一个非空行**先写 `[完成]` 或
   `[受阻] 原因` —— 平台按它落状态；不写 = 没交回可验收结论，卡 / 这一步会停在「已阻塞」。

## 放在坏例与好例旁边看

**坏（叙述式，结论在最后，且停住）**
> 我先看了时区问题，DB 存的是 UTC，前端切原始串慢 8 小时，嘉辉那张卡 apply_patch 找不到行挂了，
> 杜衡那张 QA 也是工具报错。Next: 把两张失败卡退「待办」重跑。

**好（同一件事，结论先行，动作已做）**
> 【结论】时区问题未修完：2 张执行卡跑挂（工具层报错），已退「待办」并重跑，等新一轮结果。
> 依据：① DB 存 UTC、前端切原始串慢 8 小时（messages.createdAt=…T01:12:01Z）；
> ② 嘉辉卡 pt-xxx 失败原因 apply_patch 找不到目标行（运行 r-xxx）；③ 杜衡 QA 卡 pt-yyy 失败原因参数解析 EOF（运行 r-zzz）。
> 这一轮已做：pt-xxx、pt-yyy 退回「待办」并重跑。
> 在等：两张卡新运行出结果，我按结论汇报。

**坏**：只写"5 张卡已建完"（没卡号、没谁在办、没说下一步）。
**好**：结论 + 每张卡的卡号与执行人 + 哪个在跑、哪个等拍板。

## 常见错误

| 错误 | 改法 |
|---|---|
| 结论在最后一段 | 搬到第一句；过程最多留一句背景 |
| 理由互相重叠（同一件事说两遍） | 合并成一条；宁可两条真理由，不凑三条 |
| 理由是证据（细节站在理由那一层） | 降级成证据，挂到它支持的那条理由下面 |
| 用"应该/可能/大概"当判断 | 给出判断的必要条件，或明说不确定 + 怎么确认 |
| 把 "Next:" 当收尾 | 这一轮先做完；做不了的写「需要你拍板 / 在等」 |
| 删掉风险、依赖、等待项 | 单独放"在等 / 风险"一行，别当理由删掉 |
| 把工具输出整段贴出来 | 只留结论所需要的那一个证据（卡号/报错原文一行） |
