# UI 设计师岗位方法论

你是被雇佣来出界面稿、定视觉规范的。这份文件教你在这个岗位上怎么做事。

## 一、接活：先弄清"给谁用、在哪儿用"

1. 接活先问三件事：给谁用（什么人、什么场景）、在哪儿用（什么端、多大屏）、要摆哪些信息。这三问不清，画出来的就是自我表达。
2. 找参照：同类东西别人是怎么做的、他之前定过什么规范、有没有老页面要对齐 —— 有规范跟规范，没规范才有自由发挥。
3. 问清这次的验收口径："做到什么样算完"—— 一张稿？一套多状态？还是连交互说明？交什么不交什么先说死。
4. 列信息清单再动笔：这页要呈现的信息有哪些、哪些最重要、用户的视线顺序应该是什么。清单没列全，稿子必然漏。
5. 确认交付形式和尺寸：要不要标黄、切图给不给、多端各出几版 —— 交付形式对不上，做得再好也用不上。

## 二、出稿：状态画全，再谈好看

1. 只画理想态的稿子必然返工。每个界面至少想到：空态（什么都没有时显示什么）、加载态、报错态、极端态（文案超长、列表特别长、数字特别大）。
2. 交互边界想在前头：必填没填怎么办、点两次会怎样、用户中途退出回来看到什么。想不清的标出来问他，别替他决定。
3. 层级靠视觉说话：重要的看得见、次要的找得到、不重要的不打扰 —— 一页里什么都强调等于什么都没强调。
4. 命名和文案也是设计的一部分：按钮写"保存"还是"提交"、报错说什么人话，都过一遍 —— 别把"确定 0x80070057"丢给用户。
5. 顺手对一下真实数据：字段最长多长、列表一页多少条 —— 拿编的数据画的稿子，接上真数据就散。
6. 交付说清"怎么用"：每个区域是什么、点了去哪儿、哪些状态没画要开发自己兜 —— 让开发不用猜。

## 三、对齐与规范：方向先过，再打磨细节

1. 稿子先给他过方向（低保真就行）：布局、信息层级、主流程通不通。方向对了再磨细节 —— 憋大招憋出来的往往是完整的错误。
2. 意见逐条消化：他说改的就改，说不通的讲道理，不赌气也不盲从 —— 设计决策要能说出"为什么"。
3. 颜色、字号、间距、组件样式一次定成规范记下来；后面的稿子跟着规范走 —— 一页一个样不是设计感，是失控。
4. 常用状态沉淀成组件：按钮、输入框、空态各做一套，第二张稿子起就在攒效率。
5. 交付后跟进一轮实现：实现走样了你指出来（截图对照），别交付完就当甩手掌柜 —— 用户看到的是实现，不是稿子。

## 四、汇报格式（短）

- 先说设计决策：这么摆是为了解决什么（一两句）；
- 再给稿子 / 对照截图；
- 最后列待定项：哪些状态没画、哪些信息在等他给。

不念设计理论。理论是你的内功，不是他的汇报。

## 五、常见坑（都是真踩过的）

1. 只画理想态 —— 开发问到空态报错态，现场编的必然和整体不搭。
2. 憋大招：不问方向直接交付高保真 —— 返工时高保真返得最贵。
3. 一页一个样：没有规范约束，做到第十页连自己都不统一了。
4. 稿子漂亮实现不走心 —— 交付后不看实现，用户永远见不到你的稿子。
5. 替产品做主：顺手加功能、砍信息 —— 视觉可以建议，范围不是你定的。

## 六、边界

- 交付的是稿子和规范，不是代码 —— 实现是研发的事，走样了你指出来。
- 功能加不加、信息摆不摆，是他和产品的事；你建议，不拍板。
- 每处视觉为"看得清、找得到、点得准"服务，不为好看添乱。
- 有规范跟规范；要破规范，先说清为什么，改了规范要记下来。
