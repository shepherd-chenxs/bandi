# 班底 · 契约

**平台唯一一份**：人和机器都按它读写。**改本文件之前先告诉用户。**

> **它不再往项目里发副本**（2026-10-16 取消）。老做法是"纳管时把这份复制成项目的
> `.bandi/README.md`"——于是一份文本散成 N 份，谁也不知道自己手里那份是不是最新。
> 现在：**这份随平台走**，读它的路径是**平台根**下的 `skills/bandi-flow/references/契约.md`；
> 项目那边只需要两样 —— `.bandi/status.yaml`（面板读它）与 `docs/项目文档-by班底/`（文档本身）。

> **2026-10-14 起：进度真相在平台，不在本文件。**
> 谁上场、走到哪一步、通过还是驳回，全在平台的**流程实例**里（实例页可看）。
> `status.yaml` 只登记**版本台账与文档入口**——它不是进度来源；卡片（`tasks`）也不再维护。
> 本契约管的是**产物与文档**：文档放哪、版本怎么记、交付要带什么证据。

## 一、目录结构

```
<项目根>/
├─ .bandi/
│  ├─ status.yaml        项目索引：版本台账 + 文档入口（**不是进度来源**）
│  └─ 发布记录/          发布记录与执行日志（运维写入；首次发布才出现，没发过就没有）
└─ docs/
   └─ 项目文档-by班底/
      ├─ 10-需求/        10-版本/vX.Y.Z.md、20-设计/、版本记录.md（演进型）
      ├─ 20-排期/        10-版本/vX.Y.Z.md、20-任务卡/T-XXX.md
      ├─ 30-研发/        10-开发报告/T-XXX.md、问题台账.md
      ├─ 40-测试/        10-测试报告/T-XXX.md
      ├─ 50-运维/        运维手册.md、机器清单.md（演进型）
      └─ 60-产品说明/    10-版本/vX.Y.Z.md
```

**`.bandi/` 里只有两样**：`status.yaml` 与 `发布记录/`（**契约不放这儿** —— 本契约随平台走，见开头）。

**发布记录只有一个落点**：`.bandi/发布记录/v<版本号>.md`（运维写；`versions[].released` 填它的相对路径）。
老项目里的 `10-需求/30-发布记录/` 是**流程之前**的位置：历史文件不动，**不再往那儿新写**。

**每一层都编号**：顶层六类用 `10/20/30/40/50/60`，类内子目录从 `10` 起、同样留间隔、同样永不变更。**快照型文档一律放本类的 `10-版本/` 子目录**；其余按性质命名子目录（`20-任务卡/`、`10-开发报告/`、`10-测试报告/`、`20-设计/`），单一性质的文件就地放。

编号一旦分配**永不变更、不许重排**。目录里已有的原项目文档**不搬家**，在对应编号目录放一行指针即可。

**所有路径（`doc_index` 里的值、报告路径）一律相对项目根写。** 文档在哪儿**只认 `doc_index` 里登记的路径，不许在 `docs/` 里猜**。

## 二、status.yaml 契约

键用英文、值用中文。**只覆盖三样：项目身份、文档入口（`doc_index`）、版本台账（`versions`）**，外加一个可选的 `deploy` 登记段。示例：

```yaml
updated: 2026-09-23 14:30
project: 项目名
live_version: 1.8.0          # 最近发布过的版本，回滚目标的依据；发布时由运维改
doc_index:                   # 文档入口：只认这里登记的实际路径，不许在 docs/ 里猜
  root: docs/项目文档-by班底
  version_source: <版本真源的文件路径>
  version_source_note: <怎么读，一句话>
  mirrors: [<与真源同值的文件>]
  requirement: <需求文档实际路径>
  schedule: <排期文档实际路径>
  changelog: <版本记录实际路径>
  runbook: <运维手册实际路径>
  product_spec: <产品说明实际路径>
versions:                    # 台账，列表顺序 = 计划发布顺序
  - version: 1.3.0
    title: 一句话主题
    scope: 需求.md#v1.3.0    # 边界正文的锚点
    released:                # 发布记录路径；未发布留空
deploy:                      # 可选段。没有它 = 本项目不部署到服务器；deploy: [] 同义
  - name: 生产                # 必填：目标别名（人看的名字）
    host: yaojian-deploy      # 必填：机器别名，与 doc_index.runbook（机器清单）里的机器对得上
    path: /opt/app/releases   # 必填：部署路径（服务器上的绝对路径）
    method: script            # 必填：只能是 script | ssh | agent
    script: deploy/deploy.sh  # method=script 时必填：部署入口脚本（相对项目根）
    artifact: deploy/dist/app-1.0.0.jar   # 必填：产物（相对项目根，或一句"构建产物"说明）
    rollback: bash deploy/deploy.sh --rollback   # 必填：回滚入口（命令或路径）
    service: app-api          # 可选：服务名 / 容器名
    healthcheck: curl -fsS http://127.0.0.1:8080/actuator/health   # 可选：探活命令
```

### 版本台账（`versions`）—— 仍然要维护

面板读它（`GET /api/status/projects`）。`released` 是**事实字段**：发布了就填发布记录路径，没发布留空。列表里没有的版本号 = 没登记过的版本。

### `stage` 与 `tasks`（历史遗留，不再维护）

- **`stage`**（`需求 | 排期 | 开发 | 测试 | 部署 | 完成`）：老账本里的项目阶段。平台不读、面板不出，**不许拿它当进度**。新项目可以不写。
- **`tasks`**：老账本里的任务卡镜像（带 8 个状态那套）。平台不读、面板不出，**任何角色都不许再改它**；历史数据原样保留（要删旧账本得用户拍板）。进度一律看流程实例。

任务卡**文件**（`20-任务卡/T-XXX.md`）照旧要写——它是验收标准的载体：研发照它实现、测试照它验。

### `deploy` 段（可选）

登记「这个项目发到哪台机的哪个路径」。**0 到 n 条**；没有这一段（或写成 `deploy: []`）就是本项目不部署到服务器，不猜、不推断。

- **必填键六个**：`name` / `host` / `path` / `method` / `artifact` / `rollback`。
- **`script` 条件必填**：`method=script` 时必填（部署入口脚本，相对项目根）；`ssh` / `agent` 不用填。
- **`method` 只有三个值**：`script`（项目内脚本）| `ssh`（人工 ssh 步骤）| `agent`（交给某个 agent 执行）。不许自造第四个值。
- **可选键两个**：`service`、`healthcheck`。缺省就是没填，不留空行、不显示 `None`。
- **目标别名唯一**：`name` 在同一段内必须唯一。
- **不许出现凭据**：不写密码、不写私钥路径与正文、不写口令。要写机器在哪，写机器别名（`host`），细节去机器清单查。
- **平台不执行它**：没有一键部署（旧面板那套已退役，见 `bandi-ops`）。这一段只是**登记**；执行由运维数字员工在会话里做，过程留在事件流里。失败即停，不重试、不自动回滚。

## 三、进度与状态（真相在平台）

> **「三」「四」「五」「六」讲的是平台引擎的行为**，真源在平台（流程实例页 + 平台自己的代码）。
> 本文件是**随项目走的一份副本**，平台改了这儿不会自动跟着改 —— **冲突一律以平台为准**。

一条**流程实例**的状态只有三种：`进行中` / `已完成` / `已终止`。
实例当前这一步的状态只有六种：`待开始` / `进行中` / `待确认` / `已完成` / `已阻塞` / `失败`；人对它的决定只有三种：`通过` / `驳回` / `终止`。

- **到站即派活**：推进到某一步，**按节点上点名的人**（`personaId`）把它派出去，不用人再点一次。
- **没点名 = 故意留空**：不是"等人顶上"，是**这一步就先空着**——到站即标「已阻塞」并写明原因，等人来指派。**引擎不按技能替你挑人。**
- **停不停只由节点上的 `manual` 开关决定**：勾了就干完停在「待确认」等人拍板；没勾就干完自动往下走。
- **已阻塞 = 等人处理**：没点名、额度拦下、失败等人处理、人工标阻塞，是同一档语义。指了人、或重跑，就接着办。
- **驳回**按节点声明的出口回到前面某个节点，**每一次访问单独记一条任务**——旧的办理痕迹不被覆盖。
- **终止**随时可用；正在跑的那次不会被硬杀，它跑完也不会再把流程推起来。

**卡片不再是「状态」的载体**，老的 8 状态流水线作废：那条线现在由模板的**节点与连线**表达。

## 四、流转由平台驱动

流程 = **模板**（节点 + 连线 + 出口）+ **实例**。发起一条流程 = 在工作台点开模板、填写想法、选项目；**项目选定后，这一步就在那个项目目录里干活**。

- **一步一停是默认**：`manual` 节点干完停住等人放行；其余节点干完自动往下走。
- **部署永远要人下令**：内建模板的部署节点不自动流转，必须有人放行。
- **派到谁就只做那一段**：做完在会话里交回结论，**不推下一步、不派生下游角色**——推进是平台的事。
- **只有两种情况该停下来找用户**：① 需要他拍板（缺信息、方案选择、口径冲突）；② 门禁不通过且改不了（要动需求）。

## 五、谁上场（派活规则）

1. **只认点名**（`personaId`）。节点上写了谁，就派给谁。
2. **没点名 = 故意留空 → 那一步立刻标「已阻塞」**，写明「没点名经办人」；不许静默空着，也不许显示成"随时会开跑"。等人指派——**引擎不按技能找人顶上**。
3. **节点上没有"技能"这一维**。技能是**员工身上的能力**（这个人会干什么），流程不按它路由：节点的选择只有"点名谁"和"不点名"。**不是每个节点都有对应技能**——步骤可以先有、人后配，也可以在界面上直接点名一个你觉得能办的人。
4. **用户明确指派某个人** → 在实例上就地改这一步的经办人（改模板只影响以后新起的流程，救不了已经起跑的那条）。
5. **一次只推进一条流程、一步**。要并行是再起一条实例，不是自己在本步里兼职下一步。

## 六、三道门禁

门禁判的是「**能不能往下走**」，不是「要不要问用户」。不通过就走**驳回**回路。按内建模板：

| 门禁 | 卡在哪 | 判据 | 打回落点（内建模板） |
| --- | --- | --- | --- |
| 排期门 | 定计划出卡时 | 每条验收标准都能被执行、被复现吗？ | 写代码发现卡不达标 → 驳回回「定计划」 |
| 交付门 | 测试出结论时 | 每条验收标准都有证据吗？ | 测试不通过 → 驳回回「写代码」 |
| 发布门 | 部署前 | 检查单全过、回滚方案写了吗？ | 发布失败 → 驳回回「测试」 |

**判据是这一步的职责，谁办谁判**——流程里没有专职裁判，也没有「编排」这个中间人替你判。模板改了连线，就以模板为准。

## 七、纪律

- **进度只有一个来源：平台的流程实例。** 不许另建进度文件，不许再往 `status.yaml` 的 `tasks` 里写状态，不许拿旧账本的状态当进度。
- **不采信自述**：测试不从研发报告里抄结论；研发报告里没实测过的行为写「未验证」，不许写成结论。
- **数字三件套**：报告里任何数字都要给**命令原文 + 完整输出 + 基准**（相对谁）。缺基准的数字算无实据。
- **环境类结论要标清来源**：执行环境的 PATH 可能和用户真实终端不一致，观测不到不等于不存在。

## 八、汇报

问进度时**看流程实例**（当前在哪个节点、谁在办、进行中/待确认/已阻塞、卡了多久），直接给一张表：流程名、当前节点、经办人、状态。不复述过程、不罗列文件路径，除非用户要。

**对话要简明（硬约束，用户 2026-10-11 明确）**：**跟用户对话的每一条回复必须在 300 字以内讲清楚**，不许长篇大论、不许铺陈背景、不许罗列多条证据链。300 字不够就砍：只留结论 + 必要依据 + 下一步选择。长内容一律写进文件，回复里只给路径。

## 九、版本与文档速查

- **版本真源在项目里**（CHANGELOG / 代码常量 / tag），`live_version` 只是索引登记的镜像。
- 当前版本：**纳管时问一次、登记 `doc_index.version_source`**，之后一律读索引，不再满仓库找。
- 判据：读到全部相同 → 直接采用；一处都没读到 → 提 `0.1.0` 并记录；**两处及以上、值各不相同**才是矛盾 → 列出来请用户拍板。**空值 / 缺字段等于未读到，不算矛盾。**
- 开新版：`10-需求/10-版本/vX.Y.Z.md` 写边界（含「要做什么」「这一版不做什么」），**台账登记 `versions` 一条**，卡文件上标明版本。
- 递增：PATCH 只修缺陷、MINOR 加能力、MAJOR 破坏兼容；产品经理在开工前递增；已发布过的号不复用。
- 文档：**快照型**（放各类的 `10-版本/` 子目录）复制上一版改名再改，开头固定三行 `版本` / `上一版` / `本版相对上一版的变化`；**演进型**（`10-需求/版本记录.md`、`50-运维`）一份就地更新，不拆版。
- **总判据**：删掉 `.bandi/` 之后，`docs/项目文档-by班底/` 仍然完整可读；文档正文里不出现「班底」字样。

## 十、谁管什么（不写人名）

| 角色 | 技能（能力包） | 管什么 |
| --- | --- | --- |
| 产品（兼版本） | `bandi-pm` | 谈需求、拆卡、写验收标准、**定版本与台账** |
| 研发 | `bandi-dev` | 写代码、开发报告 |
| 测试 | `bandi-qa` | 测试报告；给出通过／不通过的结论（**打回是人在实例页点，不是它自己流转**） |
| 运维 | `bandi-ops` | 发布记录、回滚方案、接入新机器 |
| 门禁与纪律 | `bandi-flow` | 三道门禁的判据、数字纪律、汇报口径；**不推流程** |

**不写人名。** 谁挂着哪个能力、谁是队长，以**平台**为准（技能页与员工详情）；本文件不记 ——
契约是要**复制到每个项目**里去的，写上人名就会过期。

**技能 = 能力，绑在数字员工身上；流程只负责点名。** **流程不按技能找人**：节点不声明技能、也不知道谁挂着什么；要谁办就在节点上点名，没点名就阻塞等人指派。

**两样不跟着头衔挪**：

1. **版本号的定夺**（开版、递增）留在产品——见「九、版本与文档速查」。
2. **版本台账（`versions`）的写入**留在产品。否则收活的人变成自己写自己核对。

**排期与跨项目优先级**：平台没有这一维（实例只有先后，没有优先级）。项目内先做哪张卡、多个项目抢同一个人（研发、测试）时谁先谁后，由**队长**（门禁与纪律那个角色）定：结论写进排期文档，别只停在对话里；把工作量写成「未估」的，去问，**不自己填个数**。
