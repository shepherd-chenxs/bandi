## 目录结构

装在项目根目录下一个 `.bandi/`，不散落：

```
.bandi/
├─ status.yaml          唯一进度来源，飞书读它
├─ README.md            本节的副本，项目内的权威定义
├─ 需求.md              一版一节，记每个版本的边界
├─ 任务卡/T-001.md      产品经理产出
├─ 开发报告/T-001.md    研发产出
├─ 测试报告/T-001.md    测试产出
└─ 发布记录/v0.3.0.md   运维产出（按版本命名，不是按卡片）
```

任务 ID 用 `T-001` 递增，前四种产物按同一个 ID 命名；发布记录例外，按版本命名 `vX.Y.Z.md`。

## status.yaml 契约

`status.yaml` 的键用英文、值用中文——键给程序读，值给人读：

```yaml

project: 项目名
stage: 开发          # 需求 | 排期 | 开发 | 测试 | 部署 | 完成
live_version: 1.2.0  # 索引登记的当前线上版本；没有线上版本就留空
doc_index:           # 项目文档索引：班底只记路径，正文在项目里
  root: docs/项目文档-by班底
  version_source: yaojian-frontend/utils/version.js  # 版本真源（纳管时问一次、登记下来）
  version_source_note: APP_VERSION                   # 真源在文件里的哪一处
  mirrors:                                          # 还写着版本号的地方（发布时一起同步）；没有就留空
    - yaojian-frontend/manifest.json
  requirement: docs/项目文档-by班底/10-需求/需求-v1.3.0.md   # 每类只登记「现在该看的那一份」的实际路径
  schedule: docs/项目文档-by班底/20-排期/排期-v1.3.0.md
  changelog: docs/CHANGELOG.md                       # 沿用原项目文档 → 登记它的原路径
  runbook: docs/项目文档-by班底/40-运维/部署手册.md
  product_spec: docs/项目文档-by班底/50-产品说明/产品说明-v1.2.0.md

  - version: 1.3.0
    title: 飞书指挥升级
    scope: 需求.md#v1.3.0    # 指向边界正文的锚点
    released:                # 该版本的发布记录路径；没有发布记录文件就留空
tasks:
  - id: T-001
    title: 任务标题
    owner: 研发       # 产品经理 | 研发 | 测试 | 运维
    status: 开发中    # 见下方状态机
```

**这几个字段名和取值就是契约，不要临时发明新的。** 真需要加字段，先改本文件并告诉用户，再往下走。

## 版本管理

**版本 = 一批任务卡的边界 + 一次发布的单位。** 名字形如 `MAJOR.MINOR.PATCH`（如 `1.2.0`）。

- **版本不是状态。** 任务状态仍然只有那 8 个；版本是**任务卡之上的一个维度**，不新增「版本状态」这种枚举。
- 一个任务卡**只属于一个版本**：`version` 必填，只能一个值。
- 版本的进展是**派生**出来的——把该版本的卡按状态聚合。
- **版本真源是项目自己的东西**——变更日志、代码里的版本常量、tag。位置登记在 `doc_index.version_source`。
- `live_version` 是**索引登记的当前线上版本**（镜像，任何时间点只有一个值），**不是真源**；与真源不一致时以真源为准改 `status.yaml`。

### 版边界（做什么 / 不做什么）记在哪

记在 `.bandi/需求.md`，**一版一节**。每节标题格式 `## v<版本号> · <一句话主题>`；节内**必须**有 `### 要做什么` 和 `### 这一版不做什么` 两个小节，缺一不可。

边界正文**只写在 `需求.md` 这一处**；`status.yaml` 的台账只放 `scope` 指针，不复制正文——同一件事不写两遍。

### 怎么答「某版里有哪些卡、都开到哪一步了」（**已作废**）

> 卡片状态不再由谁记账。要答「这一版做到哪了」→ 看**流程实例**；要答「这一版包含什么」→ 看 `versions` 与 `doc_index` 指向的版本文档。下面这段是技能时代的做法，留作历史。

读 `status.yaml`，取 `version` 相等的卡，按 8 个状态分组，输出两样：

1. 一张表：**任务 ID、标题、状态、卡在谁那（`owner`）**；
2. 一行该版本的计数（形如 `待开发 2，开发中 1`），数字之和等于该版本的卡数。

该版本全部卡 `已发布` → 该版本完成。

### 发布记录与回滚怎么跟版本对上

- **发布单位 = 版本。** 发布记录文件名是 `.bandi/发布记录/v<版本号>.md`（目录不变，命名从 `T-XXX` 改成 `vX.Y.Z`）。
- 发布记录在原有六项（编号、发布内容、发布步骤、验证结果、回滚方案、遗留问题）之外，**新增三项**：
  - `版本`：这次发布的是哪个版本；
  - `包含任务卡`：该版本的卡 ID 列表（`version` 相等的卡）；
  - `回滚目标`：**发布前**的 `live_version`——发布时就算好，不能事后猜。
- 发布完成后：`versions` 里该版本的 `released` 指向该文件；`live_version` 改成该版本；该版本所有卡 `status` → `已发布`、`evidence` 指向该版本的发布记录。
- **回滚**：不改写历史发布记录，**新增**一条 `.bandi/发布记录/v<被回滚版本>-回滚.md`，至少记：触发判据、从哪个版本回滚、回到哪个版本、结果、后续动作；同时把 `live_version` 改回目标版本。
- 于是「回滚到哪个版本」有两个各自独立、可查的答案：该版本发布记录里的 `回滚目标`，以及当前的 `live_version`。

### 面板一键部署产出的记录（v0.7.0 起 —— **已退役**）

> **一键部署没有了**：面板改只读、没有部署接口；发布由运维数字员工在会话里做，过程留在事件流里。下面这段是旧面板的行为记录，留作历史；现行的部署口径见 `.bandi/README.md` 的「`deploy` 段」与 `bandi-ops`。

- 面板部署成功后写 `.bandi/发布记录/v<版本号>.md`：**不存在则生成、已存在则文末追加部署小节，绝不改写已有内容**。自动生成的记录显著标注「面板自动生成」，只写实际发生的（版本、卡、目标、时间、部署入口、退出码、日志路径、登记的回滚入口）；**发布前检查单、验证结果、回滚演练留给运维补记**——面板不替代发布门。
- 执行日志全量落盘 `.bandi/发布记录/日志/v<版本>-<时间戳>.log`，边跑边写，面板中途被杀日志也在。
- 面板的**写入白名单**（契约 §二「面板写入白名单」的细则）：`发布记录/` 下的记录与日志、`status.yaml` 里该版本待部署卡的 `status` 与 `evidence`、`versions` 里该版本为空的 `released`、顶层 `updated` 时间戳。**面板不改 `live_version`**——「发布完成后 live_version 改成该版本」是手工发布流程的动作，由运维核对后自己改。

### 部署单和 `deploy` 段怎么对上（v0.8.0 起 —— **已退役**）

> **部署单没有了**：`50-运维/10-部署单/` 与「登记部署目标」表单都已退役。现行做法：`deploy` 段只是**登记**（发到哪台机、哪个路径、怎么回滚），执行由运维在会话里按 `bandi-ops` 的接入协议做。下面这段留作历史。

面板「登记部署目标」走的是**先派单、后按钮**的两段路，两个落点各管一半：

- **`deploy` 段条目**：表单提交后追加一条，`method` 固定 `script`、`script` / `rollback` 写空值——这三个空位是**故意留的**：部署入口与回滚入口由 agent 按部署单开路后回填，回填了门禁自然变绿（沿用一键部署的 `deploy_gate`，不写任何新逻辑）。别名 `name` 段内唯一，面板按它把部署单挂到目标上。
- **部署单** `50-运维/10-部署单/D-XXX.md`：编号在已有 `D-*.md` 里取最大 +1；内容带索取包全字段、agent 执行指引（引用 `bandi-ops` 接入协议四段）、回填清单、完工判据。**面板只读「目标别名」「状态」两行**（状态取值：待执行 / 执行中 / 已完成 / 失败，由执行者手工更新），其余内容归执行者。
- **回填清单四样**（干完才算收口）：`deploy` 段回填 `script` / `rollback`、机器清单登记、发布记录落盘、部署单状态改「已完成」。完工判据一句话：**忘掉 agent，面板按钮能独立完成第二次部署**。
- **凭据边界**：表单与部署单都只收「交付方式 + 落点路径」（落到本机路径 / 已在 ssh-agent），结构上没有口令与私钥正文的输入框——`deploy` 段与部署单都是要进 git 的文件，凭据正文从结构上进不来。

### `released` / `scope` 为空的口径

- `released` 为空 = **没有发布记录文件**——可能是还没发布，也可能是制度建立之前的历史版本。它**不是**「这个版本没做过」。
- `scope` 为空 = 边界正文没有落在 `需求.md`（同样只出现在历史版本上）。

### 版本号谁递增、什么时候递增、怎么递增

- **谁递增**：产品经理在「定计划」阶段递增。**运维不递增**——运维只发布 / 回滚已经定好的版本号。
- **什么时候**：开发开工**之前**就把版本号定死、登记台账；开工后不改号。一批卡全部 `已发布` → 该版本关闭，下一批新卡必须开新版本。
- **递增规则**（语义化）：
  - `PATCH +1`（`1.2.0 → 1.2.1`）：只修缺陷，不加能力、不改契约；紧急修复走这条。
  - `MINOR +1`（`1.2.1 → 1.3.0`）：向后兼容地加能力（新卡、新技能章节、新字段）。
  - `MAJOR +1`（`1.3.0 → 2.0.0`）：破坏兼容（改契约、改产物结构、改状态机、老用户的用法要变）。
  - 跨过 `1.0.0` 之前（`0.y.z` 阶段）改契约走 `MINOR +1`——`0.y.z` 表示初始开发期，任何东西都可能变。
  - 预发布号（`-rc1` / `-beta`）不在本版范围。
- **已发布过的版本号不复用**：回滚之后要再发就往上开新号（`1.3.1`），不许原地重发 `1.3.0`。

### 真源与镜像：真源在项目里，班底只记路径

| 类别 | 是什么 | 语义 |
| --- | --- | --- |
| 唯一真源 | `doc_index.version_source` 登记的那一处 | 「这个项目的版本号谁说了算」。纳管时问用户一次，落进索引；之后一律读这里 |
| 镜像 | `doc_index.mirrors` 清单里的每一处，以及 `status.yaml` 的 `live_version` | 取值应等于真源。`live_version` 是**索引登记的当前线上版本**；不一致时**以真源为准去改 `status.yaml`**，不许反过来改项目自己的版本声明。清单为空 = 这个项目只由真源一处记账 |
| 不参与一致性检查 | `docs/vX.Y.Z-设计.md` 的文件名、老格式文档抬头里的「版本：」 | 设计归属 / 老格式文档，不算版本声明 |

「三镜像（仓库根 `VERSION`、`plugin.json` 的 `version`、根 `README.md` 的版本句）必须永远同值」**只对本仓库成立**——把这三处写进本仓库的 `mirrors` 即可，不要当通用规矩：真实项目里这三处常常一个都不存在。

### 当前版本：纳管时问一次、登记真源，之后一律读索引

**那张六处探测顺序表（`status.yaml` → `VERSION` → `plugin.json` → 根 `README.md` → `docs/` 设计文档名 → `git tag`）作废。** 依据是实测：真实项目 `yaojian` 六处里只命中 `git tag` 一处（`status.yaml` 那处是班底自己写进去的，循环），真正管用的 `docs/CHANGELOG.md` 和前端 `utils/version.js` 的 `APP_VERSION` 一个都没进表；同一份清单里 8 个 `pom.xml` 全写着 `1.0.0`（父模块坐标）。**列一张可能命中的表，不如问一次、登记一次、再核对一次。**

纳管一个项目时走一遍：

1. **问用户一次**：这个项目的版本号，**哪个文件说了算？**
2. **登记**：答案写进 `doc_index.version_source`（+ `version_source_note`）。
3. **当场核对一次**：读那一处取值，与用户同时给出的「现在是什么版本」、与 `git tag` 最近一个各对一遍；**三处不一致就列出来问用户，不许挑一个**。
4. **登记镜像清单**：再问一句「还有哪些地方也写着版本号？」→ 写进 `mirrors`；**答「没有」就留空**。
5. **登记五个入口路径**：见「项目文档规范」。
6. **之后一律读索引**：任何一次「现在是什么版本 / 文档在哪」，读 `doc_index` 就够，不再满仓库探。

### 三态判据：读到什么，就做什么

判定「读到的版本号」时，**空值、缺字段、文件不存在都算「未读到」；未读到不是矛盾。**

| 读到的结果 | 必须做什么 |
| --- | --- |
| 只读到一处；或读到多处但**值全部相同** | 直接采用，**不再问用户**；按需要写进台账，**不新开版本** |
| **一处都没读到** | 提出一个初始版本号并**记录**：默认 `0.1.0`；在 `需求.md` 写 `## v0.1.0 · <主题>` 一节（含两个小节），在 `status.yaml` 的 `versions` 登记一条、`released:` 留空；`live_version` **仍留空**（还没发布）；并向用户说明「这是本项目的初始版本，我按 `0.1.0` 起」 |
| **两处及以上，且值各不相同** | **不许自己挑一个**：把矛盾如实列出（哪几处、各写了什么），给建议值，请用户拍板；拍板**之前**不得往 `versions` / `需求.md` / 任何文件里登记版本号 |

**「两处及以上、值各不相同」是矛盾的唯一判据。** 只有一处写了版本号、别处空着或缺字段 → 按「只读到一处」处理，直接采用；**不许拿空值凑数说「对不上」**。

**默认初始版本号是 `0.1.0`，不是 `1.0.0`**——语义化版本里 `0.y.z` 表示「初始开发期，任何东西都可能变」，还没到承诺兼容的阶段就别占 `1.0.0`。记录只用两处：`需求.md` 一节放边界正文，`status.yaml` 的 `versions` 放指针。

## 项目文档规范

**文档属于项目，不属于班底。** 班底只往里写、并在索引里记路径。

### 位置与目录名

项目根下的 `docs/项目文档-by班底/`。文件夹名**用户定死，不改**——不翻译、不改大小写、不加版本号后缀。它必须是 `docs/` 下的一个子目录：**不许直接铺在 `docs/` 根上，也不许放到项目根之外。**

### 编号登记表

| 编号 | 目录 | 类型 |
| --- | --- | --- |
| 10 | `docs/项目文档-by班底/10-需求` | 快照型 |
| 20 | `docs/项目文档-by班底/20-排期` | 快照型 |
| 30 | `docs/项目文档-by班底/30-版本记录` | 演进型 |
| 40 | `docs/项目文档-by班底/40-运维` | 演进型 |
| 50 | `docs/项目文档-by班底/50-产品说明` | 快照型 |

三条规则：

1. 目录名 = `<两位数字>-<类别名>`，类别名用中文。
2. **编号按十位分配、中间留空号**（用到 10/20/30/40/50，11–19、21–29、31–39、41–49、51–59 全空着）；六类及以后从 60 往下发。
3. **编号一旦分配，永不变更、永不重排。** 要插入一个新类别，**取一个空号**（例如「测试」取 25）；不许改已有目录的号，也不许为了整齐重排。类别在文档里的先后顺序可以调，**编号不跟着调**。

类别只有这五类。要加第六类，先改本文件并告诉用户，再加目录。

### 快照型 / 演进型

| 类别 | 类型 | 规则 |
| --- | --- | --- |
| 需求、排期、产品说明 | **快照型** | **复制上一版 → 改名成新版号 → 再改**。每版留一份文件，谁也不覆盖谁 |
| 版本记录、运维手册 | **演进型** | **一份文件，按版本追加或就地更新**，不拆成每版一个文件 |

- 版本记录每版一个文件，会丢掉「一处按时间线读懂整个项目」的价值——那是它唯一的价值。
- 运维手册是「当下怎么部署」，不是历史档案；翻它的人要的是现在这台机器该怎么做。历史做法属于历史，**历史进版本记录**。

### 快照型开头固定三行

快照型（需求 / 排期 / 产品说明）每份文件的**第 1–3 行必须是**（全角冒号，一个字不差）：

```
版本：v1.3.0
上一版：v1.2.0
本版相对上一版的变化：<一句话写实>
```

- `上一版` = **从哪份文件复制来的**；首版写 `上一版：无（首版）`。
- `本版相对上一版的变化` 必须写实；首版写 `首版`。**不许写「无」「同上」「略」**——没有变化就不该开这一版。
- 有 `上一版`，整条版本链**在文件自己身上**就能一路往回读——这是「删掉 `.bandi/` 之后文档仍完整可读」的支点。

### 命名，与「不许按文件名排版本号」

- 快照型：`<类别名>-v<版本号>.md`（`需求-v1.3.0.md`、`产品说明-v1.2.0.md`）。
- 演进型：类别目录下**只有一个主入口文件**（如 `30-版本记录/版本记录.md`、`40-运维/部署手册.md`）；可以有从入口文件相对链接出去的附属文件，但**索引每类只登记入口那一份**。

**铁律：不许靠文件名排版本号。** `v1.10.0` 按字符串会排在 `v1.2.0` 前面。文件名里的版本后缀**只为人眼识别**；**任何「取当前版」的动作（人、脚本、后续技能）都必须走索引**——不许 `ls | sort` 取最后一个、不许正则取最大、不许「看着像最新的那个」。

### 既有项目文档：不搬家、一行指针、机器只认索引

1. **已有等价文档：不搬家。** 原文件留在原地，**路径与内容一个字不改**（不复制进来、不改名、不移动）。
2. **在对应编号目录里放一行指针**：该目录下的 `README.md`，**全文只有一行**——固定四个字「本项目沿用」+ 一个空格 + 反引号包起来的**相对项目根路径**。例：`30-版本记录/README.md` 全文就是「本项目沿用 `docs/CHANGELOG.md`」。不许加标题、日期、说明、签名。
3. **没有等价文档的类别：新建**——快照型从当前版本起建一份（带三行头），演进型建入口文件。
4. **机器只认索引里登记的实际路径，不许在 `docs/` 里猜。** 任何取路径的动作（读版本记录、找产品说明、写变更日志）都读 `doc_index`；**禁止**在 `docs/` 下 glob、按名字像不像去猜、遍历目录找「最像的那一份」。
5. 指针 README 只是给人看的路牌，**不参与索引**：索引登记的是**正文的实际路径**（沿用时就是它的原路径，如 `docs/CHANGELOG.md`）。

> 由此可推出一条简化：索引路径**在 `docs/项目文档-by班底/` 之内** ⇒ 新建的；**在其之外** ⇒ 沿用的原项目文档。所以不需要另加字段去标「新建 / 沿用」。

### `doc_index`：字段口径

字段示例见上面的 `status.yaml` 契约。

- `root`：项目文档根。**改它等于改契约级别的事。**
- `version_source` / `version_source_note`：这个项目「版本号由谁说了算」及其位置（如 `APP_VERSION`）。**纳管时问用户一次**，之后一律读这里。
- `mirrors`：还写着版本号的地方（清单）；发布 / 回滚时**清单里每一处一起改**。**清单为空 = 只由真源一处记账。**
- 五个入口键固定：`requirement` / `schedule` / `changelog` / `runbook` / `product_spec`，与五个编号目录一一对应；**不许改名、不许加第六个入口**（要加类别先改契约）。
- 每个入口的取值 = **「现在打开这一类，就该看的那一份」的实际路径**（相对项目根）。
- **「现在线上是哪个版本」和「现在该看哪一份」是两个问题**：前者答 `live_version`，后者答入口路径，两者**不必同版本**（线上 `1.8.0`，`requirement` 可能已经是开发中的 `需求-v1.9.0.md`）。**由索引回答，不许猜。**
- **某一类还没建**：该键留空。口径与 `released` 一致——空 = 「这一类还没有登记的路径」，不是「这类不存在」。
- **不新增第二个版本字段**：索引里的「当前版本」就用既有的 `live_version`。

### 发布链

规则链照抄成流程：**需求先定版本 → 开发完之后写变更日志 → 提交代码 → 打 tag。**

1. **定版本**（产品经理，开发开工前）：开快照——`需求`、`排期` 各**复制上一版 → 改名成新版号 → 改三行头与正文**；更新 `doc_index` 的两个入口；`versions` 台账加一条。
2. **开发**（研发）。
3. **写变更日志**：向**演进型**的 `changelog` 那一份**追加一节** `## v<版本号> · <日期>`，写清这一版改了什么。
4. **产品说明按版本留存**：`产品说明` **复制上一版 → 改名成新版号 → 改内容**；`doc_index.product_spec` 改指新版；**老版文件不动、不删**。
5. **提交代码。**
6. **打 tag**：`v<版本号>`。
7. **同步索引与镜像**：`live_version` 改成新版本；`mirrors` 清单每一处一起改；`doc_index` 里所有快照型入口指向新版文件。

**`.bandi/发布记录/` 与项目文档的 `版本记录` 是两件事，别混**：前者放**发布过程**（步骤、验证结果、回滚方案、回滚目标），是班底的干活记录；后者放**对外可读的变更内容**。**删掉 `.bandi/` 之后，项目的变更史仍要从 `版本记录` 里读得出来。**

### 总判据：删掉 `.bandi/` 之后，文档仍完整可读

四条都要过：

1. **五类入口都在、非空**（含指针 README 指向的原项目文档）。
2. **每份快照型的三行齐全**，人能沿 `上一版` 一路读回最早的版本。
3. **演进型文件里按版本的节齐全**，读得出时间线。
4. **正文不依赖 `.bandi/`**：`docs/项目文档-by班底/` 下的正文里**不出现 `.bandi` 字样**，也不出现 **「班底」** 二字——**文件夹名 `项目文档-by班底` 是用户定的，不算在内**。

> 第 4 条的理由：`.bandi/` 是班底的账本，用户随时可能不要它。**删掉它，文档要还是文档**；反过来说，文档里一旦写了「见 `.bandi/xxx`」，「班底」就不再是可选的外部工具，而是文档的必需依赖——那就违背了「文档属于项目、班底跟项目不耦合」。

## 五个环节（**已作废**：现在是流程模板的节点）

> 谁上场不再靠"信号触发"，而由平台流程模板决定：内建模板的节点是「谈需求 / 定计划 / 写代码 / 测试 / 部署」，各自带 `skill`（`bandi-pm` / `bandi-pm` / `bandi-dev` / `bandi-qa` / `bandi-ops`），到站即派活、停不停看节点的 `manual` 开关。见 `.bandi/README.md`「五、谁上场」。下表是技能时代的分工，留作历史。

| 环节 | 技能 | 什么信号触发（历史） |
| --- | --- | --- |
| 谈需求 | `bandi-pm` | 用户描述一个想做的东西，还没成形的需求 |
| 定计划 | `bandi-pm` | 需求对齐了，要拆任务和排期 |
| 写代码 | `bandi-dev` | 有 `待开发` 的任务卡 |
| 测试 | `bandi-qa` | 有 `待测试` 的任务 |
| 部署 | `bandi-ops` | 有 `待部署` 的任务 |

## 派活规则（**已并入平台**）

1. **用户明确指派就照办** → 现在是在实例页改这一步的经办人。
2. ~~**用户没说就按状态机推**~~ → 现在由模板的节点与连线推进，不许自己造下一步。
3. **一次只推进一条流程、一步。** 要并行是再起一条实例。
4. **状态和现实不符时，以平台为准，但要告诉用户。**

## 范围和停止（优先级最高，压过上面所有规则）

1. **用户划的范围就是边界。** 用户说"只做 X"就只做 X；说"先不碰 Y"，那即使状态机推得下去，也不做 Y。
2. **做完一步就停。** 停不停现在由节点上的 `manual` 开关决定：勾了就是"干完停下等人放行"，没勾就是"干完自动往下"。**你不自己决定要不要往下走。**
3. **派生出去的角色不能越界。** 派给某个角色，它只做那一段，做完交回来；不许它顺手把下游角色的活一起干了，也不许它再往下派生。

## 三道门禁

门禁不通过就不许往下走，这是硬的：

| 门禁 | 卡在哪 | 判据 |
| --- | --- | --- |
| 排期门 | `bandi-pm` 出任务卡前 | 每条验收标准都能被执行、被复现吗？ |
| 交付门 | `bandi-qa` 出结论时 | 每条验收标准都有证据吗？ |
| 发布门 | `bandi-ops` 发布前 | 检查单全过、回滚方案写了吗？ |

用户要求跳过门禁时，把后果说清楚再执行，并在**流程实例的那一步上写明**（备注或人工标记），别只停在对话里——`tasks` 段已经不许再改了。

## 状态机（**已作废**）

> 卡片不再是状态的载体，这 8 个状态与「状态纪律」一并作废。现行：流程实例只有 `进行中 / 已完成 / 已终止`，当前这一步只有 `待开始 / 进行中 / 待确认 / 已完成 / 已阻塞 / 失败`，决定只有 `通过 / 驳回 / 终止` —— 见 `.bandi/README.md`「三」。下面留作历史。

每个任务只有这 8 个状态，别临时造新的：

```
待开发 → 开发中 → 待测试 → 测试中 ─┬─→ 不通过 ─→ 开发中
                                    └─→ 待部署 → 已发布

任意状态 ─→ 已阻塞
```

`stage` 只有 6 个取值：`需求 | 排期 | 开发 | 测试 | 部署 | 完成`。

`不通过` 是**独立状态**，不是"回到开发中"的注释——打回必须在进度上留下痕迹，产品经理必须看到，研发必须重新认领。

**版本是任务卡之上的一个维度，不是第 9 个状态。** 版本的进展靠聚合派生（见「版本管理」）——不引入「版本状态」这种新枚举。

## 状态纪律（**已作废**）

> 现行纪律只有一条：**进度只有一个来源——平台的流程实例**；不许另建进度文件、不许再往 `status.yaml` 的 `tasks` 里写状态。见 `.bandi/README.md`「七」。下面留作历史。

- **只有一个进度来源。** 所有角色都改 `status.yaml`，不许各自维护一份。
- **状态只升不降。**
- **`不通过` 是独立状态，不是注释。**
- **改完状态要更新 `updated` 字段**，格式 `YYYY-MM-DD HH:MM`。

## 数字纪律：自报数字不可信（三件套）

**缺一不采信**：进报告、卡片、文档的数字必须带 **命令原文 + 完整输出 + 采集时间**。

- **必须自带基准**：写清跟谁比（`v1.8.0..HEAD`、`origin/master..HEAD`、`origin/feature-x..HEAD` 是三件不同的事）。「多了 20 个提交」这种没有基准的写法一律不采信。
- **基准要选对**：feature 分支上问「累积了多少提交」，跟它自己的 upstream 比才是这个话题；跟 `origin/master` 比是另一个话题（同一棵树同一天，前者 13、后者 58）。选错基准不是算错，是**答错题**。
- **两处对账**：进文档的数字用另一条命令复核一次（例如 `git rev-list --count <基准>..HEAD` 与 `git branch -vv` 里的 `ahead N` 互相对账）。两处不一致就标「存疑」，**不许挑一个填上**。
- **没实测的写「未验证」。**

这是**全体角色**的纪律：定义只写在本文这一处，各技能引用，不各写一份。

## 汇报

问进度时**看流程实例**（当前节点、经办人、进行中/待确认/已阻塞），直接给一张表。不要复述过程，不要罗列文件路径，除非用户要。

问**某一版**时：读 `status.yaml` 的 `versions` 与 `doc_index` 指向的文档，给那一版的边界与发布状态。**不要再按卡的 8 个状态分组**——那套已作废。
