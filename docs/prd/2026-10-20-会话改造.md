**原始需求复述（用户已确认，不推翻）**

1. 消息列表项去掉悬浮「×」，改右键菜单：「删除」= 彻底删除（消息一并永久删除、不可恢复，需二次确认）；「不显示」= 现有 hide（列表不显示、记录保留、可从「已移除的会话」恢复）。
2. 详情页「发消息」= 每次发起一条全新的 1:1 会话，不复用旧会话（一次任务一段，独立成条）。
3. 「聊天记录」按钮（现为占位）落地：显示这个人的所有历史会话（标题/时间/预览），点击可回看、可继续聊。
4. 消息列表里同一个人只显示**当前/最新**一条会话，其余历史会话进「聊天记录」，不占列表行。

**范围**：本次只动会话（conversation）的**展示与删除**，不加新表、不加新字段、不引入「置顶 / 当前会话」这类新概念。

## 二、产品定义

### 2.1 产品目标

1. **一次任务一段会话**：从员工详情页点「发消息」永远是新的一段，上下文不串味；与 Codex / DeepSeek 的单次会话心智一致。
2. **列表只留当下要处理的**：消息列表一人一行；历史不占行，但一条不丢——可查（聊天记录）、可续聊、可恢复。
3. **删除语义分明到不会误操作**：「不显示」可恢复、「删除」永久消失，两者在文案与视觉上区分清楚。

### 2.2 用户故事

- 作为使用者，我在员工详情页点「发消息」，希望**开一段干净的对话**，而不是接着三个月前那堆旧消息往下聊。
- 作为使用者，我处理完一段任务后，希望消息列表里这个人**只剩最新那条**，不被同一人的 N 段历史刷屏。
- 作为使用者，我想点聊天头部「聊天记录」**翻这个人的历史会话**，找到上次那段接着聊，聊完它就自动回到列表最前。
- 作为使用者，我右键一条会话，能选择**只是不想看见它**（以后还能找回），还是**彻底删掉它**（含消息，谁都找不回）。
- 作为使用者，误删是不可接受的，所以点「删除」时我要先看清**到底会消失什么**。

### 2.3 核心规则（本文档的结论，实现按此）

**规则 1 · 当前会话的定义**
某人名下 `kind='direct'` 且 `hiddenAt IS NULL` 的会话里，`updatedAt` 最大的那条 = **当前会话**；其余同条件的会话 = **历史会话**。
> 不新增字段、不新增「置顶」概念：`updatedAt` 已经由 `store.addMessage` 在每次说话时刷新（`store.mjs:1377`），天然就是「最后活跃时间」。

**规则 2 · 消息列表展示**
- `kind='direct'`：每个 persona 只显示**当前会话**（一行一人）。
- `kind='group'`：按现状显示（一个群本来就一条会话，天然唯一）。
- `kind='exec'`：照旧不进列表。
- 收敛在**前端**做（`S.conversations` 已返回全部未隐藏会话，按 `personaId` 取 `updatedAt` 最大即可）；不改 `listConversations` 的查询，避免影响工作台等其它调用方。

**规则 3 · 活跃即上浮**
在「聊天记录」里打开旧会话并继续说话 → `addMessage` 把它 `updatedAt` 刷到最新、并清掉 `hiddenAt` → 它重新成为当前会话、回到消息列表。
> 明确采纳：**是**。谁最后活跃谁上，规则才自洽；用户不需要理解「当前」是个手动状态。

**规则 4 · 聊天记录的范围**
只列该 persona 的 `kind='direct'` 且 `hiddenAt IS NULL` 的会话，**包含当前会话**（用户原话：「聊天记录就是一个会话列表」），按 `updatedAt` 倒序。
被「不显示」的会话**不进聊天记录**——它已经在「已移除的会话」里，且「不显示」的语义就是不想看见；两处都给会让人以为没生效。

**规则 5 · 删除 = 物理删除，且不可恢复**
删除会一并抹掉：会话本身、它的全部消息、它的运行记录与运行事件、成员会话状态。删除后**不出现在「已移除的会话」里**，任何入口都找不回。
「已移除的会话」只收纳 `hide`（和群解散）造成的记录，语义保持为「藏起来了，不是删了」。

**规则 6 · 删除后的兜底**
删掉当前会话后，该 persona 剩余 `hiddenAt IS NULL` 的最新一条自动成为当前会话；一条不剩 → 这个人在消息列表里消失（跟他有关的记录都已按用户意愿删除）。

**规则 7 · 跑中保护**
会话有运行中的 run（`status='跑中'`）时，「删除」置灰并说明「这段还在跑，等它跑完或先终止再删」。后端同样兜底拒绝（错误码 + 中文），因为前端可以被绕过。
> 选择「禁用」而不是「先自动终止」：静默终止一个正在干活的 agent 比让用户多点一步更糟。

**规则 8 · 不受影响的部分**
工单会话（`exec`）、群聊的现有行为不变；群聊本次**不提供**「删除」（解散群仍是群设置里的既有操作）。

**规则 9 · 看板/工作台的「聊天派活」行会变多（已知副作用，接受）**
`project-tasks.mjs:229 chatRows` 是「一个会话一行聊天派活」。一人多段会话之后，同一个人在看板上可能出现多行。
判定：**这是语义更准，不是回归**。原来一个人在一个会话里派过 3 次活，看板只留最近一轮，前两轮直接看不见；现在一段会话一段活，各占一行，都对得上。
补充两条边界：a) 没跑过活的空会话不产生行（`if (!runs.length) continue`），所以连点「发消息」不会弄脏看板；b) 若日后行数确实挤，解法是在看板层按 persona 归并（**不是**限制会话数量），本次不做。

### 3.3 UI 设计草案

**① 消息列表项**
```
┌──────────────────────────────────┐
│ (头像) 张三              14:32    │   ← 悬浮只做背景高亮，不再出现「×」
│        ● 帮我看下这个报错…        │

```
- 删掉 `.item-x` 与它的 hover 规则；行其余结构、高亮、时间戳不动。
- 列表项加 `contextmenu`：`preventDefault()` 后按 `clientX/clientY` 弹菜单；右键某行**不**打开该会话（不触发 `click`）。

**② 右键菜单（新增轻量浮层）**
```
┌────────────────┐
│  删除           │  ← 危险色（红），右侧留出与「不显示」的间距
│  不显示         │
└────────────────┘
```
- 单例 DOM，挂在 `body` 下，`position: fixed`，`z-index` 高于列表与抽屉；随手势定位，右/下越界时向左/上翻转。
- 关闭时机：点任一项、点空白、`Esc`、滚动、窗口失焦、切换路由。
- 删除项在跑中时置灰 + `title` 说明原因，不响应点击。
- 视觉沿用项目现有浮层的圆角、阴影、字号（与群设置/下拉一致），不新造一套主题。

**③ 删除确认（复用 `confirmDo`）**
```
标题：永久删除这段会话
正文：删除「和 张三」？这段里的消息会被永久删除，找不回来。
      （「不显示」只是从列表收起来，那条还能在「已移除的会话」里找回。）
```

**④ 聊天记录视图（右侧抽屉，复用现有 drawer 容器）**

- 列表项：预览（末条消息截断，粗体；空会话写「还没聊过」）+ 时间；当前会话打「当前」标记（可点，点了就是回到它，无害）。**不显示条数**（数据在 `S.conversations` 里现成，不为它加接口）。
- 点击任一项 → 关抽屉 + `openConversation(id)`；如果该会话 `hiddenAt` 非空（理论上不在列表，防御性处理）先 `unhide`。
- 空态：「还没有更早的会话」+「从员工详情页点『发消息』，每次都会开一段新的」。
- 手势/键盘：`Esc` 关闭（与现有抽屉一致）。

**⑤ 详情页「发消息」**
按钮、位置、文案都不变；只改行为：**新建一段 → 进消息页 → 光标就位**，并且仍先 flush 自动保存。

### 3.4 验收标准

1. 消息列表里同一个人只出现一行（当前会话）；聊天记录里的行数 = 该 persona 未隐藏的 direct 会话数（含当前这条）。
2. 详情页连点两次「发消息」，产生两段独立会话（若两次之间没说过话，按 P1-2 复用一个空会话）。
3. 旧会话在聊天记录里说一句后，它回到消息列表成为唯一一行，原「当前」那条降级进聊天记录。
4. 右键「不显示」→ 列表少一行、`/api/archived` 多一条、可在「已移除的会话」恢复；聊天记录里看不到它。
5. 右键「删除」→ 二次确认文案含「永久」「不可恢复」字样 → 确认后列表、聊天记录、已移除的会话里都查不到；直接查库 `messages` / `runs` / `run_events` 无残留，引用过它的任务卡还在（只是 `conversationId` 变空）。
6. 跑中会话的「删除」是灰的，接口直调返回错误码而非 500，且库内数据完整。
7. 全程无 `alert` / 原生 `confirm`；失败提示为「错误码 + 中文」。

## 四、待确认问题（3 条，附建议默认值）

1. **群聊这次要不要一起上右键菜单？**
   建议默认：**要，但只给「不显示」**，不给「删除」。群的历史（尤其多人协作记录）物理删除风险太高，解散群已有独立入口；实现成本只是多分支渲染一个菜单项。

2. **详情页连点「发消息」时，已经有一段刚建好、一个字没说过的会话，还要再建一条吗？**
   建议默认：**不建，复用它**（P1-2）。否则用户手抖两下就多出一条空会话，还要手动删。

3. **被「不显示」的会话，要不要也出现在聊天记录里？**
   建议默认：**不出现**。聊天记录只承载「正常存续」的历史；隐藏的留在「已移除的会话」，两处入口各司其职，避免语义打架。

## 五、给架构/开发的一句话

改动集中在 4 个文件、1 个新接口、1 个新浮层：`app.js`（列表项 + 右键菜单 + 聊天记录抽屉 + 详情页跳转 + 列表收敛）、`style.css`（删 `.item-x`、加菜单/抽屉样式）、`server.mjs`（DELETE 路由）、`store.mjs`（`deleteConversation` 事务）。其余全部复用现有 hide / archived / createConversation 能力。
