# 班底 · 增量 PRD：手机端（PWA 响应式改造 + 扫码配对）

> 本文为增量 PRD，只描述本期变更部分。基线以桌面端现有 PRD/实现为准。
> 已定决策（不在本文讨论范围内推翻）：本期不做原生 APP；不做外网穿透/中继（总机中继为后续迭代）；不做推送通知；复用 `apps/web` 前端做响应式改造；手机端做受限视图；扫码配对换发长期令牌。

---

## 1. 产品目标

1. **局域网手机可用**：同一局域网内的手机浏览器（iOS Safari / Android Chrome）可直接访问 PC 上的班底服务，完成配对后无需手动输地址、无需重复登录。
2. **受限视图即可交付价值**：手机端覆盖"看状态、审卡票、和员工轻量对话"三个核心场景，P0 流程 3 步内可达（验证标准：配对后任意页面出发，到"查看任务卡详情 / 审批一张卡票 / 给指定员工发一条消息"各不超过 3 次点击）。
3. **一次改造双端受益**：`apps/web` 完成响应式基础改造后，桌面窄窗口（半屏、小笔记本）体验同步改善，不引入独立移动端代码分支。

## 2. 用户故事

**PC 主用户（桌面端操作者）**

- 作为 PC 主用户，我想在设置页一键弹出"配对二维码"，让手机扫码即用，以便不用在手机上手动输入局域网地址和令牌。
- 作为 PC 主用户，我想在设置页看到当前已配对的手机设备列表（设备名、最近活跃时间），并踢出不再使用的设备，以便控制局域网访问安全。

**手机用户（同一人拿起手机，或家庭成员/协作者轻使用）**

- 作为手机用户，我扫码后希望页面直接打开工作台首页并自动完成登录（令牌已换发保存在本机），以便 10 秒内能看到班底当前状态。
- 作为手机用户，我想在手机上浏览项目任务看板、点开卡片查看详情，以便离开电脑时也能掌握任务进展。
- 作为手机用户，我想在手机上对一张待审批卡票执行"通过/驳回（附一句理由）"，以便不阻塞团队成员的派活流程。
- 作为手机用户，我想在手机上选中一个员工进入会话并发送消息（文字为主），以便随时和 AI 员工保持轻量沟通。
- 作为手机用户，我把班底添加到主屏幕后，希望它以独立窗口、带图标的方式打开（像 App 一样），以便长期当成一个应用使用。

## 3. 需求池

### P0（Must have，本期交付）

| # | 需求 | 说明 |
|---|------|------|
| P0-1 | **响应式布局改造（核心三视图）** | ① 左栏列表视图：`<900px` 宽度时"左栏列表 + 右栏详情"主从结构折叠为单栏，列表占满屏，点击进入详情页，返回回列表（含专家/成员列表、项目列表）；② 卡片墙视图：任务看板列在窄屏下从多列横排改为单列纵排或横向滑动列，卡片信息密度收敛（标题+状态+负责人+截止）；③ 对话页：输入栏吸底、消息区全屏、键盘弹起不遮挡。`style.css` 仅 6 处 @media，本期系统化补齐断点体系（建议 `900px / 600px` 两档）。 |
| P0-2 | **扫码配对流程** | 桌面端设置页新增"手机配对"入口：服务端生成一次性配对令牌（短时效，如 5 分钟、单次使用），把 `http://<局域网IP>:8787/pair?token=xxx` 编码为二维码展示。手机扫码打开页面 → 校验一次性令牌 → 服务端签发长期会话令牌（按设备维度）→ 手机保存并进入工作台。二维码弹窗带倒计时与刷新。 |
| P0-3 | **手机端登录/令牌机制** | 长期令牌存储于手机端（localStorage + httpOnly cookie 兜底，取实现成本低的方案）；所有手机请求带令牌鉴权；令牌失效时引导重新配对而非裸登录页（本期不做账号密码登录）。服务端需新增设备表（device_id、设备名、令牌哈希、最近活跃时间）。 |
| P0-4 | **PWA manifest + 图标** | 新增 `manifest.json`：名称/图标（192/512）/`display: standalone`/主题色；iOS 补 `apple-touch-icon` 与 meta 标签。目标：手机"添加到主屏幕"后以独立窗口打开、有像样的图标。 |

### P1（Should have，紧随其后）

| # | 需求 | 说明 |
|---|------|------|
| P1-1 | **手机端交互优化** | 窄屏下增加底部导航（工作台 / 会话 / 我的），替代桌面左栏；对话页输入框聚焦时页面正确上推；列表页下拉刷新手势；关键弹窗改为底部抽屉（bottom sheet），更符合拇指操作。 |
| P1-2 | **配对设备管理** | 设置页展示已配对设备列表（设备名、配对时间、最近活跃），支持踢出（吊销令牌）。安全兜底能力，建议紧跟 P0-2/3 交付。 |
| P1-3 | **Service Worker 缓存骨架** | SW 预缓存静态资源（HTML/CSS/JS/图标），API 请求不缓存（本地优先产品，数据以服务端为准）。本期只打地基，为 P2 离线只读快照做准备；同时解决弱网局域网下静态资源重复加载慢的问题。 |

### P2（Nice to have，后续迭代）

| # | 需求 | 说明 |
|---|------|------|
| P2-1 | 离线只读快照 | SW 缓存最近一次拉取的任务/会话摘要，断网时展示只读快照并标注"离线数据"。依赖 P1-3。 |
| P2-2 | 桌面通知转发 | PC 端事件（卡票待审批等）转发到手机端页面内角标/横幅。**不做系统级推送**（决策已定），仅限页面打开时的应用内提醒。 |
| P2-3 | 手机端发起轻量任务 | 允许手机端向员工派一条轻量指令（语音输入可探索）。先验证对话场景再扩展。 |
| P2-4 | 外网访问（总机中继复用） | 复用现有总机/节点中继让手机在外网访问。明确列为后续迭代，本期不做。 |

### 调整理由说明

- 相对候选清单的**增项**：P1-4（对话富内容降级规则）——来自飞书接入失败的直接教训，必须在对话页改造时同步定义，否则手机对话页会被富内容撑爆。
- 相对候选清单的**降级/明确化**：P2-2 明确为"应用内提醒"而非推送通知，对齐已定决策；P2-4 从 P1 候选中移到 P2，因为外网访问依赖总机中继迭代节奏。
- P1-2（设备管理）从 P2 上调至 P1：配对令牌一旦发出，没有吊销手段会带来局域网安全隐患，应与配对功能几乎同期交付。

## 4. UI 方向（文字版线框）

**主从结构映射**：桌面端"左栏列表 + 右栏详情"是全产品的主骨架（专家列表、项目列表、会话列表皆如此）。窄屏统一映射为**两级导航**：

- **一级页（列表）**：原左栏占满全屏，顶部保留页标题 + 操作按钮（如"新会话"），列表项增大触控行高（≥48px）。
- **二级页（详情）**：点击列表项，右栏详情内容全屏铺开，顶部出现"← 返回"栏。不使用侧滑抽屉放详情（抽屉留给筛选/设置类浮层）。列表滚动位置在返回时保留。

**工作台/看板**：窄屏下看板列改为**单列纵向堆叠**（按列顺序排）为主方案；若列数 ≤3 且卡片轻，可用横向滑动列作备选。卡片收敛为一行标题 + 一行元信息（状态色点、负责人、截止日）。点开卡片 = 全屏详情页，"通过/驳回"操作按钮吸底常驻。

**对话页**：消息区全高滚动，输入栏吸底；员工/成员切换通过顶部会话标题下拉或返回列表完成。富内容（任务卡、技能结果）默认折叠为一行摘要（"📋 任务卡：xxx · 点击展开"），展开后内联渲染，绝不跳转外部聊天窗口。

**配对页**：手机扫码落地页极简：校验中（loading）→ 成功后直接进工作台；失败（令牌过期/已用）显示一行错误 + "请在桌面端重新生成二维码"。

**底部导航（P1）**：`<600px` 显示三 tab：工作台 / 会话 / 我的（我的 = 设备管理、设置只读视图）。列表一级页自动隐藏底部导航，返回后恢复。

## 5. 待确认问题

1. **手机端使用边界**：手机端是否允许"新建/派活"等写操作，还是本期严格只读 + 审批 + 对话？建议本期放开审批与对话两类写操作，其余只读——但需要用户确认审批写操作的范围（哪些卡票类型可手机审批）。
2. **多手机/多用户**：是否只支持"一人一 PC 多手机"，还是允许多个不同人配对各自手机？影响设备管理粒度与令牌权限设计。
3. **令牌安全等级**：长期令牌是否需要有效期（如 30 天需重新配对）？还是永久有效直到手动踢出？建议加有效期上限 + 手动踢出双保险。
4. **服务端局域网地址发现**：PC 可能有多个网卡 IP（虚拟网卡、多网络）。二维码内嵌 IP 的选取策略（枚举让用户选 / 自动优选 / 展示候选列表）需确认，这是扫码配对最常见的翻车点。
5. **目标系统优先级**：iOS Safari 与 Android Chrome 先保哪个？iOS 添加到主屏的 PWA 限制更多（无安装提示、SW 行为差异），建议明确主验证平台。
