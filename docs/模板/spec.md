> 快照型：复制上一版改名再写，开头保留三行 `版本` / `上一版` / `本版相对上一版的变化`。

## 版本

- 上一版：无（首版）
- 本版：v1
- 本版相对上一版的变化：新建。确立本轮自主迭代 + 设计漏洞审计的范围、边界、验收标准。

## 为什么做

- 班底（bandi）是多 agent 自托管协作平台，近一个月密集加了身份中枢、岗位权限、流程引擎、桌面壳自动进门、完全自主交付等模块；架构/模块边界/数据流/接口契约在这种高速叠加下最容易长出隐含耦合与契约漂移。
- 用户要的是"团队自己把活干完、最后给我结论"：先系统排查设计漏洞，再对可逆、有回滚的改进点自迭代，提交 PR + 验收汇报，合并/部署由他择时。

## 用户故事与验收场景

### S1 · 设计漏洞清单（架构师主责，可拉研发/测试）

- **故事**：作为团队，我要拿到一份覆盖「架构 / 模块边界 / 数据流 / 接口契约」的设计漏洞清单，以便后续排期自迭代。
- **场景 1.1**：Given 班底仓库当前代码（以工作区 HEAD 为基准：`apps/server`、`apps/web`、`apps/desktop`、`apps/mobile-native`、`plugins`），When 架构师按四维度审一遍并用证据（文件路径 + 函数名/行号）记录每条问题，Then 产出 `docs/design/2026-11-13-设计漏洞清单.md`，每条含：维度、严重度（高/中/低）、证据位置、复现/验证路径、建议归属岗位。
- **场景 1.2**：Given 清单初稿，When PM 随机抽任一条按证据位置翻代码，Then 能在仓库中翻到对应代码并复现该问题（翻不到 / 不复现 = 退回架构师重审）。

### S2 · 自迭代方案与排期（PM 牵头，团队讨论）

- **故事**：作为 PM，我要把漏洞清单转成可派活的自迭代方案，以便团队按岗位进场施工。
- **场景 2.1**：Given S1 清单，When 团队按「严重度 + 可逆性」排序并把每条拆成卡（每张卡绑定验收场景编号 + 归属岗位 + 交付物 + 验收标准 + 证据要求），Then 产出方案文档且**不含任何部署 / 合并 / 对外发布动作**。
- **场景 2.2**：Given 方案中的某张卡涉及不可逆 / 花钱 / 对外 / 改范围，When 团队识别到，Then 该卡以 `idea` 形态上报雇主，绝不直接施工。

### S3 · 施工与提交 PR（研发主责）

- **故事**：作为研发，我要按方案改代码并提交 PR，以便测试验收、雇主择时合并。
- **场景 3.1**：Given S2 方案中的 `todo` 卡，When 研发改动代码且每处改动对应 commit / 卡，Then 在仓库开 PR（标题含卡号，描述引用对应验收场景编号与证据）。
- **场景 3.2**：Given 已开 PR，When 检查 PR 内容，Then 其中不含部署脚本执行、不含合并、不含密钥/环境变量写入；仅源码与配置（有回滚）改动。

### S4 · 验收测试（测试主责）

- **故事**：作为测试，我要按 spec 验收场景与原漏洞复现路径回归，以便确认漏洞真的消除且无回归。
- **场景 4.1**：Given S1 每条漏洞的复现路径，When 测试在 PR 对应分支执行该路径，Then 原问题不再复现（或按方案降级），并记录证据（命令 + 输出 / 截图路径）。
- **场景 4.2**：Given 验收场景 S1–S3，When 测试逐条执行，Then 产出 `通过 / 不通过` 清单；不通过项退回对应研发卡（PATCH status=todo + startNow:true）并写清原因。

### S5 · 验收汇报进信箱（PM 主责）

- **故事**：作为 PM，我要汇总交付与验收证据产出汇报，以便雇主一眼判断结果并择时合并/部署。
- **场景 5.1**：Given S1–S4 全部产物（漏洞清单 + 方案 + PR + 测试结论），When PM 按「结论先行」格式写汇报，Then 汇报进入雇主信箱，含：结论（已修 / 部分修 / 受阻）、漏洞处理统计（已修/降级/未修 数量）、证据索引（清单/PR/测试结论文件路径）。
- **场景 5.2**：Given 汇报草稿，When 雇主查看信箱，Then 第一行即结论且可知要不要他动手（合并/部署由他择时，不在本流程内）。

## 这版不做什么

- 不做部署 / 合并 / 上线 / 重启服务——由雇主择时，本流程不含部署节点。
- 不在本步做具体代码修复——修复在 S3 节点，由研发按卡施工。
- 不改需求或范围；任何新增的不可逆 / 花钱 / 对外 / 改范围项一律 `idea` 上报。
- 不花銭、不对外发布、不删数据、不对生产做无备份覆盖。
- 不审计打包产物（`apps/desktop/runtime/**`、`dist/`、`target/` 视为旧版产物，不作依据）。

## 待澄清

- 审计基准分支：默认以当前工作区 HEAD 为基准；若雇主另有指定基准（如某 release tag）需告知，否则按 HEAD。
- 优先级口径：默认全量审计但按「严重度 + 可逆性」排，先啃高优；若雇主只关心某一子系统（如仅 `apps/server` 的权限模型）需点名，否则全量。
- 上述两项若 24h 内无补充，团队按默认口径推进（可逆、有回滚、不花钱、不对外、不改范围，PM 已获授权直接定）。
