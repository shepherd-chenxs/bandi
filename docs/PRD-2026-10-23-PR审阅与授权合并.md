# PRD：PR 审阅与授权合并（仓库管理员）

| 项 | 值 |
|---|---|
| 版本 | v1.0（2026-10-23 定稿） |
| 作者 | 司南（产品） + 智能设计助手（实现） |
| 状态 | 已拍板，进入实现 |
| 需求来源 | 用户 2026-10-22~23 口述（原文要点见文末「需求溯源」） |

## 一、背景与目标

**背景**：仓库值班（2026-10-17）解决了"别人提的 PR 我能**看见**"——巡检把 open PR 写成值班卡。但看到卡之后的一切还是人工：自己读 diff、自己判断是不是垃圾、自己去 GitHub 合并。用户的原话：「我看不懂的时候」是真实痛点，且「不想看 diff，想看 diff 我直接去 GitHub，不要重复造轮子」。

**要解决的问题**：别人提 PR → 我不知道它干了什么、有没有风险、是不是垃圾 → 判断成本全在我身上。

**目标（成功标准，可验收）**：

| 编号 | 指标 | 口径 |
|------|------|------|
| G-1 | 新 PR 从提交到卡上出现管理员结论 ≤ 一个巡检节拍（默认每天 2 次） | 以卡上「管理员审阅」段落出现时间为准 |
| G-2 | 授权后，满足条件的 PR 全程无需打开 GitHub 即完成合并 | 合并动作在班底流程实例内完成，留痕可查 |
| G-3 | 收回授权后，所有后续 PR 停在「待人确认」 | 以流程实例状态为准 |

## 二、名词与术语

- **仓库管理员**：一个数字员工（persona），被绑定为某个仓库的值班审阅人。
- **审阅**：管理员基于 PR 标题/描述/文件清单/patch 产出的四段结构化结论（见五）。
- **授权合并**：用户对某个仓库开启的开关；开启 = 该仓库审阅通过的 PR 由平台自动调合并 API。
- **等人确认**：流程引擎已有的检查点机制（节点 `manual` 语义），实例停在「待人确认」等人拍板。

## 三、需求范围

**包含**：
1. 仓库 ↔ 管理员绑定（`git_repos.keeperPersonaId` + 代码托管页下拉）
2. 服务端巡检增强：带令牌拉 PR（公私有均可，令牌绑定即私有可拉——用户 2026-10-23 实测确认）、`head.sha` 判新、拉 files 做审阅素材
3. 「PR 审阅与合并」内建流程模板：审阅节点（管理员）→ 合并节点（平台动作）
4. 审阅四段结论写回值班卡
5. 合并动作：判据（结论+CI+敏感文件+改动量）→ 调 `PUT /pulls/{n}/merge`
6. 授权开关 = 合并节点等人确认的勾选（随时收放，只影响新实例的自动性；已停实例等人点）

**不包含（本期不做）**：
- PR 详情侧栏 / 平台内读 diff（去 GitHub 看，不重复造轮子——用户明确拒绝）
- 在 GitHub PR 页面上自动发评论（方向不对：那是替用户公开表态）
- 邮件/浏览器推送通知（班底还没有通知基建，等真实需求）
- webhook 实时触发（本机服务无公网端点，不值得内网穿透）
- 驳回 PR / 关闭 PR 的平台内操作（本期只做合并）

## 四、方案选型

| 方案 | 思路 | 结论 |
|------|------|------|
| A. 自研三档开关（关/影子/自动） | 在 pr-watch 里写一套独立状态机 | **弃**。用户 2026-10-23 否决影子模式概念：授权是随时可收放的权利，不是试用期；且自研状态机会造出第二份真相 |
| B. 复用流程引擎（推荐，已选） | PR 审阅做成流程模板：审阅节点 → 合并动作节点；授权 = 合并节点前是否等人确认 | 复用引擎的「待人确认」「到站即派活」「实例留痕」，零新概念；审计天然有（实例即账本） |

## 五、审阅产出契约（输出四段，写入值班卡）

```
【管理员审阅】<时间>
结论：<✅ 值得合 / 🗑️ 垃圾 / ⚠️ 拿不准>
干了什么：<一句话> + ≤3 条要点
改了哪里：<按区域点名，不贴 diff>（碰没碰敏感文件单独说）
风险：<对照判据台账；没有风险要明说"没看出">
（垃圾附一句为什么）
```

- 结论由管理员**最后一行**给出，格式固定：`结论：值得合` / `结论：垃圾` / `结论：拿不准`。解析不到按「拿不准」处理——**不许装懂**。
- 管理员可以交白卷：材料不足时明说拿不准、指出该看哪里，比硬给结论有价值。

## 六、流程与状态

```
巡检发现新 PR（head.sha 变化）
  → 有管理员绑定 → 起「PR 审阅与合并」实例
      节点① 审阅（管理员，manual=false，干完自动流转）
      节点② 合并（平台动作，无经办人）
  → 无管理员绑定 → 照旧只写「待审」卡（现状行为）
```

合并节点判定表（平台执行，顺序固定）：

| 管理员结论 | 四条闸 | 已授权 | 结果 |
|-----------|--------|--------|------|
| 🗑️ 垃圾 | — | — | 终止实例，卡上标结论（**垃圾不进「待人确认」列**） |
| ⚠️ 拿不准 | — | 任意 | 停「待人确认」，永远等人 |
| ✅ 值得合 | 闸未全过 | 任意 | 停「待人确认」，写明哪条闸没过 |
| ✅ 值得合 | 全过 | 否 | 停「待人确认」，写"点通过即合并" |
| ✅ 值得合 | 全过 | 是 | **自动合并** → 实例完成 → 卡收状态 |

**四条闸**（自动合并的边界，缺一不可）：
1. 管理员结论 = 值得合
2. GitHub 闸门 CI 全绿（check-runs 无失败；**没有 CI 状态不算过**）
3. 未碰敏感文件（`.github/`、鉴权/令牌/密钥/凭据类路径）
4. 改动量 ≤ 阈值（additions+deletions ≤ 400 行，估算值，可调）

**人工拍板语义**：停在「待人确认」的合并节点，人点「通过」= 授权合并 → 平台执行合并（失败标「失败」可重试）；点「驳回」= 不合并，实例收尾。

## 七、关键规则

- **授权随时收放**：勾选改动只影响之后的判定；已经停在「待人确认」的实例仍等人点，不批量放行/拦截（状态不回跳）。
- **状态不回跳**：巡检绝不覆盖人拖过的卡状态、管理员结论写进卡后不被下次巡检的模板文本冲掉。
- **令牌隔离**：合并 API 由服务端持令牌执行；管理员（agent）只有建议权，不碰令牌（沿用 `agentEnv()` 清 GIT_* 的隔离哲学）。
- **PAT 权限**：自动合并需要 `contents: write`（读不需要）。用户需在 GitHub 后台换令牌——这是**阻塞级依赖**，未换则合并节点停在待人确认并写明原因。
- **降级**：审阅模型超时/失败 → 卡上写明失败原因与原始事实（标题/作者/规模），不发假结论；下个巡检节拍不自动重试同一 sha（避免反复烧模型），人可手动重跑巡检。

## 八、数据设计

| 落点 | 字段 | 说明 |
|------|------|------|
| `git_repos` | `keeperPersonaId TEXT` | 值班管理员 |
| `git_repos` | `autoMerge INTEGER DEFAULT 0` | 授权开关 |
| `workflow_runs` | `prRepo TEXT` / `prNumber INTEGER` | 实例 ↔ PR 关联（审阅结论写回卡、合并都要用） |
| `meta` | `prseen:{repo}#{n}` | 上次见过的 head.sha（判新用） |
| 值班卡描述 | 「管理员审阅」段落 | 结论落点；巡检保留带此标记的描述 |

## 九、依赖评估

| 依赖 | 分级 | 说明 |
|------|------|------|
| PAT 升级 contents:write | **阻塞**（仅对自动合并） | 未升级：审阅与人工确认合并不可用合并 API，合并节点会停在等人并写明 403 原因 |
| 模型可用（管理员 runtime） | 阻塞（对审阅） | 管理员没配 runtime / 额度超限 → 审阅节点「已阻塞」，引擎既有语义 |
| GitHub check-runs API | 并行 | 公开仓库无令牌也可读；失败降级为"没有 CI 状态" |

## 十、风险登记

| 编号 | 风险 | 概率×影响 | 应对 |
|------|------|-----------|------|
| RK-1 | 管理员误判垃圾 PR 被自动合（幻觉/误读） | 2×5=10 中 | 四条闸 + 结论必须含证据段；⚠️/🗑️ 永不自动合；授权默认关 |
| RK-2 | 审阅烧模型费用失控 | 3×2=6 低 | 只对新 head.sha 审阅；失败不自动重试；巡检与审阅频率解耦 |
| RK-3 | 合并动作与引擎解耦不干净，出现第二份推进逻辑 | 2×4=8 中 | 动作节点做成引擎原生概念（registry），推进仍走 decide/goto 单行道 |
| RK-4 | 卡描述被巡检模板冲掉结论 | 3×3=9 中 | 描述带「管理员审阅」标记时巡检不覆盖（第六节规则） |

## 十一、验收标准（节选，完整见冒烟脚本断言）

- FR-1 新 PR → 实例创建 → 审阅派给绑定管理员（Given 绑定了管理员且新 sha，When 巡检，Then startWorkflow 且经办人=管理员）
- FR-2 未绑定 → 行为与现状完全一致（回归保护）
- FR-3 同一 sha 只审一次；推新提交重新审
- FR-4 🗑️ → 实例终止且卡不进「待人确认」
- FR-5 ⚠️ → 无论授权与否停在「待人确认」
- FR-6 ✅+闸未过/未授权 → 停「待人确认」，note 写明原因
- FR-7 ✅+全过+已授权 → 调合并 API，卡收「已合并」，实例完成
- FR-8 停在确认的节点点「通过」→ 执行合并；合并失败 → 任务「失败」可重试
- FR-9 收回授权只影响新实例
- FR-10 卡上已有「管理员审阅」段落时，巡检不覆盖描述

## 十二、需求溯源（用户原话要点）

- 「别人提交了一个 pr，然后仓库管理员帮我去检查，告诉我这个 pr 干了什么东西，有没有风险。是不是垃圾。我来做决策。」
- 「我不想看什么 diff，想看 diff 我直接去 github 不就可以了吗，不要重复造轮子」
- 「我可以给它这个合并的权利，他就能合并，他把权利收回来，他就不能调合并的 api，就要等我来审核……复用现在的流程编排模式……有一个等人确认」
- 「令牌绑定了，私有仓库也可以拉到，共有仓库不管是否绑定都能拉到。之前是做过测试的」
- 「什么时候拉 pr？一天一次吗」→ 默认每天 2 次（09:00/21:00），巡检便宜审阅才花钱，二者频率解耦
