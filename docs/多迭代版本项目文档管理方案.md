多迭代版本项目文档管理方案

核心思路：多迭代版本项目文档管理（重点解决：版本多、文档容易混乱、不知道哪个文档对应哪个版本、改一次到处改）

一句话原则：**稳定的基线文档 + 迭代增量文档分开；文档本身也要带版本，和产品版本绑定；区分【全局不变】和【每个版本会变】的内容**

很多人踩坑：每个迭代都复制一份全套SRS、设计文档，最后一堆重复文档，改漏、改错。

> 不推荐：V1文档、V2文档、V3文档，整套复制一份。 推荐：**一份主基线文档 + 每个迭代单独的变更记录/增量说明**

## 一、先做分类：两类文档分开管

### 1. 基线文档（全局、长期共用，不随小迭代频繁复制）

代表系统当前最新的整体状态，**只有需求/架构发生变更时才更新**，所有迭代都基于这份基线。

- 系统总体架构、概要设计HLD
- 数据库主设计（核心表结构、ER图）
- 基础权限模型、全局字典
- 通用接口总文档（Apifox/YApi主库）
- 用户手册【基线版】：系统基础功能

> 规则：基线文档永远维护**最新生效版本**；历史基线不直接在原文覆盖，重大架构升级时，才归档一份旧基线快照。

### 2. 迭代增量文档（每个版本单独一套，跟着迭代走）

每个迭代（V1.1、V1.2、V2.0）独立存放，记录**本次迭代新增、修改、删除的内容**，不重复抄基线里已有的内容。 每个迭代文件夹里一般放这些：

1. 迭代需求清单（本次迭代需求、优先级、验收标准）
2. 需求变更CR单（本次涉及的变更）
3. 本次迭代专项技术方案（新功能、改造、重构）
4. 新增/改动的接口说明（可以直接在Apifox里打版本标签）
5. 本次迭代测试方案、测试用例、测试报告
6. Release Note（版本发布说明，非常关键！给内部、运维、甲方看）
7. 上线发布方案、回滚方案、上线checklist

> Release Note 就是多版本项目最重要的文档： 写明：版本号、上线时间、新增功能、修改功能、废弃功能、已知缺陷、依赖、数据库脚本、配置变更、影响范围。

## 二、推荐目录结构（适配持续迭代项目，可直接落地）

```
00-项目总基线（全局基线，持续更新）
├─ 00.1 项目章程、干系人、整体里程碑
├─ 00.2 总体设计（产品设计说明书、架构设计说明书）
├─ 00.3 数据库基线设计文档
├─ 00.4 全局接口文档（主库）
├─ 00.5 通用运维手册、管理员手册（基线）
└─ 00.6 风险、问题总台账（跨迭代）

01-迭代版本包（按版本号建文件夹，V1.0、V1.1、V1.2、V2.0…）
├─ V1.0（首个正式基线版本）
│  ├─ 迭代需求清单
│  ├─ 专项设计方案
│  ├─ 测试报告
│  ├─ ReleaseNote.md
│  └─ 上线方案
├─ V1.1（小迭代，新增功能）
├─ V1.2（Bug修复迭代/补丁版本）
└─ V2.0（大版本，架构/大范围改造）

02-变更管理（统一存放所有CR需求变更单）
├─ CR-001 【V1.1】xxx需求变更
└─ CR-002 【V1.2】xxx字段修改

03-过程文档（跨迭代：周报、会议纪要、评审记录）
04-交付物&培训材料
05-归档区（不再维护的旧基线快照、下线版本）
```

> 小技巧：补丁版本（hotfix）单独标记，比如 V1.1.1，文件夹单独放，重点写清楚只修复了什么、影响范围极小。

## 三、版本绑定规则（解决“文档对应哪个代码版本”）

1. 所有文档、接口、数据库脚本、测试报告，都打上产品版本标签

   - 接口工具（Apifox/YApi）：支持接口集合打版本，每次发布导出对应版本接口文档；
   - 数据库脚本：脚本文件名带上版本号 `V1.2_20261124_add_table.sql`，并且记录回滚SQL；

2. 基线文档更新时，在文档头部加【变更历史表】

   放在基线文档最顶部，示例：

   | 版本 | 修改日期   | 修改人 | 修改内容         | 对应产品迭代版本 |
   | :--- | :--------- | :----- | :--------------- | :--------------- |
   | V1.0 | 2026-10-01 | 张三   | 初始版本         | V1.0             |
   | V1.1 | 2026-10-15 | 李四   | 新增订单状态字段 | V1.1             |

3. 基线文档只存

   最新版

   ；想看旧状态，两种方式：

   - 方式A：文档工具自带历史记录（飞书/语雀/Confluence），可以回溯到某个时间点；
   - 方式B：**重大版本（如V2.0）发布时，对基线文档做一次快照归档**，放到归档目录，作为永久快照，不再修改。

> ✅ 小迭代（新增页面、小功能）：**不复制基线，只在迭代包写增量+更新基线变更历史** ✅ 大版本重构、架构改动：归档上一版基线快照，再更新新基线

## 四、变更联动机制（最容易乱的地方）

只要迭代里改了需求/库表/接口：

1. 先出CR变更单，评审；
2. 开发完成后，**同步更新【全局基线文档】**（不是只写在本次迭代文档里）；
3. 在Release Note里写明这次改动；
4. 接口、数据库脚本打上版本标识；

举个例子：V1.2迭代修改了订单表一个字段

- 在V1.2迭代文件夹记录这件事；
- 同时去【00-项目总基线-数据库设计文档】更新表字段；
- 在基线文档的变更历史里增加一条，关联V1.2； 这样：基线永远是最新真相，迭代包记录当时发生了什么。

## 五、不同工具配套方案（持续迭代场景）

1. Markdown + Git（推荐技术团队）
   - 基线文档和代码放在同一个git仓库；
   - 用Git Tag标记产品版本，tag和迭代版本一一对应；
   - 想查V1.1的文档状态，直接切到tag看，天然自带历史快照。
2. 语雀 / Confluence / 飞书知识库（产品、甲方项目）
   - 空间分：基线空间 + 迭代版本目录；
   - 开启文档历史；大版本手动复制一份快照归档；
3. 接口：Apifox / YApi
   - 每个迭代新建版本分支，发布后导出该版本接口文档，放到对应迭代文件夹；
4. 需求缺陷：Jira/禅道
   - 所有需求、bug绑定版本号，和Release Note互相引用。

## 六、几个重要约定，避免越迭代越乱

1. **禁止：基线文档不更新，只靠迭代文档堆信息** → 几个迭代之后基线和线上不一致，所有人看不懂；
2. 区分：大版本迭代 vs 补丁hotfix迭代
   - 功能迭代：完整走评审、测试报告、ReleaseNote；
   - Hotfix紧急补丁：文档轻量化，只写修复点、影响范围、回滚脚本，不用全套材料；
3. **Release Note 标准化，统一模板** 版本号、上线时间、依赖版本、新增、变更、删除、数据库变更、配置项变更、已知问题、联系人；
4. **文档Owner责任制**：基线文档固定owner，每次变更由owner合并更新；迭代文档由本次迭代负责人维护；
5. 定期（每个迭代收尾）做一次**文档巡检**：核对基线是否和线上一致，过期文档清理。

## 七、敏捷迭代精简版（互联网小团队，不想写很多文档）

不用复杂全套，保留最小集合：

- 一份基线：数据库设计 + 架构图 + 接口主库
- 每个迭代只维护：迭代需求列表 + Release Note + 数据库变更脚本 + 测试报告
- 用Git Tag做快照，不需要每个迭代复制整套设计文档
