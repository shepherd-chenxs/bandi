# 交接：把「岗位本命」从技能库搬出来（2026-11-22）

> 施工单。执行者是 Trae，验收者是主理人 + 监工（另一个会话）。
> **先读完「铁律」再动手**；每一步都有验收命令，红了就停，别往下推进。

## 一、为什么要做

`skills/bandi-expert-*` 这 15 份东西不是技能，是**岗位作业手册**：讲这个岗位怎么拆活、怎么对口径、怎么放行。
它们被当成「技能」挂进技能库，带来三个反效果：

1. 技能页把它们当用户资产列出来（带「内置·只读」标签），用户既看不懂、也不会去读；
2. 语义上不可组合：岗位包是「被雇来干这个就该这么干」，不是「用户想加就加的方法论」；
3. 加载绕远：首轮只注入「名字 + 48 字描述 + 路径」，模型得再花一次 Read，PM 那份 216 行未必读全。

本轮只做一件事：**把岗位包从技能系统里摘出来，变成「随岗位走、用户不可见」的 playbook**，行为保持不变。

## 二、铁律（违反任意一条，本轮作废）

1. **不许改行为**。这一轮是等价重构：该注入的方法论一个字不能少，只是换位置、换注入方式。
2. **不许手改** `apps/desktop/runtime/**` 和 `apps/desktop/target/**` —— 那是打包产物，下次 `stage-runtime.mjs` 会覆盖。
3. **不许删** `skills/bandi-report`、`skills/bandi-repo`、`skills/bandi-git` —— 这三份是跨岗位通用的方法论，留在技能库。
4. **不许改** `docs/契约.md`。
5. **不许顺手做**「PM 的 pmDispatchBlock 与 playbook 去重」「把判据搬进代码」—— 那是下一轮，写进「不在本轮范围」即可。
6. 一个阶段做完、验收通过，再进下一个阶段。红了就停，把报错原文带回来。

## 四、阶段 A：搬家 + 拆分岗位定义（行为等价）

### A1. 搬文件

按上表逐条 `git mv skills/<旧>/SKILL.md apps/server/src/roles/packs/<新>.md`，再删空目录。
`skills/bandi-expert-operator/` 保持原样。

### A2. `apps/server/src/roles.mjs`：每个岗位拆成 `playbook` + `skills`

现在 `skills` 数组里混了两类东西（岗位包 + 通用方法论），拆开：

```js
{ key: 'dev', name: '研发工程师', kind: 'expert', permissions: [],
  playbook: 'dev',                       // 岗位本命，文件 roles/packs/dev.md，用户不可见
  skills: ['bandi-repo', 'test-driven-development', 'systematic-debugging', 'verification-before-completion'] },
```

15 个岗位逐一处理，规则：**数组里凡是 `bandi-expert-*` / `bandi-secretary` 的，移到 `playbook`；其余留在 `skills`**。
按此规则，`ui` 和 `steward` 的 `skills` 会变成空数组 —— 这是对的，不要为了凑数留东西。

同时新增（都在 `roles.mjs` 里，注意这个模块原本是叶子、不 import 任何东西，**读文件不要写在这里**，见 A3）：

```js
/** 岗位本命手册的 key（没有 playbook 的岗位返回 null） */
export const rolePlaybook = (key) => roleOf(key)?.playbook ?? null;
```

### A3. 新增 `apps/server/src/roles/pack.mjs`

职责：读 `roles/packs/<key>.md`、缓存、生成注入块。**不要**在 `roles.mjs` 里加 fs 依赖。

```js
// 约定：
//  · 文件不存在 → 返回空串（宁可少一段，不能让派活挂掉）
//  · 进程内缓存（按 key），文件 mtime 变了才重读（开发时改了立刻生效）
//  · 只读一次全文返回，不做截断 —— 本轮要求行为等价（现在模型可以 Read 全文）
export function rolePackBody(roleKey)      // 正文（去掉 frontmatter），找不到返回 ''
export function rolePackMeta(roleKey)      // { name, description } 供界面用，找不到返回 null
export function rolePackBlock(roleKey)     // 注入用文本，找不到返回 ''
```

`rolePackBlock` 的文本形状（照抄，别再发挥）：

```
【你的岗位手册 · 平台内置，随岗位固定；下面是这个岗位的做事方法，按它做】
（这里是正文）
```

### A4. 注入位置（两处，别漏）

1. `apps/server/src/dispatch/contract.mjs` 的 `buildDirectTask()`：
   现在是 `宪法 → 身份 → 技能 → 插件 → brief`，改成 **`宪法 → 岗位手册 → 身份 → 技能 → 插件 → brief`**。
   排在身份之前的原因和宪法一样：身份块那句「后续对话请一直保持」权重最高，岗位方法必须压在它前面。
2. `apps/server/src/dispatch.mjs` 的 `buildGroupTask()`（firstTime 分支）：
   同样插在 `constitutionBlock` 之后、`你的职责与身份设定如下` 之前。

两个函数的 `roleKey` 参数已经存在，直接用。

### A5. `apps/server/src/experts.mjs`：改自检 + 目录返回

1. 加载期自检（文件末尾那个 IIFE）现在检查 `roleOf(x.roleKey)?.skills?.length`，
   改成检查 **playbook 文件真实存在**（用 `rolePackBody(...)` 非空判定）。错误文案改成
   「这些专家包对应的岗位没有岗位手册（见 roles/packs/）」。
2. `hireExpert()` 里挂技能的循环、`syncExpertSkills()` 的 `pkg`：继续用 `roleSkills`，
   现在它天然只含通用技能，无需改逻辑。
3. `listExperts()` 每个专家多返回一项 `playbook: { name, description } | null`（来自 `rolePackMeta`），
   给前端详情卡用；`skills` 字段保持现有形状（只列通用技能）。

### A6. `apps/server/src/steward.mjs`

`ensureSteward` / 同步里用 `roleSkills(STEWARD_IDENTITY.roleKey)` 挂技能。
搬家后 `steward` 的 `skills` 为空，这里会变成「什么都不挂」——**这是预期**，
但必须确认：系统管家启动时不再报「缺 skill」，且首轮注入里有岗位手册（A4 已覆盖）。
如果该文件里有「技能包为空就报错」的判断，改成允许为空（playbook 才是他的本命）。
