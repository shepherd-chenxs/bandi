# 形态决策：托管控制面 + 客户端出站节点

| | |
| --- | --- |
| 定于 | 2026-10-15 |
| 来源 | 用户讨论（原问题：「做成 web 版本还是桌面版本」） |
| 状态 | **已定**（用户 2026-10-15 确认）。落地情况见「十一、实施记录」；细节见「十、未定项」 |
| 取代 | `README.md` 技术选型一节末句「桌面端后置」；`v1.0.0` 的 B6 与「不做多机」两条边界 |

> 同类产品的形状取自[第三方架构解读](https://gitcode.csdn.net/6a26bf6d662f9a54cb7b5abc.html)（非官方文档），细节待核。

## 一、结论

**不是 web 还是桌面 —— 是控制面放哪、执行面怎么连上来。**

定了三件：

1. **控制面托管**，班底自己运营一个服务；用户**只装客户端**。
2. **客户端出站连接**：每台机器上常驻一个节点，主动连出去（注册 ＋ 心跳 ＋ 领活）。不开端口、不要公网 IP、不配 SSH。
3. **单机零外部依赖**：同一份代码，单机时控制面就地在本地跑 —— 用户看不见「节点」这个概念。

于是原来那三个问题一起消失：

| 原来的担心 | 现在 |
| --- | --- |
| web 还是桌面 | 桌面客户端是**形态**；web 只是控制面/客户端的一个**界面** |
| 关掉浏览器会不会挂 | 干活的是客户端里的**节点进程**，浏览器只是一块屏幕 |
| 怎么控制多台电脑 | 出站连接。这也正是同类产品敢做云端所依赖的同一个办法 |

顺带修正一个误判：**「关掉浏览器会挂」在现状下就已经不成立** —— `start.mjs` 起服务用的是 `detached: true` ＋ `unref()`，server 不是终端或浏览器的儿子；SSE 订阅时会先回放已发生的事件，所以刷新、重开浏览器都能从当前进度接上。真正会挂的是「重启电脑 / 杀掉 node / `restart.cmd`」，那是**服务化**问题（阶段 0），与形态无关。

## 二、三层，职责边界写死

```text
控制面（托管）              编排 / 身份 / 状态 / 审计 / 任务队列
      ↕  长连接（WS）—— 节点主动连出
节点（用户机器，常驻）        注册 · 心跳 · 领活 · 拉起并管住 agent CLI
      ↕  子进程
Runtime（codex / claude / dsh）   真正干活
```

### 权威边界（本决策里最要紧的一条）

| 数据 | 在哪 | 为什么 |
| --- | --- | --- |
| workspace / 成员 / agent 配置 | 托管 | 多人要看见同一份 |
| 任务队列 / 流程实例 / 进度真相 | 托管 | 同上 |
| 审计与运行事件流 | 托管 | 跨机器、跨重启都要能回放 |
| 代码与仓库 | **只在本机** | 出站连接的本质收益 |
| 私钥、CLI 凭据、`.env` | **只在本机** | 沿用既有硬约束：班底不碰凭据 |
| 文件路径是否存在、进程本身 | **只在本机** | 那是**这台机器上的事实** |

对外能讲的一句话：**代码和密钥一个字节都不离开你的机器，云端只知道谁该干什么。**

这条边界不是新发明 —— `runtimes.json` 本来就是**按 deviceId 分域**存的（`saved.devices[deviceId].runtimes`），`resolveForRun()` 天然就是「这次派给哪台设备」的决策点。顺着现有数据模型划即可。

## 三、单机 → 团队：认领，不做同步

**第一次登录 = 认领。** 把本地那个 workspace 导上去，之后**本机那份降为副本**，权威在托管。一次性、单向、不回头。

**为什么不做双向同步**：「单机用着用着拉同事进来」如果两边都是权威，就要解决冲突，而冲突解决是这类产品里最贵、最容易做错的部分。认领把这个问题整个删掉。代价是接受一个约束：**权威只有一份，在托管。**

## 四、参考同类产品的哪些做法、不参考哪些

**采用**：出站连接（关键）、三层分职、Agent 作为持久配置实体、`runtime_id` 绑定、离线排队、Profile 式的环境隔离。

**不采用**：

1. **不用 30s 轮询。** 同类产品的思路是 issue 驱动（派活、等结果），30s 延迟无所谓；班底的卖点是「**看它干，随时接管**」（`README.md` 第一行），靠的就是实时事件流。控制面 ↔ 节点用**长连接**，轮询只做弱网兜底。这是班底能做得更好的地方，跟着抄一遍等于把最值钱的部分做没。
2. **`kind: 'local' | 'ssh'` 这个建模是错的。** SSH 不是设备类型，是**到节点的一种传输方式**（同机直连 / 局域网直连 / SSH 隧道兜底）。不改，接完节点之后 `runtimes.mjs` 那两层会被撑成一个奇怪的形状。
3. **注意它的 `workspaces_root` 解决了什么。** `projects.root` 是**本地路径** —— 多机之后同一个项目在 A 机器上是 `E:\...`、在 B 机器上可能根本不存在。项目需要多一维「这是哪台机器上的路径」。这个坑比接通道更容易漏。

## 五、对现有代码的影响

### 可直接复用

| 已有 | 在新形状里的位置 |
| --- | --- |
| `runtimes.json` 按 deviceId 分域 | 节点 → 该节点上的 agent CLI |
| `resolveForRun()` | 挑设备的决策点 |
| `detectAll()` / `probe()` / `launchable()` | 节点上「装了哪些 CLI、能不能起来」的自动识别 |
| `personas` 表 | 同类产品的 Agent。缺 `custom_env` / `custom_args` / `max_concurrent_tasks` / `pre_launch_commands` / `mcp_config` / `visibility` |
| `workflow_*` 三张表 | **比同类产品的 Squad 强**：真流程引擎（节点 ＋ 连线 ＋ 驳回访问），不是只有队长评估 |
| `projects` ＋ `project_tasks` ＋ 两块看板 | Issue / Project 那一层 |
| SSE 事件流 | 实时性优势，别丢 |

### 要改 / 要加

1. **拆角色**：现在 server 同时是控制面和节点（本地 spawn 子进程）。拆成两个角色，但**默认同进程** —— 单机用户不该看见「节点」。
2. **节点通道**（唯一值得新写的组件）：出站注册 ＋ 心跳 ＋ 长连接 ＋ 离线排队。
3. **控制面地址可配**：现在 `allowedOrigins()` 写死 `127.0.0.1` / `localhost`，且 `server.listen(port)` 没绑地址 —— 结果是局域网另一台机器打开页面**能看、不能动**（写在库里的状态一律 403）。这条不修，「笔记本连台式机」连门都没开。
4. **事件流落库**：现在只在进程内存里（最多留 50 条运行），跨机器、跨重启都不可回放；重启后那次运行的中间过程永久丢失，只有 final 文本进了消息表。
5. **离线排队**：现在派活是直接起进程，没有「等某台机器上线」这个状态 —— 而团队模式的核心恰恰是这个。

## 六、阶段

- **阶段 0（不动架构）**：开机自启 ＋ 事件流落库 ＋ 中断后续跑。把「会不会挂」彻底消掉。
- **阶段 1（拆角色，行为不变）**：control-plane 与 node 两个角色，单机装配零变化，加 `--control-plane <url>` 开关。纯重构。
- **阶段 2（通道）**：节点出站注册 ＋ 心跳 ＋ 领活；`deviceId` 落地；离线排队。
- **阶段 3（团队）**：托管鉴权、多租户隔离、可见性与审计；客户端分发。

**阶段 2 的第一步不是写通道，是先做一个最小切片**：把 `deviceId` 从硬编码 `'local'` 改成节点身份，让一个节点**出站注册 ＋ 心跳**到现有 server，控制面把它列成一台设备。不做派发、不做排队。

成了，就同时验证了三件事：节点能不能出现、掉线能不能被发现、每台机器上的 CLI 能不能自动识别。形状成立之后，排队与派发才有意义。

### 建议的执行顺序（2026-10-15）

上面的阶段是**分层**，不是**先后**。按「每一块钱买到多少信息」排，建议这样走：

1. **砍掉 `apps/desktop/ui`，壳指向 `apps/web`。** 一行配置 ＋ 一次删除，先把唯一会变成「改双份」的陷阱拆掉（见 §九）。
2. **事件流落库**（`run_events` 表 ＋ 单调 seq ＋ SSE 支持 `Last-Event-ID`）。这不是打磨，是**阶段 2 的地基** —— 节点在远端时，控制面必须有一份可回放的落库事件流，否则「看它干」跨机器就断。
3. **阶段 2 的最小切片**：节点出站注册 ＋ 心跳 ＋ 报到成一台设备。这一步验证的是**整个形态押注是否成立**，越早越好。
4. 然后才是**中断续跑**与**开机自启** —— 单机便利，价值真实，但与形态无关，放后面不亏。

### 阶段 1 先别做

**不要一上来做阶段 1（拆控制面 / 节点角色）。** 两条理由：

- 它是**纯重构、零用户可见价值**；
- 节点通道还没写，此时拆出来的角色边界是**凭想象划的**，等通道真写完，十有八九要重划。

替代做法：**把节点写成一个独立入口**（新文件 ＋ `POST /api/nodes/register`、`POST /api/nodes/:id/heartbeat` ＋ 一张 `nodes` 表），对现有 server **只增不改**。等独立节点跑通了，单机的「零配置装配」再由桌面壳把 server 与节点一起拉起来 —— 那时**角色拆分是打包的自然结果，不是一次投机重构**。

同理，**桌面壳（Tauri 打包、安装器）也放到形状验证之后**，别先做安装包。

## 八、不做什么

- **不做浏览器当执行器** —— 那才是真的关掉就挂，而且是最坏的一种挂。
- **不做 SSH 优先的远程执行** —— `v1.0.0` 那条实现不回来。SSH 降为节点的**一种传输方式**，跨网段兜底用。
- **不做控制面 ↔ 节点的双向数据同步** —— 只做单向认领。
- **不做 P2P / NAT 打洞** —— 已经选了托管，这条最难的省掉了。
- **不做 30s 轮询为主** —— 只做弱网兜底。
- **不做「单机要登录才能用」** —— 单机必须零外部依赖、不需要 token。

## 九、哪里会重复、哪里不会

用户 2026-10-15 的顾虑：「我担心改双份。」核过代码，分四类。

### 今天没有重复（已核）

| 东西 | 体量 | 结论 |
| --- | --- | --- |
| `apps/web` | `app.js` 345 KB、`index.html` 13.7 KB、`style.css` 99.5 KB | 平台界面，只有这一份 |
| `apps/desktop/ui` | `main.js` 14.6 KB、`index.html` 5.2 KB、`style.css` 6.4 KB | `v1.0.0` 那个独立小应用（SSH 服务器登记），**不是**平台界面的副本 |

两者**功能不重叠、共用 0 行代码**。`apps/desktop` 那套 Rust（`keys.rs` 8.9 KB / `ssh.rs` 9.8 KB / `store.rs` 15.6 KB / `lib.rs` 13 KB）做的是密钥生成、服务器登记、连通性测试 —— 与平台功能没有交集。

**所以现在不存在「改双份」的问题。**

### 一条必须提前掐死的重复

**桌面壳不许自己再长一套前端。** `tauri.conf.json` 现在写的是 `"frontendDist": "ui"` —— 如果新客户端继续在这套 `ui/` 上长出平台界面，就会变成两个前端维护同一个产品。这是唯一一处「照现状往下做**一定**会重复」的地方。

处置：壳的 webview 指向本地 server 的 `apps/web`（`frontendDist` 指过去，或直接加载 `http://127.0.0.1:<port>`），把 `apps/desktop/ui/` 删掉。**一行配置 ＋ 一次删除**，在动客户端之前做掉。

顺带：`apps/desktop` 那套 Rust 不再是死资产 —— SSH 降为节点的一种传输方式，`ssh.rs` / `keys.rs` 值得开工前 review 一次（但别指望全留）。

### 两条现在就要定的边界（否则以后会变成重复）

1. **控制面只有一份代码。** 单机 = 同一个服务、不启用鉴权与网络，**不许**为单机写一个「简化版控制面」。一旦写了简化版，以后每个功能都要改两遍。
2. **数据层不换。** 云端多租户继续用 `node:sqlite`，隔离粒度取「一个租户/一个 workspace 一个库文件」，别为了多租户换 Postgres —— 那会让 `store.mjs` 的 SQL 裂成两份。

### 回答「打磨还是开工」

**两者不是二选一。** 有一批活不论形态怎么走都不作废，而且正好是形态决策的前置条件（阶段 0）：

1. 事件流落库（现在只在内存，重启丢中间过程）
2. 中断后续跑（`sessionId` 已经落库，只差一个入口）
3. 开机自启
4. 砍掉 `apps/desktop/ui`、壳指向 `apps/web`（消掉上面那处唯一的重复隐患）

**反过来，先大规模打磨现有功能是亏的** —— 形态一落地，设备/运行时这两层的层次会挪，现在打磨的部分可能要返工；而上面这四件不在会挪的位置上。

顺序：**先做这四件，再进阶段 1（拆控制面 / 节点角色）。**

## 十一、实施记录（2026-10-15）

按 §六 的建议顺序做的：**①②③ 已落地，④ 未动**。

### ① 消掉重复：删掉第二套前端

- 删 `apps/desktop/ui/`（`index.html` / `main.js` / `style.css`）。
- `tauri.conf.json` 的 `frontendDist` 从 `"ui"` 改成 `"http://127.0.0.1:8787/"` —— **薄壳**：
  不打包任何前端资源，窗口直接指向本地控制面。这是翻 `tauri-utils 2.10.1` 源码确认的用法
  （`FrontendDist::Url`：*No assets are embedded in the app in this case*），不是猜的。
- 顺手订正了配置里已经过时的描述（那还写着 `v1.0.0` 的「服务器登记」）。

### ② 事件流落库 ＋ 断线只补缺口

- 新表 `run_events(runId, seq, evt, at)`，append-only；`seq` 按**每次运行**从 1 起。
- SSE 带 `id:`，服务端读 `Last-Event-ID` **只补缺口**。改前是全量重放 ——
  而 EventSource 每次重连都要重发一次请求，于是回话被**重复追加**一遍（真 bug，已修）。
- 事件从**库里**回放、不再从内存数组：服务重启之后那段照样接得上。
- 启动清账（`reapStaleRuns`）**给被中断的运行补一条终止事件** —— 不补的话，
  重连会拿到半段、然后**永远等不到 `__done`**，连接挂着、界面停在「还在跑」。
- 顺带修了一个实测出来的毛病：子进程**异步**起不来时（`spawn EINVAL`，例如路径给了 `.cmd`），
  错误只落成光秃秃的 `spawn EINVAL`；现在与同步那条路一致，说「起不来：…」。
  判据是「一条事件都没产出 ＋ 启动类错误码」。

**验证**：`node apps/server/src/smoke-run-events.mjs` —— 22 项。覆盖落库、`Last-Event-ID` 三种边界、
认不出来的运行仍然 404、跨重启回放、清账补终止事件、以及真派活那条链路。

### ③ 节点最小切片：报到 ＋ 心跳 ＋ 掉线可判

- 新表 `nodes`（心跳是十几秒一次的高频写，落库比落文件稳，也不会两台互盖）。
- `POST /api/nodes/register`、`POST /api/nodes/:id/heartbeat`、`GET /api/nodes`。
  心跳 15 秒一次，**45 秒（三个周期）收不到判离线** —— 容忍一次丢包，别网络一抖就满屏离线。
- 新入口 `apps/server/src/node.mjs`：**出站**报到 ＋ 心跳。身份**认文件不认主机名**
  （主机名会改、也会两台重名，认它就会在控制面上攒僵尸设备）。`--once` 供验收。
- `GET /api/devices` 合并节点设备；`GET /api/devices/:id` 给只读详情；
  在节点设备上改运行时一律 400 并说明原因。
- **远程运行时进不了 `runtimes.loadDevices()`** —— 于是 `resolveForRun` 挑不到，
  控制面不会拿着一个只有那台机器才有的路径、在本机去 spawn。这是安全边界，不是洁癖。
- 界面：设备列表多一枚「在线/离线」；节点详情页**只读**（一颗能按的按钮都不给 ——
  那一页的开关改的是控制面这台机器上的文件，摆在那儿语义就错了）。

**验证**：
- `node apps/server/src/smoke-node.mjs` —— 21 项：报到成设备、自报只读且不混进本机清单、
  重报不攒第二台、心跳过期判离线、边界拒绝（无 id / 陌生心跳 / 改节点运行时）。
- **无头 Edge 实测**（`tmp/ui-probe/`，三张图）：设备列表（在线）、设备列表（离线）、节点详情。

### ④ 节点领活：派活 ＋ 离线排队（2026-10-15 落地）

这是「多台电脑一起干活」真正成立的那一步，也是整个形态押注的兑付。

**协议（控制面不 push、不开端口、不引 WebSocket）：**

| 方向 | 接口 | 说明 |
| --- | --- | --- |
| 节点 → 控制面 | `POST /api/nodes/:id/claim` | **长轮询**挂 20 秒，有活立刻回。不是 push —— push 要求能连到节点，而"连不到"才是多机要解决的问题 |
| 节点 → 控制面 | `POST /api/runs/:id/events` | 事件**批量**回传（攒 20 条或 200ms）。响应里带回 `{stop}` —— 这是**反向的控制通道**，不用另开连接 |
| 节点 → 控制面 | `POST /api/runs/:id/finish` | 回执。走的是**与本机同一个 `finish()`**：消息落库、会话状态、流程推进、终止事件全一样 |
| 控制面 → 节点 | `POST /api/nodes/:id/claim` 的返回 | 活的内容：`family`/`model`/`sandbox`/`cwd`/`task`/`sessionId`。**不带路径** —— 路径是那台机器上的事实 |
| 人 → 控制面 | `DELETE /api/nodes/:id` | 忘掉一台节点（换过身份文件就会多出一行，永远"离线"躺着） |

**几条关键取舍：**

1. **派活就是员工绑一个运行时的 id**（`node-xxx:codex`）。不再造一套"指派机器"的交互 ——
   员工本来就绑 runtime，多机只是 runtime 多了一种。所以节点自报的运行时从"只读"变成**可派**。
2. **`remote: true` 是边界**：`runs.startRun` 见到它就不在本机 spawn，而是进队列。
   这就是当初那个"远程运行时不许进 `loadDevices()`"守卫的正式替代 —— 守卫是权宜，分支才是机制。
3. **控制面也建一个内存 run 对象**：于是事件广播、SSE 的 `id:`、落库回放、收尾那套**全部复用本机那条路**，
   只是事件从 HTTP 来。少一套"远端专用"管线，就少一处只有多机才暴露的坑。
4. **离线排队不需要另写**：节点不在线时，活就躺在队列的"待领"里 —— **排队是这个队列的默认状态**。
5. **掉线清扫分两种**（判据是**节点离线**，不是"跑了多久"，长活只要还在心跳就不动它）：
   一次动静都没有 → **放回队列**（那边没开张，重派安全）；有动静之后才断 → 判**中断**
   （副作用可能发生了一半，悄悄重跑比说清楚危险）。

**这一步踩到的坑（都写进代码注释了）：**

- **长轮询的请求方可能已经死了**。节点被杀之后，它那条挂着的领活请求照样把活"领"走（86ms 之内），
  于是活落在空气里：节点没人跑、队列里也看不见、界面永远"跑中"。
  判据试了两个才对：**`req.destroyed` 不能用**（请求体读完恒为 true，会把正常领活全拒掉），
  **`'close'` 事件在这种情况下根本不触发**；真正管用的是 **`res.destroyed`**（以及它底下的 socket）。
- **空批次也要回 `stop`**：停止指令搭事件批次的响应回去，而"模型在想"时可能几分钟不吐一个字 ——
  所以节点每 2 秒发一个**空批次心跳**，既是停止通道也是"我还在干"的信号。只看批次里的事件，这个通道等于不存在。
- **"节点 → 设备"的映射只能有一份**。我一度在 `server.mjs` 里又写了一份 `nodeDevice()`，
  于是同一个节点在设备列表里**出现两次**、两份逻辑还会各自漂。收进 `runtimes.mjs` 一处。
- **名字里必须带机器名**：不然两台机器都叫「Codex CLI」，员工的下拉里分不出活会落到哪台。

**验收：**

- `node apps/server/src/smoke-node-jobs.mjs` —— 24 项。真起控制面 ＋ 真起节点 ＋ 一个**确定性假 CLI**
  （`fixtures/fake-agent.js`，按 codex 的事件词汇吐几行 JSON，不烧 token、结果不飘）。
  覆盖：可派 → 领走 → 在那台机器上跑完 → 事件与回话回到控制面 → 离线排队 → 没领走就撤 → 一声不吭也掐得掉。
- **跨机实测走通**：控制面在火山那台（公网），节点在我这台 Windows ——
  公网派一句话，活在本机跑完（`[节点] 在 E:\02CodeSpace\bandi 里干活`），回话与 `run_events` 回到公网。

### ⑤ 还没做

**中断续跑**（重启不再打断活）、**开机自启**（服务器一行 crontab）；
「单机零配置装配」还要等桌面壳把控制面与节点一起拉起来（现在桌面版只拉控制面，节点同机不必要）。
另外：**工作目录是那台机器上的事实** —— 两边路径不一样时明确失败，不做悄悄换目录；
"同一个项目在两台机器上路径不同该配什么"是下一步。

## 十二、技术选型复审（2026-10-15，桌面版动手前）

目标变了（本地工具 → 托管控制面 ＋ 多机客户端），所以把四层重过一遍。

**结论：两层不动（而且是资产），一层要加约束，两层必须现在定。选型不用大改 ——
换的是「数据落点」和「客户端装配」，不是语言、框架或数据库。**

### 不动，而且是资产

| 层 | 为什么不动 |
| --- | --- |
| 执行端适配层（codex / claude / dsh ＋ 统一事件词汇） | 跟形态完全无关 —— 不管控制面在哪，活都是 CLI 干的。这是整个项目最值钱的一块 |
| 服务端 `node:http` ＋ SSE（零依赖） | 「一个人能维护」在新目标下更值钱（你要自运营一个托管服务）。不需要框架 |

### 一层要加约束（不是换库，是收口）

存储继续用 `node:sqlite`，但有三件**现在不做、以后更贵**的事：

1. **数据落点必须可配，且默认到用户目录。** 现在 `dataDir = <仓库>/data`（`config.mjs`），
   而 **7 个模块**从它派生自己的路径（`runtimes.json`、`plugins.json`、`connectors.json`、`node.json`、
   `model-routes/`、`bandi.db`）。桌面版装到用户机上，这就是**往安装目录写** ——
   要么要管理员权限（撞 `v1.0.0` 的 B5「不要求管理员权限」），要么升级时被覆盖。
   → 加 `BANDI_DATA`，桌面版默认 `%APPDATA%\bandi`，服务器部署用环境变量指到别处。
   顺带这也是「一台机器跑两个实例」和测试隔离的前置。
   **2026-10-18 复评**：当时为了「不惊动既有数据」只把桌面版指到用户目录，命令行仍默认
   `<仓库>/data` —— 结果同一台机器两个库（命令行空库、桌面壳真实库），看错库是常事；
   而「开发版不碰真实数据」这条根本没成立（开发壳连的就是真实库）。现在**一并收敛**：
   默认只有本机用户目录（`apps/server/src/data-dir.mjs`），仓库 `data/` 只作 `BANDI_DATA` 显式沙盒。
   ⚠️ 现在只有 4 个变量能覆盖（`BANDI_DB` / `BANDI_CONNECTORS` / `BANDI_CONNECTORS_DIR` / `BANDI_ROUTES_DIR`），
   **`runtimes.json` 与 `plugins.json` 根本没法覆盖**。

2. **SQL 收口。** §九 那句「换库会让 SQL 裂成两份」说得不准。核了一下：现在 `store.mjs` 之外，
   `quota.mjs` 有一整套自己的 `db.prepare` / `db.exec`，`server.mjs` 还有一句直接伸进 `store.db`。
   → **换库的代价目前是 3 处**，可控；但要先收口，否则以后就是 3 处一起改。

3. **`node:sqlite` 是实验特性**（每个用例都会打 `ExperimentalWarning`）。长期托管别人的数据，
   得评估换 `better-sqlite3`（成熟依赖）或等它转正。有了第 2 条的收口，这一步才是小手术。

**所以：现在不换库** —— 换 Postgres 解决不了上面任何一条，只会把代价放大。但 1、2 两件现在就做。

### 两层必须现在定（不定就没法动手）

**4. 客户端怎么装配** —— 三选一：

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| Tauri 壳 ＋ 内嵌 `node.exe`（sidecar） | 最像产品；`apps/desktop` 已有壳；Rust 侧要写的很少 | 体积要算；**子进程生命周期要自己管**（别留孤儿进程）；依赖 WebView2 |
| Electron | 主进程**本身就是 Node**，最省事 | 体积接近 B3 的 200 MB 上限 |
| 托盘启动器 ＋ 系统浏览器 | 最便宜 | 不像「桌面应用」（不过「关浏览器不影响」已经成立） |

仍建议 **Tauri**（`apps/desktop` 已有壳，Rust 侧要写的很少）。有一个**前置**：壳要能拉起控制面并在退出时收掉。

**2026-10-15 已落地（开发形态）**：

- **前置**完成：起停逻辑抽成 `apps/server/src/lifecycle.mjs`，`start.cmd` 与壳**共用一份**，
  并顺手**跨平台**（以前是 Windows 专用，而控制面已经跑在 Linux 上）。
- 薄壳三层：`apps/desktop/src/shell.rs`（找 Node → 拉起 `shell.mjs` → 读协议行 → 退出收摊）
  ＋ `apps/desktop/shell.mjs`（Node 那半：起停判断、数据进用户目录、退出的分寸）
  ＋ `lib.rs`（只剩：起控制面、把窗口指过去、收摊）。那条 SSH 线的五个模块整体删除。
- 两半之间**只有三行协议**（`READY` / `ALIEN` / `FAILED`），判断逻辑**只在 Node 那一侧** ——
  多写一处就多一个跑偏的机会。
- **端口**：桌面版**不固定 8787，自己挑**（从 8787 往上）。对每个候选：空着就用、是我们自己的实例
  且在响应就**复用**、是**别人的程序就跳过**；选中的记进数据目录，下次据此复用**自己**那个。
  理由：命令行的 8787 是"给人用的约定"，桌面版没有这个约定 —— 而硬编码端口的桌面版，
  在"用户机器上恰好有别的程序占着 8787"时只剩一张错误页，对不懂电脑的人是死路。
- **安装包做出了**：`班底_1.0.0_x64-setup.exe`（22 MB）。`fetch-node.mjs` 取一份 Node
  运行时（81 MB，不进版本控制）随包分发 → **B2「不许要求用户自装运行时」满足了**。
  另外 `stage-runtime.mjs` 把控制面与界面摊成 `runtime/apps/...`，用
  `"runtime/apps" → "apps"` 映射进安装目录 —— 装出来的形状**与仓库一模一样**，
  `find_root()` 与那些相对 import 一行都不用改。
  （漏了摊平这一步的后果实测过：装出来只有 exe + node.exe，双击就是"没找到安装根"。）

**5. 控制面 ↔ 节点的传输** —— 建议**不引 WebSocket**：

- Node 没有内置 WS 服务端。自己实现握手 ＋ 分帧是两百行易错代码；引 `ws` 又破了「零依赖」。
- 用**挂起式长轮询**：节点发一个 GET 挂着等活，有活立刻返回（延迟 = 立即，不是 30 秒）；
  事件用 POST 批量上报（事件本来就是分块推的，不是逐 token）。纯 `node:http` 就够。

这同时落实了 §四「不用同类产品的 30 秒轮询」。

### 可以等，但现在把话说清

6. **前端不换 React。** 真正的痛点是 `apps/web/app.js` —— **一个文件 345 KB / 7683 行**，
   不是「没用框架」。要动就拆 **ES 模块**（浏览器原生支持、不用打包器，保住零依赖），
   收益接近而风险小得多。React 留到界面真撑不住再说。
   （README 那句「形态定了再换 Vite + React」的条件确实满足了，但结论是**不换**。）

7. **Rust 那堆旧代码。** `store.rs`（服务器登记）、`guide.rs`（公钥指引）属于已停的 SSH 登记那条线，
   跟「节点」模型相冲 —— **建议删**（git 历史里留着）。`ssh.rs` / `keys.rs` 等真要做 SSH 传输时再说，
   到那时设计可能已经不一样。

8. **桌面壳的旧产物别当现在的东西。** `apps/desktop/target/release/` 下有 `bandi-desktop.exe`
   与 `本软件_1.0.0_x64-setup.exe`（2026-10-11），是 `v1.0.0` 那条线打的包，旧界面已经**编进二进制**里了 ——
   跟现在的配置对不上，别拿它当桌面版。（`target/` 在 `.gitignore` 里，是本机残留。）

### 这一轮落地了什么（2026-10-15，为「部署到一台服务器」做准备）

| 条目 | 状态 |
| --- | --- |
| 1. 数据落点可配 | **已落地**，且 **2026-10-18 收敛为单一默认**：不设 `BANDI_DATA` → 本机用户目录（命令行与桌面壳同一份，`data-dir.mjs`）；`<仓库>/data` 只作显式沙盒。启动日志会打出数据目录与库路径 —— 「我在看哪个库」不该靠猜。刻意**不做**「写不进去就自动换家」的兜底：那会在权限抖动时悄悄换成空库，比启动失败糟 |
| 2. SQL 收口 | **已落地**。`db` 不再导出；`quota.mjs` 那一整套 SQL 与 `server.mjs` 里那一句都归回 store。现在全仓库**只有 `store.mjs` 有 SQL** |
| 3. `node:sqlite` 实验特性 | 记录在案，**未动**。换库的前提（第 2 条）已经具备，真要换是小手术 |
| 4. 客户端装配 | **未定**（桌面壳那一步定）。前置的一件已经做了：`start.mjs` 的起停自检逻辑将来直接复用 |
| 5. 控制面 ↔ 节点传输 | **长轮询（已落地）**：`POST /api/nodes/:id/claim` 挂 20 秒，有活立刻回；停止靠事件批次的响应带回 `stop`；**不引 WebSocket** | 见 §十一 ④。一个坑：长轮询要盯 `res.destroyed`，死了的请求方照样能把活领走 |
| 6. 前端不换框架 | 未动（也无需动） |
| 7. 删 Rust 旧代码 | **推迟，并说明原因**：`lib.rs` **整个就是**那条 SSH 登记线，`ApiError` 等类型四个模块互相引用 —— 删一半 crate 就编译不过，而删干净 == 重写 `lib.rs` == 桌面薄壳那一步的活。所以**删除与重写必须一起做**，已在 `lib.rs` 顶注写明，别在半途拆 |

**顺带补上的两件（不在原清单里，但不补就是隐患）：**

- **监听地址与来源可配** `BANDI_HOST` ＋ `BANDI_ORIGINS`。默认只听本机。不配 `BANDI_ORIGINS`
  而只改 `BANDI_HOST` 的话，远端浏览器打开页面**能看不能动**（写请求全 403）—— 这是「部署上去发现
  界面点不动」最可能的原因，所以它必须跟第 1 条一起做。
- **测试隔离补齐**：既有 smoke 用例以前只隔离数据库（`BANDI_DB`），`plugins.json` / `connectors/`
  照样写进真实 `data/`（`smoke-status.mjs` 的注释里就记着这个限制）。现在一律带上 `BANDI_DATA`，
  跑完全套真实 `data/` **零改动**（已实测）。
- **访问令牌**（第三条前置，2026-10-15）：规则**只看监听地址** —— 只监听回环（桌面版/单机）免鉴权；
  监听非回环（服务器）**所有请求都要令牌**。为什么不看"来源是不是回环"：反向代理会把来源变成回环，
  那样架一层代理就把闸绕过去了；规则跟着**配置**走，才不会被部署方式偷走。
  令牌在数据目录的 `token` 里（或 `BANDI_TOKEN`，不落盘）；浏览器填一次记进 HttpOnly Cookie
  （`EventSource` **没法自己设头**，Cookie 是它唯一的活路）；节点/脚本用 `X-Bandi-Token`。
  **已部署实测**：外网不带令牌 401、首页给登录页、带令牌 200、错令牌 401。
  ⚠️ 这是**一枚共享令牌**，不是账号体系 —— 拿到它的人就是「我」。单操作员自托管够用；
  多人各看各的，是另一件事（还没做）。

**验证**：`smoke-data-dir`（14 项）、`smoke-quota`（20 项）两个新用例，加既有 6 个，共 **8 个用例全过**。
`smoke-quota` 是这个功能**第一次有覆盖** —— 收口 SQL 时才发现它此前一条用例都没有。

**部署产物**：`deploy/bandi.service`（systemd；数据指 `/var/lib/bandi`、只听本机）＋
`deploy/start-control-plane.sh`（**无 root** 时的用户态起停）＋ `deploy/README.md`
（装、SSH 隧道访问、节点报到、备份、排障）＋ `start-node.cmd`。
⚠️ **还没有鉴权**，所以隧道优先、别开公网 —— 这条写在手册最前面。

### 部署实测（2026-10-15 · 火山引擎一台）

**目标机实况**：Ubuntu（内核 6.8、x86_64、3.9 G 内存、40 G 盘），`bandi` 用户 ——
**没有免密 sudo**、**没有 Node**、**连 git 都没有**。所以原手册那套 root + systemd 在这台上用不了。

**做法**：Node 22.21.0 装进 `~/.local/node`（不碰系统）；代码用 `tar` ＋ `scp` 传到 `~/bandi`
（无 git，只能推）；数据放 `~/bandi-data`（**在代码目录之外**，升级不冲）；用
`deploy/start-control-plane.sh` 用户态起停。

**结果**：

| 验什么 | 结果 |

## 十三、能不能把服务端放到 Cloudflare（2026-10-16 问的）

**短答：整台服务端不适合。但 Cloudflare 对这件事有一件非常合适的用法 —— Tunnel。**

先把服务端的**真实依赖**摆出来（在 `apps/server/src` 里数出来的，不是印象）：

| 依赖 | 用量 | 放到 Workers 会怎样 |
| --- | --- | --- |
| `node:sqlite`（`DatabaseSync`） | 12 处 | **没有**。D1 虽然也是 SQLite，但那套绑定是**异步**的，而 store 里全是同步调用 |
| `node:fs`（`readFileSync` 33 / `writeFileSync` 14） | 47 处 | **没有文件系统**。数据目录、日志、`runtimes.json`、静态前端全靠它 |
| `node:child_process`（`spawn` 25 / `execFileSync` 7） | 32 处 | **没有进程**。本机执行、CLI 探测、`netstat`/`taskkill` 全在这一层 |
| `node:http` ＋ `text/event-stream` | 3 处 | 得换成 `fetch` handler；SSE 还能流式，但下面那条长轮询不行 |
| 长轮询（挂 45 秒领活）＋ `setInterval` 清扫 | — | 没有"挂起的请求"、也没有"常驻定时器"，要改用 Durable Object ＋ alarms |
| CPU 时间 | — | 有上限；而**起一个 CLI 跑半小时**这种活本来就不该在边缘节点上干 |

所以这不是"改几行"，是**换了个运行时模型**。

### 但有三块是可以搬的（如果哪天真要托管）

1. **静态前端** → Pages / Workers Assets。这块最容易，`apps/web` 本来就是无框架的静态文件。
2. **队列与推送** → Durable Object：一个 workspace 一个 DO，用 WebSocket 替掉长轮询，
   用 `alarms` 替掉 `setInterval` 的掉线清扫。**模型上最贴的一块是它。**
3. **存储** → D1。`store.mjs` 把 SQL 收口到了一处（那是当初那个决定的红利），
   但**同步改异步**仍是一次彻底重写 —— 每个 `db.prepare(...).get()` 都得变成 `await`。

**执行端永远不该上云。** 那正是整个形态的立身之本：代码、凭据、CLI 会话都在用户机器上，
控制面只存编排数据（见 §二 的权威边界表）。

### Cloudflare 对现在这套真正有用的两件事

1. **Tunnel（`cloudflared`）** —— 不用开端口、不用公网 IP，把控制面挂到公网，自带 TLS。
   它能把现在那套"安全组限源 IP ＋ 一枚共享令牌"整个替掉；而且
   **Cloudflare Access 能按邮箱/OTP 做真身份**，恰好补上"共享令牌不是账号体系"这个弱点
   （见 §十一 ④ 与 deploy/README 第六节）。**零代码改动**：
   `cloudflared tunnel --url http://127.0.0.1:8787`
2. **R2 当备份落点** —— 控制面的数据就一个 SQLite 文件 ＋ 一个数据目录，现在**完全没有备份**。

### 结论

留在那台小 VM（火山）上。对"几十台节点 ＋ 几个人"它绰绰有余，而且**长连接、CPU 时间、本地文件**
这三样恰好是它的强项 —— 而 Workers 把这三样都拿掉了。真要接 Cloudflare，是为了接
**Tunnel 的接入与身份**，不是为了把服务端搬过去。

⚠️ Cloudflare Containers（能跑容器、有文件系统）这条新路也在，但磁盘是**临时**的、实例会休眠 ——
真要拿它跑，得配 R2/D1 做持久化。**这条我没实测**，要用请以官方文档为准。
