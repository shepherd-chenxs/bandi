## 主体功能

**主体功能以本文件为准**，不走任务卡与版本台账那套重流程。只做这四条，做完就能用：

1. **集成 agent CLI** —— 第一版接 **Codex**（`codex exec --json`），dsh 作为第二个适配器并存。
   两个适配器输出**同一套事件词汇**，上层不关心底层是哪个 CLI。
2. **创建数字员工** —— 一个数字员工 = 名字 ＋ 职责指令 ＋ **岗位手册（随岗位固定，不可见）** ＋ 绑定的 runtime ＋ 权限（沙箱模式）＋ 工作目录。
3. **和数字员工对话** —— 一条消息一次进程调用；从事件流里取回会话 id，下一句带回去就续上了。
4. **会话即工作项** —— 每个会话有标题、状态（待跑／跑中／完成／失败）和完整事件流。这是产品的骨架。

**这四条是骨架**。骨架之外后来陆续落地了：流程引擎（模板 ＋ 实例）、项目与任务看板、
鉴权与开机自启 —— 这些的设计理由，以及「已经撤掉的体系」（含多机节点），见 [形态决策](形态决策.md)。

## 这一版不做

移动端、IM 集成、多租户、权限矩阵、成本分析、逐 token 打字机。

**中途递话**这一版也不做——但性质变了：Codex 有 `codex queue --thread <id> --message <text>`，
能给正在跑的会话递话；dsh headless 没这个能力（每次调用只跑一个任务）。
所以这是**排期问题，不是能力问题**，接口先按"排队式"设计，留出递话的位置。

## 怎么算做完了

一条可复现的链路，不靠感觉。两个 runtime 都已实测通过：

```sh
# Codex：新会话 + 续接
codex exec --json -C <项目目录> -s read-only -          # 退出码 0，事件流含 item.completed / turn.completed
codex exec resume <thread_id> --json -                  # 同一 thread，上下文还在

# dsh：同样的两件事
dsh --profile headless --json -                         # session 事件给出 sessionId
dsh --profile headless --json --session-id <id> -       # turn 变成 2
```

**平台的验收 = 在界面上点出同一件事，落进同一份事件流。**

## 统一事件词汇

两个适配器都产出这套，前端只认这一套：

| 事件 | 含义 |
| --- | --- |
| `session` | 本次运行的会话标识（Codex 的 thread_id／dsh 的 sessionId） |
| `status` | `turn_start` / `step_start` / `step_end` / `turn_end`（带 usage） |
| `thinking` | 推理文本 |
| `text` | 助手正式回复 |
| `tool` | 工具动作（命令执行、文件改动、MCP 调用…） |
| `error` | 失败 |
| `final` | 最终答案 |

## 一个 run 的生命周期：一次尝试，还是有限次（2026-11-21）

起因是个直白的问题：「同一个任务，别的 agent 能做到底，bandi 撞一下就报失败停下，为什么」。
根因不在模型，在**外层没有循环**：一次 run = 一次 spawn，进程一退平台只拿到终态，
而成功的判据只有"exitCode 非 0 / isError"这一个布尔 —— 连接抖一下、进程被杀一次、
上游 502 一下，全都落成卡面「失败」，等人来点「重跑一次」。

现在的口径：**一次 run 可以包含 1~N 次尝试**，同一条 CLI 会话、同一个 run id、
同一份事件流，只在最后收一次尾（一次写库、一次吊销钥匙、一次推进流程）。
判据与提示语收在 [`apps/server/src/run-retry.mjs`](../apps/server/src/run-retry.mjs)，
编排在 `runs.mjs` 的 `settle()`。

| 失败长什么样 | 续不续 | 为什么 |
| --- | --- | --- |
| 上游 5xx / 超时 | **续** | 通道是通的，换个时刻就好 |
| 只有退出码、没有任何原因（如 `退出码 4294967295` = Windows 的 -1） | **续** | 进程被谁杀了不该算"活做不成"；真库里最常见的一种 |
| 配置错 / CLI 未登录 / 权限档挡命令 / 上下文满 / 4xx / 限流 | 不续 | 再跑一遍是同一个结果，等于拿 token 换一句一样的话 |
| 通道断（连不上模型） | 不续 | CLI 内部已重连过 5 次；那条"去修代理、回来回「继续」"的回话才是人能照做的下一步 |
| 已经下了交付声明（`[完成]` / `[受阻]`）才挂的 | 不续 | 不是"半路死"，是"说完了才死" |
| 有具体报错的未知失败 | 不续 | 被藏起来的错误，第二次还是错的 —— 先让人看见 |

三件容易漏的事：

- **续跑第一句是"先复核你上一轮的判断"**，不是"接着干"。停下来的诊断会过期：
  实报里某轮 15:54 判"钩子路径有问题"，次日那条残留早没了，重跑直接 101 项烟测全过 ——
  它抱着一张过期的诊断在等人回话。
- **不续也要写明为什么没续**（`（未自动续跑：…）` 会进卡面）。否则人只看到
  "跑挂了：unknown MCP server"，永远不知道平台试过没有。
- 次数上限 `BANDI_RUN_AUTO_RETRY`（默认 2，0 = 关）、间隔
  `BANDI_RUN_AUTO_RETRY_DELAY_MS`（默认 1.5 秒）。人工停止、挂死收口一律不续。

## 停之前的最后一个动作：环境类断言先实测（2026-11-21，契约第 13 条）

同一场复盘里最便宜的一处浪费：**凭代码推断宣布机器状态**。「钩子不在 / 端口被占 / 进程残留 /
依赖没装 / 连不上」—— 一条 `ls`、`netstat`、`where`、`curl` 就能证伪，却直接拿来当停下的理由。
而且环境是流动的：停下那一刻的结论，第二天多半已经不成立（上一节"诊断会过期"是同一个病）。

规则（`dispatch/contract.mjs` 第 13 条，**每轮注入**，因为它管的是任意一轮的"停"）：

| 场景 | 该做什么 |
| --- | --- |
| 要说「不存在 / 没装 / 被占了 / 没启动 / 连不上 / 已失效」 | 先跑**一条**能验它的命令 |
| 因为环境不行要写 `[受阻]` | 必须至少留一条实测输出；一条没跑 = 不算结论 |
| 真跑不了（没有可用的命令） | 写「未验证」，不许写成事实 |
| 验完发现能过 | 别停，干完再回话 |

**平台侧有一道可证伪的核对**（`task-claim-audit.mjs` 的 `unverifiedEnvClaim`）：
`[受阻]` + 本轮 **0 条 `tool` 事件** + 理由是环境事实 = 这个判断在数学上不可能验证过。
处置是**只记信箱（info）、不唤醒任何人**，跟"虚构派卡"那种打回重做不同：

- 它不是谎 —— 模型没声称做了动作，只是"该验没验"；
- 自动唤醒要花一次真跑，而且在"每轮都收尾"的链路上容易滚成循环（一次错判 = 一直重跑）。

三种情况明确不管：不是 `[受阻]`（还在干活）、理由含**权限 / 授权 / 审批 / 沙箱**
（entitlement，报了是对的）、调过任何工具（分不清验的是哪一条 —— 宁可漏报不误报）。

## 岗位判据：专业度里能被核对的那一半（2026-11-22）

岗位手册（`roles/packs/*.md`）里一直写着"验证过再交""不许按进程名清杀"，但平台**不认识这些话** ——
它只认 `[完成]` 和卡状态。于是手册里的红线只是建议：说了不一定做，做了没人核，
改一版手册也没有任何东西能说这版比上版更专业。

所以把"能被工具事件证明的动作"从手册里抽出来，变成判据（`role-criteria.mjs`）：

| kind | 判据 | 核的方式 | 什么时候核 |
| --- | --- | --- | --- |
| `must-run` | 必须跑过 | 本轮有一条**命令**包含给定候选之一（OR） | 只在**声称完成**那一轮 |
| `must-read` | 必须读过 | 本轮有一次读文件命中给定路径之一 | 同上 |
| `never` | 不许（红线） | 本轮**任何**工具动作出现该串（正则更稳） | 任何时候 |

来源两层：`BASE_CRITERIA`（全体员工，目前只有一条 —— 不许按进程名全量清杀，契约第 12 条的执行侧）
＋ 手册 `## 判据` 段（现在只有研发 / 测试）。**宁少不滥**：判据一多，合同变长、误判变多，
最后没人看。写进手册的门槛只有一条：**动作能被工具事件证明**（"要专业 / 要思考"这种一律不收）。

两条防诬告的规矩（与台账核对同口径）：

- 本轮**一条命令事件都没有** → `must-run` 记「判不了」，**不记失败**（有的运行时不吐 tool 事件）；
- 没声称完成 → `must-run` / `must-read` 不核（还在干活的中途当然可以没跑）。

处置（`criteria-audit.mjs`，挂在 `onRunFinish`、注册在台账核对**之后**）：**只记信箱**，
不改卡、不 @ 人、不自动重跑。验收权在人手里；而"判据未过"往往不是差一次跑，
自动重跑会滚成每轮都重跑。

体检侧：`tools/persona-metrics.mjs` 现在有一条「判据核对」—— 它量的才是专业度
（声称完成时动作到没到位）；前面那些字数 / 首行 / `Next:` 量的只是汇报文风。

## 长期记忆：经验簿 + 事实层（2026-11-22 / 2026-11-23）

员工的"记忆"其实一直在库里（聊天、卡、返工、交付证据都持久化），丢的只有**他自己那条 CLI 会话**。
会话一换（上下文预算、换流程、换卡），他就重新做人 —— 同一个坑踩第二遍，团队口径要重新讲一遍。
当时的「上下文交接」只带最近 8 条消息、每条 160 字，那是"刚才聊到哪"，不是"这台机器上什么是对的"
（眼前这件事的状态后来由下一节的「事实账」补上，两者分工）。

所以有 `persona_notes`（`store/notes.mjs` + `experience.mjs`），**只收两类**：

| kind | 是什么 | 谁写进来 | 例子 |
| --- | --- | --- | --- |
| `repo` | 这个团队的口径 | **只收显式写入**（接口 / `bandi note add`） | 「服务端改完必须重启，静态资源直读不用」 |
| `pitfall` | 这个人踩过的坑 | **平台从核对结论里自动记**（kind='audit' 的通知） | 「声称完成，但没做：完成前跑过测试」 |

事实层（2026-11-23 补，`persona_facts`，`store/facts.mjs` + `experience.mjs`）补的是另一半：
"这个仓里怎么跑、常改哪儿"也会随会话丢掉，但它不该由人或模型写，而是从**跑通那一轮**
的 `run_events` 里抽。只认三类，且每一类都能指回一条真实的 tool 事件：

| kind | 是什么 | 抽取条件 | 例子 |
| --- | --- | --- | --- |
| `command` | 验证命令 | 命令文本命中 `run-smokes` / `npm test` / `pytest` … | 「冒烟验证：node tools/run-smokes.mjs」 |
| `restart` | 重启方式 | 真的执行过 `bandi restart` | 「重启：bandi restart」 |
| `path` | 常改文件 | 同一文件在 **≥2 轮**里被改过 | 「常改：apps/server/src/dispatch.mjs」 |

事实按 `scope`（仓库根）隔离：`'npm test'` 只在这个仓成立，注入时只取"当前仓库 + 全局"那批；
只改过一次的文件不进注入（多半是这一轮的临时脚本），依赖/产物/临时目录一律不记。
摘不出来就一条都不记 —— **宁可少，不要猜**。

三条刻意的边界：

- **不记「聊过什么」。** 聊天摘要是模型生成的，会漏会编、没人能核，还占上下文；
  要细节就翻会话和 `run_events`。这条和「把判据押在员工记得写字上，本身就是错的」是同一个道理。
- **反复犯的并成一条。** 去重键抹掉日期 / 卡号 / 这一轮的命令清单，只留"是哪一类错"——
  于是同一个坑犯五次是 `hits=5`，不是五行各说一遍（证据留在 `run_events` 里，那里才是查证据的地方）。
- **不记"这人行不行"。** 经验簿存事实与口径，不存评价；评价是人做的事。

注入（`dispatch.mjs`，位置在"这轮要干什么"之后、"方法论"之前）：**口径 ≤4 + 事实 ≤3 + 坑 ≤3**，
用与本轮任务同一份 `matchText` 做**相关度召回**（英文/路径词 + 中文二元组重叠，确定性、不猜同义；
没用 FTS5：中文没有分词器，每人候选集也只有几百行），同分时才回到原序（口径新的在前、坑按次数）；
整块 ≤1200 字；**一条都没有就返回空串**（不印空壳 —— 空块会让模型以为缺了什么）。
每人上限 200 条，超了先删"用得少且最久没动"的；没进上下文的仍在 `bandi note ls` 里看得到。

三个入口：
- `bandi note ls/add/rm/forget <员工>`，以及 `GET|POST|DELETE /api/personas/:id/notes`
  （写只收两类、清空要显式 `?all=1`、不能跨人删）；
- `GET|DELETE /api/personas/:id/facts` + 员工简卡里的「长期记忆」栏（看得见、能删；
  **没有 POST** —— 手写的东西属于口径，事实只能由平台抽）；
- 运行钥匙对两边都**只读** —— 跑起来改自己的记忆会让"谁记的"变模糊
  （`source` 只有 `audit` / `manual` 两种，必须分得清）。

体检侧：`persona-metrics.mjs` 多一节「经验簿 / 长期记忆事实」。读法有讲究：**坑的条数不涨、
`hits` 在涨** = 提醒没拦住同一种错；**口径一直是 0** = 这条链路没人用，不是"没问题"；
**事实一直是 0** = 还没跑通过一轮（不是抽取坏了）。

## 会话轮换：交接的是「这段活干到哪了」（2026-11-22）

经验簿管的是**长期口径**；换会话那一刻还差另一半：**眼前这件事现在什么状态**。
老的「上下文交接」只带最近 8 条消息 ×160 字 —— 那是"刚才聊到哪"，不是"这段活干到哪"。
实报的代价：一段活跑了 7 轮（失败 5）、改了 4 个文件，换个会话接手的第一句是"我先看看"，
于是把已经改过的文件再改一遍、把已经踩过的坑再踩一遍。

`progress-ledger.mjs` 从库里抽**平台能证明的事实**（不生成摘要、不猜意图）：

| 事实 | 从哪来 |
| --- | --- |
| 卡号 / 标题 / 现在状态 / PR·CI 结论 | `project_tasks`（证据口径复用 `delivery-evidence.mjs`） |
| 一共几轮、完成 / 失败 / 被停各几次 | `runs` |
| 每轮什么时候、多久、改了哪些文件、最后一条命令、为什么挂 | `run_events` 尾部 80 条 + `runs.error` |
| 反复失败的原因（按次数） | `runs.error`，归一后计数 |
| 上次回话的落款（`[完成]` / `[受阻]` / 没写） | `messages` 最后一条 + `delivery-claim.mjs` |

三条边界：**只认改动类事件**（`file_change` / `apply_patch` 的 `changes[]`；Read 的 `path`
不算 —— 否则"看了一眼"会被说成"改过"，比不交接更坏）；**报错说人话**（`退出码 4294967295`
→「进程异常退出」；运行时日志行去掉时间与级别；命令剥掉 powershell 外壳）；
**有上限**（明细 3 轮 / 文件 10 个 / 整块 1200 字）。

注入时机只有两个（`dispatch.mjs`）：**轮换之后**（`rotated`）和**这条会话本来就是空的**
（`firstTime`：新卡第一次派、会话丢了）。正常续接不注入 —— 那会儿上下文里都有，再塞一遍
是噪声还费 token。没有历史也没有卡时返回空串，不印空壳。

`store.tailMessages()` 顺手修了一个贵处：交接原来用 `listMessages(...).slice(-8)`，
**把整个会话读出来再扔 99%** —— 而轮换偏偏发生在"会话已经很长"的时候。

## 「做完了没有」：声明 + 客观证据两条腿（2026-11-21）

老口径是**声明制**：平台只认回话里的 `[完成]` / `[受阻]`（`delivery-claim.mjs`），
员工漏写一次，活就算白干 —— 实报 `pt-4b6bf1ec`：PR #83 合了、80 项冒烟全过，
只因为最后一段结论里没写那三个字，卡在「已阻塞」躺了一天，还得人来问"这是完成了吗"。

病根和"假失败"是同一个：**把语义判断压在一条容易漏掉的字符串约定上**。所以补第二条腿：

| 腿 | 判据 | 谁说了算 |
| --- | --- | --- |
| 声明 | 回话里的 `[完成]` / `[受阻]`，或运行钥匙 PATCH 上报 `review` | 员工 |
| 证据 | **PR 已合并** / **CI 全绿**（都来自 GitHub，不是模型说的） | 平台 |

判据单点在 `delivery-evidence.mjs`（纯函数）：合并最强；CI 全绿次强（只认 PR 还开着时，
且结论不超 24 小时 —— 隔夜的"全绿"证明不了今天）；**CI 红是反对证据**，不许把卡往上推。
只认事实字段，不解析自然语言。

落地分两处，都在既有的节拍上，不新增后台进程：

- **收尾**（`onTaskRunFinished`）口径不变：`[完成]` → 待验收，无标记 → 已阻塞。
  收尾那一刻 CI 通常还在排队，同步去查只能拿到 pending，所以这里**不查**。
- **巡检**（`pr-watch.mjs`，默认 30 分钟）把 `headSha` 上的 check-runs 抓回卡上
  （`prCiState` / `prCiFailed` / `prCiAt`），再按证据收：
  「已阻塞」+ 强证据 → **待验收**（`advanceByEvidence`）。

`advanceByEvidence` 的四道闸，缺一不动：只动「已阻塞」（进行中归 `afterMerged`；
「失败」要让人看见这轮崩了，不能因为 PR 合了就抹掉）；只认强证据；**人手动改成阻塞的不动**
（`statusByUserId` 非空 = 人压着这事）；**员工自报 `[受阻]` 的不翻案**（证据强不代表他的顾虑消失）。
终点只有「待验收」，**永不「已完成」** —— 11-09「平台替员工宣布完成」那条实报划的线不变。

## 三处收口：让机制代替纪律（2026-11-08）

这三件事以前都靠"记得改"，现在都有机器判。

**分发顺序是数据，不是书写顺序。** `/api/*` 分两层：`server.mjs` 里一张**精确 key 表**
（`GET /api/hello` 这类字面量，一次哈希查表）在前；带动态段的路径交给 `routes/chain.mjs`
按数组下标依次问各域模块（先匹配先赢）。改造前那是 25 段手写 if —— 顺序只存在于书写顺序里，
加模块要"插在对的位置"，而十几个路由文件头部写着的「主分发顺序见 `server.mjs` 的 CHAIN」
指的是一个**并不存在**的符号。现在漏挂 / 重挂由 `tools/check-dispatch-chain.mjs` 扫
（挂在 `run-smokes` 的唯一入口上，与 `check-routes`、`check-doc-drift` 同级）。

**安全响应头装在请求链最前面。** 全站一份 CSP（`security/csp.mjs`），`script-src` 用
`index.html` 内联脚本的 sha256，而不是 `'unsafe-inline'` —— 界面是 innerHTML 拼字符串，
`esc()` 是纪律，CSP 是机制：漏转义时由浏览器挡住。哈希按 mtime 现算（含 CRLF 归一，
否则 Windows 上 CRLF 检出会让内联脚本全部失效），不维护手工哈希表。另加 `nosniff`。

**状态只有一份词表。** `store/status.mjs`：任务八态 ⇄ 看板列（反向映射由同一张表推出）、
流程态、运行七态。看板、流程、聊天回执全从它派生；建表默认值必须是词表里的词
（`smoke-status-vocab.mjs` 按源码文本核，不开库）。库另有**结构代次** `PRAGMA user_version`：
`SCHEMA_VERSION` 一旦落后于库里记的版本就**拒绝启动** —— 老程序打开新库会照常写、把新列
当不存在，静默产出半对的数据，那比报错难查得多。

**形态已定（2026-11-09 更新）**：**单机 ＋ 隧道**。每台机器跑一个完整班底（控制面就地在本地跑），
web 只是界面；远程访问用 tailscale / cloudflared / frp 把本机接出去，不把本机注册成节点。
"关掉浏览器会不会挂"不成立——干活的是本地控制面拉起的 agent 子进程。
历史形态（2026-10-15「托管控制面 ＋ 客户端出站节点」）与删除记录见 [形态决策](形态决策.md)。

## 两个适配器的已知不对称

- **Codex**：`exec` 收 `-C <目录>` 与 `-s <沙箱模式>`；但 `exec resume <id>` **两个都不收**，
  续接靠进程 cwd 与会话记录。另外 `-p <name>` 可叠加 `$CODEX_HOME/<name>.config.toml`，
  正好可以当"员工配置层"。`codex queue` 可给运行中的会话递话。会话按 cwd 过滤（`--all` 可关）。
- **dsh**：CLI 不在 PATH 上，真实做法是 `ELECTRON_RUN_AS_NODE=1` 起 Electron 可执行文件再跑
  `app.asar` 里的 `cli.js`；`.cmd` 过 shell 有引号坑，所以直接起 exe ＋ 参数数组。
  班底只把**模型名**用 `--patch` 传下去；走哪条地址、带谁的 Key 由 profile 自己的配置决定
  （凭据由 dsh 从 `$DSH_HOME/.env` 读，班底不注入）。
  ⚠️ 补丁层是**整块替换 `config`**、不是逐字段合并 —— 只写 `model` 会把 profile 里的
  `provider:` 一起冲掉，所以那一行必须原样读回来再写回去。

## 飞书通道

- **定位**：一条**平台级**通道（不是每个数字员工一个入口）——用户建 1 个飞书自建应用；
  私聊机器人 = 找**绑定的员工**（设置页下拉挑，没绑/绑的人没了 → 落到秘书），群里 `@员工名 做某事` = 派给那个员工（没 @ 不响应）；
  每条指令回一张**随 run 推进的可更新进度卡**（思考中 / 调工具 / 收尾 → 完成带结果；拍板按钮后置）。
  同类产品 Multica 的做法一致（长连接、群只响应 @、1 bot = 1 agent）——它的进度卡还是个 open issue，这版先做了。
- **为什么是出站 WebSocket 长连接**（`apps/server/src/feishu.mjs`）：飞书事件订阅的长连接模式是
  **我们主动连它**，不需要公网回调地址与 HTTPS —— 正好贴合「只听本机」的自托管形态。
  [形态决策](形态决策.md) §十二「不引 WebSocket」说的是**入站**架构；对第三方 SaaS 的
  **出站**客户端是另一回事，模块头有注释说明。
- **零依赖怎么守**：不引官方 SDK（要 npm install），协议手写 —— 帧格式（pbbp2.Frame 的 protobuf
  字段号）照抄 `larksuite/node-sdk` 的 `ws-client/` 源码：
  `POST /callback/ws/endpoint` 拿临时接入点 → WS 收帧（headers 数组、payload 按 message_id/sum/seq 分片合并）
  → 回 ack（不回会被重推）→ ping/pong 心跳 → 断线重连（间隔/次数由服务端下发，带随机抖动）。
  WebSocket 客户端用 Node 22 自带的全局 `WebSocket`。
- **派活完全复用现成链路**：`persona-task.mjs` 的形状（建/复用会话 → `dispatchToThread`；
  撞 busy → `dispatchEventToThread` 落库进队等补派）；进度归约直接 import 前端纯逻辑模块
  `web/js/run-progress.mjs`（无 DOM），不另写一份"事件 → 阶段"。
- **数据落点**：凭据 `<dataDir>/feishu.json`（0600 尽力，不进库、不进日志、接口只回掩码 —— 与生图
  Key 同一套规矩）；群↔会话映射 `<dataDir>/feishu-links.json`。配置在「设置 → 飞书」。
  HTTP 面在 `routes/feishu.mjs`，错误码认领 E2061–E2066。
- **v1 边界**：只认文字消息；`allowOpenIds` 白名单（空 = 不限制）；服务重启丢进行中的卡跟踪
  （与群排队同口径 —— 要"必须不丢"的活走任务卡）；只接中国大陆版飞书（国际版 Lark 域名不同）。
