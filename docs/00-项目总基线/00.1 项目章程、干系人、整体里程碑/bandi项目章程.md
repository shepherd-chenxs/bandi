## 1. 项目章程

### 1.1 一句话

**班底（BANDI）**：把活派给 AI 数字员工，看它干，随时接管。自托管运行，数据和工作目录都留在你自己的机器上。

### 1.2 要解决的问题

直接用 agent CLI 是"一个人对一台机器"：活的组织、过程的可见、结果的验收、出错的接管，全靠人肉。
班底把「派活 — 执行 — 汇报 — 验收」变成一个可管理的工作系统 —— 人像管理者一样定方向、看过程、收结果。

### 1.3 目标与成功标准

| 目标 | 判据（可客观检查的） |
| :--- | :--- |
| 派活闭环能跑通 | 一条消息能起一次运行，过程事件落库（`run_events`）并实时可见，收尾有落款（`runs.claim`） |
| 过程永远可见 | 思考 / 工具调用 / 回复按统一事件词汇流出，重连能按 `Last-Event-ID` 补发 |
| 交付带证据 | 完成声明能被平台按 `run_events` 的 tool 事件核对，核对结论落信箱 |
| 数据不出机器 | 代码与密钥不出本机；中枢只转发请求，不存状态、不派活 |
| 一个人能维护 | 仓库零构建依赖（服务端只用 Node 内置模块 ＋ 一个 SQLite 原生模块），四道闸在门禁里机器判 |

> ⚠️ 已有一个目标**机制建好但效果未证明**：岗位判据＋回归集能跑，但"手册改动是否让员工更专业"在 v2 上**没有证明**（4 平、无升无降）。详见 [风险台账](../00.6%20风险、问题总台账（跨迭代）/bandi风险问题台账.md) R-001。

### 1.4 范围

**做**：

- 两类 agent CLI 集成（codex / claude；dsh 已于 2026-11-24 v1.7.3 下线），统一事件词汇
- 数字员工（名字＋职责＋岗位手册＋运行时＋权限＋工作目录）
- 会话派活、群聊派活、流程引擎（模板→实例→节点任务）、项目看板
- 代码托管全链路（接入→克隆→干活→提交推送→建 PR→巡检→审阅→合并）
- 长期记忆（经验簿＋事实层）、平台事实信箱、定时任务
- 三种客户端连同一台本机控制面（桌面 Tauri 壳 / Android 原生壳 / 浏览器）

**不做**（都拍过板，理由见决策日志）：

| 不做 | 拍板时间 |
| :--- | :--- |
| 多租户、账号分级（本机登录即全权） | 2026-11-07 |
| 多机协同 / 算力节点子系统（已整体删除） | 2026-11-09 |
| 团队协作组织、分公司、协作中心 | 2026-11-07 |
| 代装 agent 运行时（只识别、只调用） | 2026-11-04 |
| 额度限额、服务端生图、CLI 详情页 | 2026-11-16 同批退场 |
| 换前端框架（原生 ES modules，不引构建器） | 2026-10-22 |

### 1.5 形态

**单机是唯一形态**：一台机器一个完整实例，有自己的库、项目和员工。跨机器协作走 git 仓库和 PR，不靠共享库。
桌面客户端是形态，web 只是界面；手机原生壳和浏览器连同一台本机控制面。

### 1.6 治理与口径

| 机制 | 落点 |
| :--- | :--- |
| 版本真源 | `apps/desktop/version.json`；release 工作流规定 git tag 必须与它一致 |
| 决策记录 | [产品决策日志](../../01-迭代版本包/产品决策.md)（按版本→日期倒序，只追加不回写） |
| 前端改动记录 | [前端改动日志](../../01-迭代版本包/web.md)（版本条目，只追加） |
| 文档对账 | `tools/check-doc-drift.mjs`：每份 .md 必须登记为活文档或快照；活文档提到的文件必须存在、错误码必须在码表里 |
| 路由/契约/分发 | `tools/check-contracts.mjs`、`tools/check-ghost-refs.mjs`、`tools/check-dispatch-chain.mjs`，与 doc-drift 合称"四道闸" |
| 业务回归 | `apps/server/src/regression/suite.mjs` ＋ `tools/regression.mjs`，**手工跑、不进 CI** |
| 状态唯一词表 | `apps/server/src/store/status.mjs`：码是唯一真身，中文只是 label |
| SQL 边界 | 只出现在 `apps/server/src/store/` 里 |

> 基线文档只维护**最新生效版本**；大版本（如 V2.0）重构时归档上一版快照，见 [文档管理方案](../../多迭代版本项目文档管理方案.md)。

## 2. 干系人

### 2.1 真人与外部依赖

| 角色 | 是谁 | 关系与决定权 |
| :--- | :--- | :--- |
| **主理人** | 产品负责人（GitHub: `shepherd-chenxs`） | **唯一的真人决策者与验收人**：定方向、拍形态、定优先级、验效果。产品假设"一个人同时扮演老板 / 项目经理 / 审阅人" |
| 目标用户 | 一个人能维护、一个人能用的开发者 / 超级个体 | 不面向团队协作组织；需求从自身使用中长出来 |
| 身份中枢（bandi-hub） | 独立仓库的外部系统 | 负责**认证**（登录、心跳、在线状态），本机负责**授权**。契约版本收在 `HUB_API_VERSION`，只准 HTTP 认它、不许 import 代码 |
| agent CLI 厂商 | codex / claude 两族（dsh 已于 2026-11-24 v1.7.3 下线） | 外部执行端：自己装、凭据自备。班底只识别、只调用，不代装、不分发 |
| 前端与桌面壳 | `apps/web`、`apps/desktop`、`apps/mobile-native` | 同一份网页 UI 的三个承载者，界面单一来源 |

### 2.2 系统内的"协作者"（不是干系人）

数字员工（`personas`）是**被管理的执行资源**，不是干系人：它们没有决策权，只在被派活时执行，
做不了的事必须停下来问人。平台侧对它们的要求写在内置岗位手册（`## 判据` 段）里，由
`apps/server/src/role-criteria.mjs` 解析、`apps/server/src/criteria-audit.mjs` 在收尾时核对。

### 2.3 决策权边界

- **形态与范围**：主理人拍板，写进决策日志。
- **专业度缺口的方向**（如何让手册判据真正拉动行为）：三条候选路线已列出，**等主理人拍板**，不由执行方自行决定。
- **环境类阻断**（如安全软件黑名单）：需主理人本人操作，禁止用等价命令绕过安全策略。
