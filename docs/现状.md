## 二、流程引擎与技能契约

编排不再是技能——谁上场、下一步去哪、干完停不停，由**流程引擎**做（模板 + 实例）：

- **技能库里没有自研的角色说明书**：全部是上游能力包（anthropics/skills 的 `doc-coauthoring` / `skill-creator` / `webapp-testing`，obra/superpowers 的 `brainstorming` / `test-driven-development` / `systematic-debugging` / `requesting-code-review` / `receiving-code-review` / `verification-before-completion`），原样引入、来源与许可记在 [skills/README.md](../skills/README.md)。**职责不写在技能里**：谁在第几步干什么由流程模板决定；**节点上只有点名（`personaId`），没有"技能"这一维**——引擎不按技能找人，点了名就派给那个人，没点名到站即「已阻塞」等人指派。
- 四个角色技能只做**本步的活**：产出文档、把结论交回会话。**不再改 `status.yaml` 的 `tasks` 状态**（老账本那段作废），路径也从 `doc_index` 读、不再写死。
- 契约**只有一份**（[docs/契约.md](契约.md)）：进度真相 = **流程实例**；`status.yaml` 只留版本台账（`versions`，面板读它）与文档入口（`doc_index`）。`stage` / `tasks` 是历史遗留，不许再维护。契约随平台走，项目里只留 `status.yaml` 与文档本身。

**2026-10-16 收拾的那一轮**（起因：技能与契约都是流程之前写的，分层没跟上）：

- **内建模板 id 是 `bandi-delivery`**（`workflows.BUILT_IN_TEMPLATE`）：老库里叫 `bandi-flow` 的模板与**实例的 `templateId`** 由 `store.renameWorkflowTemplate` 在启动时一起迁（`smoke-workflows.mjs` ⑧ 钉住）。
- **部署节点补 `manual: true`**：契约一直写着"部署永远要人下令"，代码里五个节点**一个开关都没有**，跑完会自动流转到结束——文档说的和代码做的相反。现在开关在，而且**开关真的管住自动流转**（同冒烟 ⑨⑩）。
- **角色技能的 `description` 不再绑节点名**（原来写"当流程的『写代码』这一步派给你"——用户自定义模板时就不命中了）；**测试的"有权打回"删掉**：引擎里没有给 agent 的 decide 通道，打回是人在实例页点。
- **机器台账收敛**：地址与账号只留平台登记表（`~/.bandi/servers.yaml` ＋ `ssh` 连接器），项目里的机器清单只记"允许谁用 / 能干什么 / 是否已引导"；以前同一台机器三本账各写一遍。
- **契约去掉人名表**（谁挂哪个能力以平台为准；写进文本里就会过期），并标明「三」「四」「五」「六」讲的是**平台行为**、真源在平台，以平台为准。
- **发布记录只有一个落点**：`.bandi/发布记录/v<版本号>.md`；老项目里 `10-需求/30-发布记录/` 是流程之前的位置，历史文件不动、不再新写。
- **契约不再发副本**：那份"一份母本 + 每个项目一份 `.bandi/README.md`"作废——母本只此一份、随平台走，项目里只留 `status.yaml` 与文档。
- 旧参考 `契约详解.md` **删了**：整篇都是历史，而且通篇用**旧五类编号**，留着只会误导。
- **「待开始」并入「待办」，待办即执行**（2026-10-17 对齐 Multica）：实例页那颗「派活，开始这一步」按钮去掉——步骤到站本来就自动派活，派不出去（经办人正忙）退回「待办」，由调度节拍（30 秒一次，`workflows.retryPendingSteps` 挂在 `schedules.tick` 上）自动重派；人手动把步骤改成「待办」也直接派。库里存量的「待开始」行启动时一并迁成「待办」。额度超了→「已阻塞」、真失败→「失败」，这两种照样等人，不会在重试里打转。

- **工单会话：收件箱与执行槽拆开**（2026-10-18）：流程的每一步、看板上的每张卡不再派进员工那条 1:1，各建一条 `kind='exec'` 的**工单会话**（`conversations.execScope` = `wf:<实例id>` / `task:<卡id>`，同一张卡返工续用；`projectId` 也记在会话和 run 上）。1:1 只做人和他的对话；消息模块里工单会话归成「手上的活」一组，默认收起。**并发显式封两道**（`dispatch.mjs`）：每人最多 2 件同时在跑（每条并发一份 token、一个 CLI 进程）；同一项目同一时刻只许一件（两个进程改同一份代码必出事）。撞忙都抛 `busy`：流程退回「待办」由节拍重派，任务卡落 `queuedAt` 排队标记、`schedules.retryQueuedTasks` 每 30 秒先进先出重试。
- **任务卡页改成"评论区"形态**（2026-10-18，对齐 Multica）：**左边是任务 + 评论区，右边是状态与设置**（状态 / 执行人 / 项目 / 来源 / PR；**改动自动保存**，没有「保存」按钮）。评论区**两层**：一条顶层评论 = 一个议题，回复挂在议题下（`messages.parentId`，只一层）；他的回话按触发消息的 parentId 自动归到同一议题（`runs.mjs` 按 `run.watermark` 反查触发消息；顶层评论的回复挂到**评论自己**，不靠时序猜）。会话**按需建**：第一次评论才建工单会话（没有执行人的卡不能发评论）。描述默认只读，点「编辑」才展开表单。老数据（没有 parentId 的回话）退化成"挂在当前议题下"。主聊天页不动 —— 没有载体的对话、单句来回确认，聊天更顺。
- **评论 = 讨论，开工 = 「待办 + 已指定执行人」自动流转**（2026-10-18，用户口径）：普通发送**只叫醒他回这条评论**，**不改卡状态、也不登记 runId** —— 卡在「想法」就还是「想法」，可以在评论区把技术方案/功能/漏洞聊熟；勾「只留言，不叫醒他」= 只记在卡上（对应 Multica 的 `/note`），连 CLI 都不启动。想清楚后把状态改成「待办」并指定执行人，**自动开工**（不用再点「开始工作」；这个按钮和「保存」一起删了）；没指定人只停车，想法阶段不跑。验收：`smoke-task-comments.mjs`。

- **项目页有任务看板**（平台一等功能，不是插件）：**项目 → 点一行进详情**，
  看板列 = 状态，从左到右按生命周期（待办 / 进行中 / 待人确认 / 停下等人 / 失败 / 已完成），
  卡片三种来源：**流程的每一次办理**、**聊天派活**、**手动建的任务**（单独标出来、写明执行人），
  点流程卡进那条实例、点聊天/手工卡进那个会话。
  列头的 **「＋」** 在这一列手工建任务（参照 Multica）：标题/描述/状态/执行人，
  选了执行人可勾「创建后立即开始工作」——那会真的派活（发到他的会话，工作目录是这个项目）。
  手工卡可以**拖到别的列改状态**、点 **×** 删掉；流程与聊天的卡状态归平台管，拖不动。
  **拖进「进行中」＝开工**（2026-10-17 对齐 Multica：状态本身不是触发器，「已指派 + 状态到位」才是）：
  卡上已有执行人，拖进来就走和「保存并开始工作」同一条派活链路；没执行人的卡只改状态、不派活
  （人自己干的活用得上）；派不出去（他正忙 / 运行时不在线）**状态原地不动**，原因原话弹出来 ——
  卡要是留在「进行中」却没跑，看板上就成了假话。
  头上有**「筛选」**（2026-10-15，形状照 Linear 那张）：先做了**状态**一维 —— 只画勾中的状态，
  整列都不匹配就不显示那一列，列内卡片跟着筛；按钮上带选中的个数、旁边写「显示 N / 共 M」，
  弹层里挂「清除」。**2026-10-18 参照 Multica 加到三维：状态 / 负责人 / 项目**（同一维里选多个 = 任选其一，
  不同维之间 = 同时满足，某一维不勾 = 不设限）。负责人按**员工 id** 聚（三种行都带了 `assignee_id`，
  改名不跑、撞名不串），没执行人的合成一行「未指派」；项目那维**只在全局面板出现**（项目看板整块板就是
  一个项目，再筛一遍是废话），没归属的合成「（未归属）」；记着、但这批行里没有的人/项目/状态会补出一行
  张数 0 的幽灵项，保证"角标有数、一个勾都看不见"的怪相不会再出现。建卡弹窗里那句"建完会留在看板外面"
  的提醒也跟着升级：会把**是哪一维**挡住的说出来（状态 / 人 / 项目）。
  **同日又把弹层收成两级**（用户提的"点筛选出一个一级选项单，点击再显示二级选项单"）：
  一级列三个维度，每行自带「勾了几项 + 选了谁」的摘要（名字最多摆两个，再多就「+N」）；
  点一行进二级铺那一维的选项，二级有「返回」和「清除本组」，Esc 也是逐级退（二级 → 一级 → 收起）。

  每行自己把答案写在脸上，层高也稳定。停在哪一级记在 `S.kbPane`，**不进 localStorage**：
  下次点开从一级开始（人想的是"换一维看看"，不是回到上次那一维）。

  换维 / 返回 / 重开弹层都清搜索词，Esc 在搜索框里先清词再退级。状态不搜：就那几个词。

  界面 `openProjectDetail()` / `taskDialog()`。
  聊天没有"选项目"这一步，所以没挂项目的会话按**执行人的工作目录**归属；流程的活也派进
  经办人的 1:1 会话，判定时必须把流程轮次剔掉，否则同一件活会被算两遍。
  旧面板的运维（一键部署、登记部署目标）与「版本状态」**没有搬**，随后跟归档的旧插件一起删掉了（`_archive/` 未随公开仓库发布）——现在是「要发布就让运维在会话里做」。

  全局比项目看板多两件事：卡片上多一枚**「哪个项目」**的标签；**没挂项目的活也收** ——
  流程实例没挂项目的、会话没挂项目又不在任何项目目录下的，都归到「（未归属）」，
  那些活在项目看板里根本看不见（真实数据里这种活不少）。
  聊天行**按会话算、不按项目算**，所以全局里同一场对话只有一张卡（不会因为归属算两遍而重复）。
  列头的「＋」在全局面板要先选项目（手工卡必须挂在某个项目下），右侧那栏**按项目分堆**
  （件数 + 停/待确认/失败），点一行就钻进那个项目的看板。
- **「某个人的任务」**（2026-10-18，为员工详情页铺的路）：`GET /api/personas/{id}/tasks`
  跟全局面板**同一批行**（三源合流抽成了 `allRows()`，`allTasks` / `personaTasks` 共用），
  服务端按 `assignee_id` 筛一遍，返回的形状跟看板一模一样（`board()` 的产物）——
  所以"看板上 3 件、他详情里 2 件"这种对不上的事不会发生。员工详情页的「任务」标签页已接上
  （竖着按生命周期分堆：要人管 / 进行中 / 还没开跑 / 已完成，卡片复用看板那张，只读不拖不删）。

## 四、多机器：节点、机器名、自启、鉴权

- **能接别的机器了（第二步：领活）**（2026-10-15）：**多台电脑一起干活**这条通了。
  控制面**不 push、不开端口** —— 节点**长轮询**领活（挂 20 秒，有活立刻回），在本机起 agent CLI
  （复用同一套适配器），事件**批量回传**、最后报回执；界面看到的实时流就是已经做好的 `run_events`。
  派活就是**员工绑那个运行时的 id**（`node-xxx:codex`，下拉里带机器名），不用另造一套"指派机器"。
  **离线排队**是队列的默认状态：那台机器不在线，活就躺着等它上线自己领走。
  **停止**走反向通道：事件批次的响应里带回 `stop`，节点掐子进程；节点每 2 秒发一个**空批次心跳**，
  所以它一声不吭时也掐得掉。节点掉线由清扫判**中断**（没开张的活则放回队列）。
  `node apps/server/src/smoke-node-jobs.mjs`（24 项，真起控制面 + 真起节点 + 一个确定性假 CLI）。
  **实测跨机走通**：控制面在火山那台，节点在我这台 Windows —— 公网派一句话，活在本机跑完、结果回到公网。
  ⚠️ 已知边界：工作目录是**那台机器上的事实**，两边路径不一样就会明确失败（不做悄悄换目录）；
  排队会**一直等**那台机器回来，要撤就点停止。
- **机器名与主机名分开**（2026-10-16）：设备详情页多了「重命名机器」。大标题是**人给它的名字**
  （如「我的笔记本」），下面小字回**真实主机名**（`DESKTOP-XXXXXXX`）—— 两台机器同名时才分得清谁是谁。
  要紧的是这条：**名字能挺住那台机器的下次报到**（它每次报到都会带自己的主机名上来）。
  所以 `nodes` 表把 `hostname` 与 `label` 分开存，`renamed = 1` 时只更新主机名、不动名字；
  本机那份存在 `runtimes.json` 的 `devices.local.label`。传空 = 恢复成主机名。
  连带好处：运行时在员工下拉里的显示名也跟着变（`Codex CLI（备用机·杭州）`）——
  不改名的话两台机器的条目都叫「Codex CLI」，根本分不出活会落到哪台。
  验收：`node apps/server/src/smoke-node.mjs` 的 ②b（8 项，含"重新报到之后名字还在"）。
- **节点页也有「已安装 / 未安装」**（2026-10-16）：远程节点详情页原来只有一句"一个都没探到"，
  等于**把"该怎么办"藏起来**了 —— 现在按**节点自报的清单**分两段：已装的看着能派活，
  没装的一行一条能直接粘的命令（`npm install -g …`）；dsh 那条在 Linux 上明说"这台机器上装不了"
  （它是 Windows 桌面端自带的 —— 摆一条装不了的命令比不摆更糟）。
  ⚠️ 判断依据是**节点自报**，不是控制面本机的探测：那是两台机器（这条踩过 ——
  云端在 Linux 上，看着笔记本报来的 `D:\…` 全被标成"班底起不来"）。
  另一半：**心跳现在捎带运行时清单** —— 在那台机器上装完 CLI，15 秒内页面自己就变、**不用重启节点**
  （原来只有报到时报，用户看到的是"我明明装了还是没有"）。
- **开机自启成了自带功能**（2026-10-16）：`node apps/server/src/autostart.mjs install|remove|status`。
  Linux 走 `systemd --user` ＋ `loginctl enable-linger`（**开机不必先登录**，崩了自动重启 ——
  实测 `kill -9` 之后 12 秒自己回来）；Windows 走 Startup 里的 `.vbs`（**隐藏窗口**）＋ 带循环的 `.cmd`；
  macOS 走 launchd。**四个坑**（一台机器两个数据目录、启动脚本重定向撞 `EBUSY`、
  生成的脚本必须纯 ASCII、别用 `Start-Process` 起）写在 [deploy/README.md](../deploy/README.md) 第五之二节。
- **部署前置已就绪**（2026-10-15）：`BANDI_DATA` 可指（7 处派生路径一起跟着走，启动日志会把
  数据目录与库路径打出来）；`BANDI_HOST` ＋ `BANDI_ORIGINS` 可配（默认只听本机；**不配来源的话
  远端浏览器能看不能动**）；`db` 不再导出，**SQL 只剩 `store.mjs` 一处**。
  产物：`deploy/bandi.service`（systemd）＋ [deploy/README.md](../deploy/README.md)（SSH 隧道访问、
  节点报到、备份与排障）＋ `start-node.cmd`。（**鉴权**见下一条，2026-10-15 已补上。）
- **访问令牌（鉴权）**（2026-10-15）：规则一条 —— **只看监听地址**：
  只监听回环（桌面版/单机）→ **免鉴权**（保住"单机零配置、不要 token"）；监听非回环（服务器）→
  **所有请求都要令牌**。不按"来源是不是回环"判，因为反向代理会把来源变成回环、把闸绕过去。
  令牌首次自动生成在数据目录的 `token` 里（也可用 `BANDI_TOKEN` 指定、不落盘）；
  浏览器填一次记进 HttpOnly Cookie（`EventSource` 没法自己设头，Cookie 是它唯一的活路），
  节点/脚本用 `X-Bandi-Token` 头。**实测已部署到那台火山机器上**：外网不带令牌 401、首页是登录页、
  带令牌 200、令牌错了 401。见 [deploy/README.md](../deploy/README.md) 第六节。

  见 [apps/desktop/README.md](../apps/desktop/README.md)。

  硬编码端口的桌面版，在"用户机器上恰好有别的程序占着"时只剩一张错误页。
  实测：占用 8821 → 它跳到 8822 起，**没碰别人的进程**；再开一个壳 → 复用 8822 且退出不停它。

## 六、插件机制的一处扩展（2026-10-14）

声明式 `table` 块支持给列写 `width`（如 `"72px"`）：任意一列写了，整张表切
`table-layout: fixed`，没写的列平分剩下的。起因是 `auto` 布局下中文**每个字都能断行**，
「要点」「证据」这种长文本列会把「编号」「状态」压到一两个字宽——`T-001` 断成两行、
`待部署` 竖排。契约写在 [apps/server/src/plugins.mjs](../apps/server/src/plugins.mjs) 的块注释里。

**两种版式块（2026-10-24，研发面板概览稿）**：`stats`（一行数字卡，聚合靠项上的 `calc`
声明：`count` / `countIf` / `sum` / `sumIf`，**口径写在 manifest 里，宿主只提供算子**）
与 `cards`（卡片网格，`columns` 定列数、`card.href` 只挂 `data-card-href` 不导航）。
任何块都能加 `aside: true`（只支持 cards / list）挂进右栏 —— 加了之后整页变成
「通栏的开头 text/stats + 主列 1fr + 右栏 340px」。`source` 上另有 `filter` / `sort` / `limit`
三个通用修饰，模板里可用 `{shown_count}` / `{total_count}` / `{count}`。
纯整形逻辑在 [apps/web/js/plugin-data.mjs](../apps/web/js/plugin-data.mjs)（不碰 DOM，可单测），
验收用例 `smoke-plugin-blocks.mjs`。老块的 DOM 与样式一律没动。

## 七、版本与台账

**当前版本 `1.2.0`**，真源唯一：[apps/desktop/version.json](../apps/desktop/version.json)。
`build.rs` 读它 → 编译进程序（窗口标题「班底 <版本>」）→ 同步写进 `tauri.conf.json`（安装包名）。
**别在别处记第二个号**；`build.rs` 只认三段数字，`1.2.0-rc.1` 这种后缀会让构建直接失败。

**号已经走到 `1.2.0`，但兼容承诺还没给**：`1.0.0` 是 2026-10-10 给「插件 → 桌面安装程序」那次形变的号，那一版只做
「外壳 + 打包」与「**SSH 服务器登记**」，而 SSH 优先那条路已经停了（见上「五、桌面壳与安装包」里的「已停」）；
2026-10-16 一度把对外口径压回 `0.9.0`（`0.y.z` = 不承诺兼容），可 `version.json` 那条线一直在往前走
（`1.0.0` → `1.1.0` → `1.2.0`），两套号并记到 2026-10-25 才统一回真源。
插件格式、流程模板、`status.yaml` 契约都还在动，所以**「不承诺兼容」这条继续有效**，跟号是 `1.x` 并不矛盾。
本文件别处出现的 `0.9.0` / `1.0.0`（窗口标题、安装包名、`v1.0.0` 的 B2/B5/B6 那些约束编号）都是**当时那一版的记录**，不是当前版本。

**插件与 MCP 身份是另一套号**：`plugins/*/manifest.json` 与 MCP 的 `serverInfo` / `clientInfo`
里写的 `0.1.0` 是**插件 / MCP 协议身份**，不跟产品版本走 —— 问「现在几版」只看上面那个真源。

**发版的号从哪来**：改 `apps/desktop/version.json` → 提交 → 打 `v<版本>` tag 推上去，
CI 自动出安装包并挂 Release（tag 与 version.json 不一致会直接失败）。

历史台账（本仓库自己的 `.bandi/status.yaml`）：`0.1.0` ~ `0.7.0` 是**插件时代**的版本
（最后真正发布过的是 `0.7.0`），`0.8.0` 与 `1.0.0` **从未发布**。

## 九、仓库值班（2026-10-17）

外部进来的东西（issue / PR / 评论）要有人看、有人判、有人回。这一版先落**闸门 ＋ 手册 ＋ 台账**三样，

## 十、岗位（2026-10-17）

**一个人"是什么"和"会干什么"是两件事**（用户提的，理由很直给：开发也能挂运维技能、也能干仓库管理员，
但在"写代码"这张卡上，我要找的是**开发**，不该一个个去翻他挂了哪些技能）。

- **数据**：`personas.role`，一个值、可空、自由文本（`ensureColumn`，老库自动补列）。
  **不锁枚举** —— 组织会变（"架构""队长""仓库值班"都可能冒出来），锁死就得改代码。
- **界面**：新建/编辑员工能填（给建议列表 `产品/研发/测试/运维/架构/设计/项目`）；
  通讯录那一行的副标题从 `runtime · sandbox` 换成 `岗位 · runtime`（没填岗位就退回只显示 runtime）；
  员工详情名字旁一枚岗位胶囊；**四处人员下拉**（流程编排节点经办人、实例页改派、任务卡执行人、群助手）
  显示成 `研发 · 波哥`。
- **红线**：**引擎不读岗位** —— 派活仍只认节点上点的名。这条写在契约「十、谁管什么」里，
  并由 [`smoke-personas.mjs`](../apps/server/src/smoke-personas.mjs) 钉住（点名谁就是谁、
  没点名不会按岗位顶人、阻塞原因里也不提岗位）。
- **和技能的分工**：技能＝会干什么（可多、能挂能摘，跟着能力包升级）；岗位＝主职（一个、给人看）。
  两者允许不一致，界面不做校验 —— 不制造第二份真相。


## 十一、代码托管（GitHub 仓库，2026-10-17）

用户：「我想要他这个代码托管的模块，因为我有很多个 git 仓库」。形态**不是**把每个仓库硬变成一个项目，
而是**仓库是一等资源**，项目 / 任务卡引用它。

- **设置 → 代码托管**：填 fine-grained PAT 连接 GitHub → 列出账号下的仓库（按最近更新）
  → 挑仓库「接入」＝克隆到 `<数据目录>/repos/<owner>__<name>` → 可「同步」（git pull --ff-only）、
  「建成项目」（项目 root 就是克隆目录）、「移除」（只删记录，本地目录保留）。
- **加仓库只有一个入口**（2026-10-17）：「代码仓库」标题上的「＋ 添加仓库」→ 菜单里两条路
  ——「从 GitHub 添加」（`openGitPickDialog`，从账号里挑）/「手动接入」（`openGitManualDialog`，
  本地已有克隆、私有仓库、离线），**各自开弹窗**操作。
  原来「＋ 手动接入」在标题上、「从 GitHub 添加」是页面**底部常驻的另外一整块**：两条路分在两处，
  人得先想"我现在该点哪个"；而那块清单只在要加仓库那一刻才用得上，平时是噪音，
  还跟上面的「代码仓库」清单看着像两个东西。现在页面只剩一张清单。
  **「从 GitHub 添加」里是"先挑、再确认"**（2026-10-17）：行是**选中**（`.sk-row.pickable`），
  「接入」在弹窗底部、跟「取消」并排，没选中时禁用。原来是每行一颗「接入」按钮、点了立刻克隆 ——
  一张几十个仓库的清单里手一抖点错行，就得等它克隆完再删。已接入的行看得见、选不了。
  顺带修了 `openAddMenu`：**锚点不在左栏页头里时菜单跟着按钮走**（原来 CSS 写死
  `top: calc(100% - 4px)`，主区那颗 ＋ 会让菜单浮在按钮上方老远）。
- **「怎么拿令牌」这份说明只挂一处（`GIT_TOKEN_HELP`）**：「GitHub 连接」标题旁那颗「?」点开
  （`wireHelpPop`）。**不在令牌输入框下面再贴一份** —— 那等于同一段话出现两次，
  而且连上之后表单没了、只剩「?」，那份反而多余。
  放「?」里是因为它**连上与没连上时都在**：而"给下一个仓库补授权""令牌 90 天到期要换"
  恰恰是**连着的时候**才要照着做。
- **连上与没连上是同一个骨架**（2026-10-17）：都是「令牌」那一行（左标签 + 右输入框 + 按钮），
  连上之后只改三处 —— 输入框变只读（只回显掩码，`.locked`）、按钮换成「断开连接」、
  「已连接 @xxx」写在输入框下面。原来连上后换成「状态：已连接 + 断开连接」那套行，
  整块高度和样子都变了（用户："连接之后这个区域的变化不要太大"）。
  验收：`tools/smoke-help-pop.mjs`（55 项，离线：两个状态同骨架 / 只读框 / 状态写在框下面 / 一个入口两条路 / 底部不再常驻 / 先挑再确认 /「接入」在「取消」旁 /
  「?」只挂一处 / 展开 / 再点收 / 点别处收 / Esc 收 / 点弹出层里不收）。
- **表**：`git_repos`（fullName/owner/name/isPrivate/defaultBranch/localPath/language/addedAt/lastSyncAt）。
  **令牌不进库**：单独一个 `<数据目录>/github-token` 文件（0600 尽力），只在 `git-repos.mjs` 里读写。
- **界面只回显「头 2 位 + `******` + 尾 4 位」**（`git-repos.tokenHint()`，2026-10-17）。
  原来只有尾 4 位 —— 一个 GitHub 账号下往往建了**好几个** fine-grained PAT（不同仓库、不同权限），
  90 天到期要换时"当前挂着的是哪一个"才是要回答的问题，尾 4 位区分不开。
  `****` **固定 6 个、不按令牌真实长度变**：长度本身是信息（变长变短等于在报它有多长），
  而且每次换令牌界面都会抖一下。短于 10 位的令牌**一个字都不给** —— 头尾加起来就快露完了，
  那已经不叫掩码。
- **令牌的用法**：克隆/拉取用 `http.extraheader` 把令牌带在**请求头**里 —— `.git/config` 里不写带令牌的 URL
  （那是最常见的泄漏方式）。
- **agent 的环境隔离**：`git-repos.agentEnv()` 把 `GIT_*` / `GCM_*` / `GH_TOKEN` / `GITHUB_TOKEN` 全删掉，
  强制 `GIT_TERMINAL_PROMPT=0`，三个 adapter（codex / dsh / claude）起进程都改用它。
  说清边界：Windows 凭据管理器是"同用户任何进程都能读"，这只能把最容易的路堵上，**不是完整沙箱**
  （真要隔离得换用户/容器跑）。
- **PR 联动（v1，只读，2026-10-17）**：卡上贴一个 PR 链接（或 `owner/name#123`）就挂上关系 ——
  平台拿令牌去 GitHub 查一次，把 `prRepo/prNumber/prState/prTitle/prCheckedAt` 存进卡里；
  看板卡片上多一枚「PR #n 开着 / 已合并 / 已关闭」小标签（`prPillOf`），详情页有完整信息。
  **合并后只把「进行中」收成「待确认」**（`afterMerged`）—— 合并 ≠ 验收通过，卡的状态是人给的指令：
  已完成的别覆盖、别的列一律不动；「待办」的值班卡合并了也留在原列，等人自己收。
  **状态不会自己保鲜**（GitHub 那边合了平台不知道），所以有两条刷新路：卡详情页「刷新状态」（一张），
  看板工具栏「刷新 PR（n）」（一次查完本板所有关联卡，`POST /api/git/prs/refresh?projectId=`，上限 50 张）；
  一张都没关联时这颗按钮**留着但禁用**，title 里写清"先在某张卡的详情里贴 PR 链接" ——
  藏起来的话，人只会问"为什么我的卡不动"。
  **仓库值班的 PR 卡也带**：巡检（`tools/repo-scan.mjs`）把 `pr: { url, title, state }` 一起报上来，
  `POST /api/projects/:id/repo-cards` 归成同样的五个字段（`git-repos.prFieldsOf`）——
  扫进来的卡同样有标签、同样进得了「刷新 PR」的清单；报的是 merged 且卡在「进行中」，同样收成「待确认」。
  边界：只认 `project_tasks` 里的卡（手动 / 仓库值班）；**流程卡与聊天卡挂不了 PR**，
  它们的状态归流程引擎与运行结果管。
- **没做**：PR 侧栏（在平台里读 diff / 评论）／Co-authored-by 署名／平台内关闭（驳回）别人的 PR；
  GitHub OAuth 连接（当前用 PAT：多仓库按需授权、权限最小，代价是 90 天要换）。
  ~~从平台发起合并~~ 已于 2026-10-23（§十四 流程动作节点）与 2026-10-25（§十七 手动按钮）落地，
  「建 PR」也于 2026-10-25 落地 —— 本节这段只讲读侧那批老账，写侧见 §十四、§十七。
- 验收：`smoke-git-repos.mjs`（45 项，离线：状态诚实、空令牌 400、令牌不进库不回显、agent 环境被清干净、
  值班写卡带 PR / 幂等 / merged 归一）；
  `smoke-pr-link.mjs`（28 项，离线：PR 引用解析、五个字段落库、状态机只动「进行中」、解绑清空、巡检形状归一）。

## 十二、定时任务（2026-10-17）

起因是「别人提了个 PR，我能看到吗」：答案是**看不见** —— 那时候唯一的入口是手动跑
`tools/repo-scan.mjs`，不跑就永远不知道。要让它自己看，节拍就不该写死在某个脚本里，
所以**先有调度器、再有巡检**：

- **一张表 `schedule_jobs`**：名称 / 动作 / **重复方式** / 开关 / `config`（JSON，动作自己解释）/
  `lastRunAt` / `lastStatus` / `lastError` / `lastSummary`。重复方式七选一（2026-10-17 晚，
  对齐 WorkBuddy 自己的定时任务弹窗）：**间隔（每 N 分钟）/ 单次（到点只跑一次）/ 每天 / 每周 /
  每双周 / 每月 / 每年**，时间类都带「几点」（每周/每双周还有星期几、每月有几号、每年有月份）。
  不存 cron —— Windows 上没有 cron，装解析器又违背零依赖；「每周一 09:00」人一眼就懂。
  老库自动迁移：旧行归成 interval，语义不变。
  `lastRunAt` 不只是给人看：**下次该不该跑由它算**，服务重启后天然接上，不另存 nextRunAt。
  到点判定要点：时间类到的是「锚点（上次/建任务时间）之后的下一个整点」，不是"距上次满 24 小时"；
  单次跑过一次就永远不再跑；双周的"隔一周"只约束跑过的两次之间，第一次该哪天就哪天；
  「每月 31 号」在 11 月自动落 11-30（按当月天数收，不全局钳 28）。
- **动作注册表**（`schedules.mjs` 的 `ACTIONS`，2026-10-17 晚通用化）：加一个动作 = 加一条，
  **调度核心与弹窗都不用动**。动作**自己声明参数**（`fields`：repo / project / number / text），
  界面照声明渲染 —— 所以「仓库 / 项目」只是 PR 巡检自己的参数，不是弹窗写死的下拉。
  现在两个动作：`pr-scan`（PR / Issue 巡检）和 `backup-db`（备份数据库，`VACUUM INTO`
  导出一致快照到数据目录的 `backups/`，只留最近 N 份 —— 跟 PR 无关，证明骨架通用）。
  `actionCatalogue()` 下发 `{id, label, hint, defaultName, fields}`，不发 `run`。
- **运行器**：30 秒一跳（`unref`，不拖住进程），挑**到点的、启用的**，**串行**跑，跑完写回结果。
  四条刻意的取舍：① 串行 —— 同时跑几个只是把时间烧在同一个速率上限上；
  ② **不补跑** —— 重启后错过了就等下一个间隔，补跑会在开机时把积压任务一次全放出来；
  ③ **间隔类从没跑过的立刻跑** —— 人刚建完就该看到结果，不该等半小时；时间类的等到第一个整点
  （周六 14:00 建「每天 09:00」，当天不该跑，因为 09:00 已经过去了）；
  ④ **失败也写 `lastRunAt`** —— 否则一个一直失败的任务每 30 秒重试一次，把日志刷满。
- **界面**：设置 → 「定时任务」。列表一行一个任务：名称 / 动作 / **什么时候跑（一句话）** /
  上次什么时候 / **结果原话**（成功写结论、失败写原因）/ 立即跑 / 编辑 / 停用 / 删除；
  单次任务跑完标「已完成」。新建/编辑弹窗照 WorkBuddy 的样子：**重复**下拉七选一，
  选中哪种出哪种字段（间隔给分钟数、单次给日期时间、每天给几点、每周/每双周给星期几+几点…）。
  间隔下限 5 分钟（`MIN_MINUTES`，接口与界面各拦一次）；弹窗可以限定**某个仓库**
  和**卡片落到哪个项目**（都留空 = 所有已接入仓库、落到"项目根 == 克隆目录"的那个项目，
  对不上落内置默认项目）。「立即跑」不等到点也不看开关 —— 要的是"现在到底行不行"这个答案。
- **PR 巡检这一件事，两半缺一不可**：① 每个仓库的 open PR / issue → 值班卡
  （`upsertRepoCard` 去重，**绝不覆盖人拖过的状态**）；② 已经关联了 PR 的卡逐张再查一次 ——
  PR 合并后不会再出现在 open 列表里，**只有这一半**能把卡从「开着」改成「已合并」并收成「待确认」。
  只读：不评论、不合、不改分支。
- **与手动脚本的关系**：`tools/repo-scan.mjs` 还在（临时扫一次、`--dry` 看会写什么）；
  但它不带令牌（只公开仓库）、一次一个仓库、每次都要人记得跑 —— 常态应该交给定时任务。
- 边界：只在**控制面进程活着**的时候跑（桌面版就是"班底开着"）；不做通用的「跑一条命令」动作
  —— 那需要先想清沙箱与权限边界。
- 验收：`smoke-schedules.mjs`（98 项，离线：到点判定（间隔 + 单次/每天/每周/每双周/每月/每年，
  全部本地时间钉死）/ 开关 / 串行 tick / 失败记账 / 不认识的动作 / "说人话"文案 /
  动作注册表（声明式 fields、清单里没有 run）/ 备份动作（VACUUM INTO 一致快照、保留份数清理、
  文件头是 SQLite）/ 假 fetch 喂 GitHub 验 PR 巡检写卡与合并收状态 / HTTP 校验与立即跑）。

## 十三、数据目录收敛成一个默认（2026-10-18）

复评的起因：命令行默认落 `<仓库>/data`、桌面壳默认落 `%APPDATA%\bandi` —— 同一台机器两个库，
而「开发版别碰真实数据」这条并没有成立（开发壳连的就是真实库）。两个默认是不同时间点各定的，
没有统一原则，只剩「看错库」这一类问题。

- **默认收敛成一个**：`apps/server/src/data-dir.mjs` 的 `userDataDir()`（Windows `%APPDATA%\bandi`、
  macOS `~/Library/Application Support/bandi`、Linux `$XDG_DATA_HOME/bandi`）。命令行（`start.mjs`）、
  桌面壳（`shell.mjs`，开发版/安装版一样）、服务端（`config.mjs`）都 import 它 —— 不再各写一份。
- `<仓库>/data` 仍能用，但只是**显式沙盒**：`BANDI_DATA=<仓库>/data`；测试/临时库同理（smoke 全都这么干）。
- 服务器部署不变：systemd 单元显式 `BANDI_DATA=/var/lib/bandi`。
- 启动日志把数据目录打出来（`start.mjs` 也补了一行），`shell.log` 每次启动第一行就是它 ——「我在看哪个库」不靠猜。
- 验收：`smoke-data-dir.mjs` 加 ⓪ 两项 —— 不设 `BANDI_DATA` 时默认 = 用户目录、且不是 `<仓库>/data`。

## 十四、PR 审阅与授权合并（2026-10-23）

起因是用户那句话：「别人提交了一个 pr，仓库管理员帮我去检查，告诉我这个 pr 干了什么东西、
有没有风险、是不是垃圾。我来做决策。」以及「我不想看什么 diff，想看 diff 我直接去 github，
不要重复造轮子」。设计文档在 [PRD-2026-10-23-PR审阅与授权合并.md](PRD-2026-10-23-PR审阅与授权合并.md)。

**这一版把上一节（仓库值班）的最后一块补上了**：之前巡检只把 PR 写成"待审"卡，
判断与合并都在人身上；现在卡上多一段管理员结论，合并也可能由平台执行 —— 但**放行权始终在人手里**。

- **仓库 ↔ 管理员绑定**（`git_repos.keeperPersonaId` + `autoMerge`）：绑在仓库上不绑在人身上
  （巡检/审阅/合并都按仓库发起）。界面在「设置 → 代码托管」每个仓库行第二行：管理员下拉 + 自动合并勾选，
  改了就存（`POST /api/git/repos/:id/settings`，PATCH 语义）。**默认没绑、授权关闭** ——
  没绑时行为与 2026-10-17 的巡检**一字不差**。
- **审阅流程 = 内建流程模板**（`pr-review`，`pr-review.mjs`）：审阅（管理员）→ 合并（平台动作）。
  **不造第二套状态机** —— 用户 2026-10-23 明确要求复用流程编排的「等人确认」：
  授权 = 合并节点前是否停下等人，随时收放；已停在确认点的实例等人点，**状态不回跳**。
- **新改动才审**：按 `head.sha` 判定（meta `prseen:{repo}#{n}`，跨重启），PR 改描述不算新、
  推新提交才算。巡检便宜（一两次 API）、审阅才花钱 —— 两者频率解耦，默认每天 2 次可调。
  草稿 PR、没绑管理员的仓库只记 sha 不审。
- **管理员只给建议**：四段结论（干了什么 / 改了哪里 / 风险 / ✅值得合·🗑️垃圾·⚠️拿不准），
  「拿不准」必须明说、指出人该看哪里。**令牌不进 agent 手里** —— 合并由服务端执行
  （`pr-merge` 动作节点），沿用 `agentEnv()` 清 GIT_* 的隔离哲学。
- **动作节点（引擎新概念）**：原来每个节点都是"派给一个数字员工去聊"，但调 GitHub 合并 API
  干活的是平台自己。引擎加了 `node.action` + `registerActionNode`（`workflows.mjs`）：
  到站执行、没经办人**不标阻塞**、人点「通过」= 授权执行（`onDecide` 钩子），
  收尾仍走 `finishActionTask → goto` 这一条单行道。
- **合并判定表**（顺序固定）：🗑️垃圾 → 终止实例、**不进「待人确认」列**；⚠️拿不准 → 永远等人；

    流程动作节点 `pr-create` 复用它（2026-10-25 已接上，见 §十八）。
- **三道闸摆在写操作之前**（推上去收不回来，这是这节的重点）：
  ① **只往新分支提**，分支名默认 `bandi/<标题的 ASCII 短串>-<时间戳>`（规则只在服务端一处），

## 十八、PR 交付流程：开发完成 → 建 PR → 审阅 → 合并（2026-10-25）

用户：「本地写的代码，我让仓库管家提交代码的时候，能自动建 PR、推送到服务端、并且能合并 PR，
实现全自动……或者我自己点按钮提交、建 PR。」按钮那一半见 §十七；这一节补的是**流程那一半** ——
开发节点干完不能自动落到 PR 上，自动合并也只能等巡检下一轮碰运气，两条路一直没被串起来。

- **动作节点 `pr-create`**（`pr-create.mjs`，引擎 import 时注册）：
  复用 `git-repos.openPr()`（提交/推送/查重/凭据闸都在里面，与按钮那条路是**同一个函数**，
  不写第二份"怎么建 PR"）。成功后做四件事：
  ① PR 编号写回这条流程（`workflow_runs.prRepo/prNumber`，合并节点只认它，不认"模板里第几个节点"）；
  ② 在项目看板写一张 `pr:<n>` 值班卡（与巡检同一套去重键，审阅结论/合并状态都落在它上面）；
  ③ 把审阅材料写进**下一步**（审阅节点）的 `detail` —— 员工手里没有令牌，材料必须平台给；
  ④ 按仓库 `keeperPersonaId` 自动指派审阅（仓库没绑管理员就留「已阻塞」并写明去哪补）。
  **重试不建第二个 PR**：run 上已经有编号就沿用（上一次可能只是收尾那几步挂了）。
- **内建模板 `bandi-pr`「开发完成 → 建 PR → 审阅 → 合并」**（四个节点）：
  「开发完成」「审阅」都是普通节点、**不点名**（与内建交付流程同一个规矩：技能是"这个人会干什么"，
  不是"这一步该谁办"）；「建 PR」「合并」是动作节点。第一次建出来**自动发布**
  （发布过的才在建任务时可选；工作台上的发起磁贴已于 2026-10-26 去掉）；
  用户改过连线/点名就不覆盖（`ensurePrDeliveryTemplate` 只补 detail 与坐标）。
- **审阅与合并零重复**：审阅提示词用 `pr-review.REVIEW_DETAIL`，材料用 `pullReviewMaterial()`
  （与巡检派审阅同一份），合并直接用 `pr-merge`（判定表、四闸、SHA 锁、人点「通过」的语义全不动）。
  `reviewTextOf` 原来写死"审阅节点 id = n1"；现在改成**按时间倒着找最近一份有 result 的办理** ——
  模板怎么改名/换 id，合并都只认"上一个办完的人说了什么"。
- **引擎修复（关键，2026-10-25）**：`goto` 与 `retryPendingSteps` 原来只认"有经办人"才开跑，
  而动作节点**故意没有经办人** —— 于是流程走到中间的动作节点永远停在「待办」，30 秒节拍也不补。
  2026-10-23 动作节点上线时没露出来，因为合并节点要么人点、要么用例手动 `start`；一到"审阅完成
  自动进合并"就断路。现在判据是 `node.action`（与 `createTask` 里"动作节点不标阻塞"同一条）。
- **SHA 锁修正（2026-10-25）**：自动合并原来拿的是**合并那一刻重新 fetch 到的** headSha，
  等于"锁了个寂寞"—— 审阅期间有人推新提交，新 sha 既对得上又没人看过。现在 `startPrReview`
  与 `pr-create` 都调 `rememberReviewedSha()` 把**审阅时的** headSha 记在 meta `prreview:<runId>`，
  `runMergeNode` 只认它；有人推了新提交 → GitHub 回 409 → 这一步失败等人重看，PR 不合。
- **合并后本地自动收尾 + 「回 main」按钮（2026-10-25）**：PR 是在 GitHub 上合的，本地克隆不会自己变 ——
  不收尾，人还停在已合并的源分支上、本地 main 也是旧的，下一个任务从旧代码开始（用户实问
  「合并完还要自己切回 main、拉更新，能不能集成到平台」）。现在自动合并（`pr-review.doMerge`）
  与手动合并（`routes/git.mjs` 的 `mergeOne`）都调 `git.settleAfterMerge`：
  当前停在 PR 源分支且工作区干净 → 切回 base → `pull --ff-only origin <base>` → 删本地 `bandi/`
  源分支（只删 HEAD 与 PR headSha **完全一致**的，有本地独有提交就留着）。工作区脏 / 人在别的分支 /
  切回失败 → **不动**，原因原话带回（合并返回的 `local` 字段 + 合并备注）。
  仓库行另加一颗「回 base」按钮（`POST /api/git/repos/:id/back`），给"在 GitHub 网页上直接合了"
  兜底；它没有 PR 的 headSha 可对，所以删分支走 `git branch -d`（git 自己再检查一次已合并）。
- **怎么用**：在任务看板建一张卡、「执行方式」选「由流程执行」并挑「开发完成 → 建 PR → 审阅 → 合并」
  （选的项目就是卡挂的项目）；「开发完成」
  指派研发（也可以自己办）→ 之后平台自动提交推送、开 PR、把材料交给仓库管理员 →
  结论「值得合」+ CI 全绿 + 不碰敏感文件 + ≤400 行，且仓库勾了「自动合并」→ 自动合；
  否则停在这一步等人点「通过」（点通过才合，驳回不合）。「开发完成」的 detail 里写明了
  **建 PR 会把项目目录所有未提交改动收进一个提交**，动手前先把工作区收拾干净。
- **验收**：`smoke-pr-review.mjs` ⑩（模板四节点 / 共用审阅提示词 / 首次即发布 / 动作节点
  到站自动跑 + 节拍补跑 / 审阅 SHA 记忆）；`smoke-pr-create.mjs` ⑪（真 git + 假 GitHub 整条链：
  研发交付 → 自动建 PR → 编号/材料/值班卡 → 审阅完成 → 四闸全过自动合 → 卡变 merged；
  反证：审阅后被推新提交 → 409 停下、PR 仍是 open）；另加收尾 4 项（切回 base + 拉 + 删本地分支、
  脏工作区不动）+ ⑧⑩⑪ 各验一次"合并后本地切回 base" + `POST /back`。
- **2026-10-25 两次实报的两个路径 bug（已修，回归在 `smoke-pr-create` ②③）**：
  ① `git status -z` 的输出**不能 trim** —— 第一条记录可以以空格开头（` M ...`），trim 后整条错位，
  路径首字母被切掉（弹窗把 `apps/...` 显示成 `pps/...`，`git add` 报 pathspec 不存在）；
  ② 已暂存的**重命名/删除**不能把旧路径传给 `git add` —— 旧路径已经不在工作区，会 fatal
  `pathspec ... did not match any files`。未暂存的重命名（` R`）反过来必须把旧路径一起带上。
- **没做 / 边界**：跨 fork 建 PR 仍不支持（`head` 要 `user:branch`）；模板被改到审阅节点不再是
  `n3` 时，平台不硬塞材料、不自动指派（留给人，不猜）；「开发完成」不自动点名（谁来做是人定的）；
  「审阅」也保持不点名 —— 它由仓库绑的管理员自动接，**给审阅节点点名会让引擎在材料写进那一步之前
  就派活**（默认模板故意留空）；建 PR 前不跑 `tools/check-pr.mjs`（那是本仓库的闸门，接入仓库不一定有）。
