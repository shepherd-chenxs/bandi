# 身份与职责检修（2026-11-09）

> 一次针对「数字员工不好用」的全面检修记录：体检数据、根因、目标架构、已落地改造与验收口径。
> 这是**决策快照**：写的是 2026-11-09 这轮定的方向，不回写历史文档；活文档（README / 契约 / 架构）里提到机制时以代码为准。

## 一、结论（先给判断）

身份/职责设定**本身有价值**（派活时认人、口吻、专长排序），但当前用法是反作用的：
它成了模型上下文里**唯一的长期行为法**，而真正该每轮生效的 **任务合同 + 行为契约** 缺位。
所以员工越聊越像「按人设表演」，而不是「按这次要什么交付」。检修方向不是删身份，而是
**把身份缩到只回答「我是谁」，把行为规则和本轮验收拿回平台、每轮注入**。

## 二、体检基线（2026-11-09，真实库）

## 三、根因

1. **时机错**：身份与技能只在首轮注入；长会话里被历史冲淡，平台规则（宪法/汇报口径）也只首轮出现。
2. **越权**：「只管 / 别揽 / 流程怎么做」被写进身份——与任务冲突时，模型按身份演，不按任务交付。
3. **缺省无契约**：默认形态下每轮除用户消息没有任何平台约束，输出形态由模型默认（技术报告体）决定。
4. **激励错**：验收看「有没有证据/结果」，不看「雇主 3 秒能否拍板」→ 员工学会堆数据 + `Next:` 收尾。

## 四、目标架构（四层，各管一件事）

| 层 | 谁维护 | 注入时机 | 内容 |
| --- | --- | --- | --- |
| L0 平台行为契约 | 平台代码 | **每轮**、声明优先级高于身份 | 一屏简报、≤3 条依据、证据去处、`Next:` 禁令、不编数、红线拍板 |
| L1 任务合同 | 平台从卡/流程/项目拼 | **每轮** | 目标、项目、流程节点与本步要求、受众、交付、验收 |
| L2 身份卡 | 出厂专家包，可编辑 | 首轮 | 名字、岗位、3 条擅长、口吻（≤200 字，**不写边界/流程/禁令**） |
| L3 能力包（技能） | 技能库 | 首轮给清单、正文按需读 | 怎么干的方法（TDD / 排障 / 验证…），不承担职责边界 |

岗位/角色只用于展示与人工点名，**不参与行为约束**（`docs/契约.md` §十的口径不变）。

### P3b（本版）

- **把"问进度"的度收住**：P3a 上线后实测——同一问题重启后，马超第 12 秒的思考里已经写着
  「`pt-a6841a5b` 待验收」，却继续跑了 60 秒找部署细节：猜 `/api/runs?conversation_id=…`
  （该接口不存在）、`/api/conversations/...`（403）、翻 `.workbuddy` 记忆与仓库文档，
  期间翻到的是 **thinkpad / 192.168.5.19 的旧部署**（跟卡上"阿里云"不一致），但一直没回话。
  结论：**信息不是瓶颈，口径才是**。平台契约补三条：
  1. **问「进度/怎么样了」只答台账**：状态 + 更新时间 + 在等谁/下一步，不追部署日志与验证细节；
  2. **够答即回**：能回答就先回，别为"更完整"继续翻（用户只能干等）；
  3. **不猜接口**：只用已知接口，试不通就直说"不存在/没权限"，别 `foreach` 试一串路径。
- 冒烟同步钉住这三条（纯文本断言，和契约同源）。

### P4（本版）：交付声明协议 —— 跑完 ≠ 完成

- **真实事故**：任务卡 `pt-a6841a5b`（「爻鉴部署」）的运行 `r-551f01e3` 19:17 **正常退出（exit 0）**
  但最终回话**为空**；平台 `onTaskRunFinished` 把「运行结束」当成「干完了」，自动把卡推进
  「待验收」——**替员工宣布交付、替雇主宣布验收通过**（用户原话：「这是糊弄用户」）。
  20:00 核实：服务器上**没有任何服务在运行**，卡上「已部署」的结论从未发生。
- **根因**：落点规则只看**进程状态**（完成 / 已停止 / 失败），不看**员工有没有交回结论**。
  进程正常退出只说明它跑完了，不说明活干成了；没有交付声明时，平台不该替人猜。
- **修法**：新增 `apps/server/src/delivery-claim.mjs`，解析回话的**交付声明**——只认**第一个非空行**：
  `[完成]` = 声明交付；`[受阻]` = 声明没干成 / 要拍板；两者都没有（含空回话、纯空白、
  标记在第二行）= 没交回可验收结论。落点（`onTaskRunFinished` 与 `promoteConversationToCard`
  同一套折法，仍只动「进行中」的卡、不覆盖人的指令）：
  - 完成 + 第一行 `[完成]` → **待验收**；
  - 完成 + 第一行 `[受阻]` → **已阻塞**；
  - 完成 + 无标记 / 空回话 → **已阻塞**，描述如实写「运行结束但没有交回可验收的结论」，
    不再出现「跑完了，等你验收」；
  - `已停止` → 已阻塞、`失败` → 失败（原样不动）。
  平台契约补第 10 条：**跑完 ≠ 完成**；办任务卡时收尾第一行写 `[完成]` 或 `[受阻] 原因`，
  平台只按第一行判**卡**的状态，不写标记不算交回结论、不进「待验收」（流程步骤沿用原
  `[受阻]` 协议，这一行标记同样算数）；不许把没做完说成完成、替雇主宣布验收通过。
- **边界**：工作流引擎的**节点流转逻辑本次不动**（`onAgentRunFinished` 照旧；员工自报受阻早已由
  `blockedMark` 兜住，见 `smoke-workflows` ⑬）；PR 合并后 `afterMerged` 仍照旧把卡推进「待验收」——
  合并是**可核证据**，跟"我回话说我干完了"不是一回事。
- **冒烟**：`smoke-task-run-sync`（[完成] / [受阻] / 空回话 / 纯空白 / 无标记 / 第二行标记六个落点）、
  `smoke-persona-contract`（平台契约含 `[完成]`、`[受阻]`、跑完 ≠ 完成）、
  `smoke-workflows`（`resultOf` 摘要剥掉 `[完成]` 前缀）。

### P5（本版）：交付形态检修 —— 别把问答题派成工作报告

- **真实事故**：任务卡 `pt-7c6d4229`（「数字员工的权限问题」）问的是「API 权限归谁 / 是给特定
  数字员工还是全员平权」——一个**问答题**；李俊交回的是一篇「运行钥匙怎么发」的**工作报告**，
  还带 4 处事实错。答案没给，问题没答，读的人依然不知道"归谁"。
- **根因**（四层叠起来的）：
  1. 平台契约第 1 条把所有任务都派成「做事 + 一屏简报」——问答题也被塞进"结论先行 + 3 条依据"
     的做事模板，模型只好拿一篇工作汇报顶替答案；
  2. 看板派活不带卡合同，模型的"这一轮要交什么"只剩身份与任务名可循；
  3. 身份 / 技能被当成任务模式：研发岗默认"去干活"，而不是"先审题"；
  4. 没有任何"审题 / 拆问 / 每个判断落源"的纪律——多问不拆、判断不指来源，就只剩复述过程。
- **修法**：
  - `platformContractBlock()` 重写为 7 条：①先判这一轮要交什么（问问题 → 第一行直接回答
    谁/哪个/能不能/归谁；做事 → 第一行给结果或卡点；不用工作报告顶替答案）；②多问拆答 +
    权责四层（归属方 / 授予方 / 持有者 / 能改的人）；③每个判断落源（文件:行 / 接口 / 数据，
    查不到写「未验证」，证据放运行事件或卡里）；④交付声明 `[完成]`/`[受阻]`（P4 原样保留）；
    ⑤问进度只答台账、够答即回；⑥不空转、不编数、不猜接口（保留 `Next:` 禁令）；⑦红线；
  - 新增 `guessDeliveryKind(text)`：问答型 → `'answer'`、做事型 → `'do'`、判不了 / 混合 → `null`
    （启发式，**判不了不许硬判**）；
  - `taskContractBlock()` 按形态给交付与验收：answer 卡 → 交付是「答案」、验收是「每一问」；
    do 卡 → 验收仍是「结论先行、依据可核、可拍板」；评论卡（非 board）→ 仍按卡描述逐条验，
    同时带交付形态提示；无卡时默认验收改成「用户原话逐条有交代、依据可核」，不再硬塞「结论先行」；
  - `skills/bandi-report` 补一句：问答 / 说明类问题第一行直接回答，别套工作汇报体。
  - **身份 / 技能 / 回复风格治理**（把"模式决定器"从这三层手里拿开）：14 份身份卡去掉模式/
    格式行为句（"给两三个候选方案""先给一个最关键的问题""一个 PR 只回三行"），只留名字/岗位/
    领域/语气（72–106 字）；技能清单描述截 48 字，`skillsBlock` 明说"技能是方法，不是任务
    模式、不决定这一轮交什么"；`brainstorming` 描述去掉命令式 `MUST use before any creative
    work`；运行钥匙提醒 922→335 字（只讲怎么用钥匙，不再复读查台账/建卡口径）。
    **回复风格冲突**（效果复测才暴露）：用户偏好「言简意赅」注入的 `my-adhd-caveman` 正文要求
    "结尾必须一个 `Next:` + DONE/DOING/NEXT 进度表"，与平台契约（不许 Next、标记单独最后一行）
    正面冲突 —— 已把该技能改成"只管短和直接"，并声明"风格不改变交付形态/交付标记，冲突以契约
    为准"；契约头也改成"优先级高于身份设定、技能**与回复风格**"。
  - **交付标记不当报告标题（且不占第一行）**：P4 的 `[完成]` 是给平台判卡状态的机器信号，
    复测发现它和 P5「第一行留给答案」打架（模型干脆不写标记）→ 现在标记**单独放回话最后一行**，
    `claimOf` 首行/末行都认；`runs.persistReply` 落库时剥掉首行的 `[完成]` 与末行单独一行
    `[完成]`（`[受阻]` 保留，它后面跟着原因）；`run.finalText` 原文不动，判据不受影响；
    `promote` 聊天立卡走库时改读 `run_events.__done.finalText` 原文。
  - **只引真源**（复测发现的第二个事实错源）：仓库里 `apps/desktop/runtime/**` 是打包产物
    （git 忽略、可能是旧版，里面还是 `node` 身份、old policy），员工会把它当源码引用 ——
    契约第 3 条补"只引真源：平台代码以 `apps/server/src`、前端以 `apps/web` 为准；
    `runtime/`、`target/`、`dist/` 是打包产物，不拿来当依据"。
- **边界**：只改「派活合同 + 契约文字 + 身份/技能/风格的措辞治理」，**不改**职责边界与权限层
  （`isPmRole` 那条硬闸没动）；`guessDeliveryKind` 是启发式，判不了给 `null`，合同此时两种交付
  都写全（不赌一种）；工作流节点流转逻辑不动；PR 合并后 `afterMerged` 照旧进「待验收」
  （合并是可核证据）。
- **冒烟**：`smoke-persona-contract`（新契约 7 条逐条断言、`guessDeliveryKind` 6 个用例、
  answer / do / 评论卡三种任务合同形态）；回归 `smoke-task-run-sync`（含"标记放最后一行→待验收"
  与"正文中间标记不算"）、`smoke-workflows`、`smoke-chat-to-board`（交付标记不给雇主看）。

## 八、风险与注意

- **重启会覆盖已雇佣专家的身份文本**：`experts.syncHiredExperts` 按出厂包重置（现有机制，设计如此）；
  用户对专家身份的本地修改会被拉回——要保留自定义人设，先定迁移方案。
- **prompt 变长**：每轮多约 600–900 字（身份少 ~700 字，净增不大）；上下文预算仍够。
- **模型不一定立刻守格式**：P0/P1 是"把要求放到正确位置"，效果要看 P2 指标；连续两周不达标再调模板。
- **每轮规则重复**会不会让模型忽略？当前选择"宁重复、不漏"——长会话里首轮内容衰减是实锤；
  后续可按指标决定是否改为"每 3 轮一次 + 关键节点强化"。
