# 身份与职责检修（2026-11-09）

> 一次针对「数字员工不好用」的全面检修记录：体检数据、根因、目标架构、已落地改造与验收口径。
> 这是**决策快照**：写的是 2026-11-09 这轮定的方向，不回写历史文档；活文档（README / 契约 / 架构）里提到机制时以代码为准。

## 一、结论（先给判断）

身份/职责设定**本身有价值**（派活时认人、口吻、专长排序），但当前用法是反作用的：
它成了模型上下文里**唯一的长期行为法**，而真正该每轮生效的 **任务合同 + 行为契约** 缺位。
所以员工越聊越像「按人设表演」，而不是「按这次要什么交付」。检修方向不是删身份，而是
**把身份缩到只回答「我是谁」，把行为规则和本轮验收拿回平台、每轮注入**。

## 二、体检基线（2026-11-09，真实库）

| 指标 | 数值 |
| --- | --- |
| 出厂身份文本 | 14 人，427–1534 字/人（贺韬最长 1534 字） |
| 身份/技能注入时机 | 只在会话**首轮**（`dispatch.buildDirectTask` 的 `firstTime`） |
| 默认每轮约束 | **零**（`replyStyle` 默认 = 不加任何约束） |
| 助理回话长度 | 173 条，均值 262 字，最长 1935 字；>500 字 19 条（11%） |
| 结论先行 | 首行是判断（结论/完成/卡在/拍板）仅 21 条（12.1%） |
| 收尾 | 64 条出现 `Next:`（37%） |
| 按员工 | 嘉辉均 454 字、沈丹青 428、马超 348；助理喜儿 152 |
| 运行失败 | 174 次里失败 40（23%）；杜衡 13/24、高进 7/17、嘉辉 5/19 |

可复现：`node tools/persona-metrics.mjs`（只读打开本机库，输出同口径指标）。

## 三、根因

1. **时机错**：身份与技能只在首轮注入；长会话里被历史冲淡，平台规则（宪法/汇报口径）也只首轮出现。
2. **越权**：「只管 / 别揽 / 流程怎么做」被写进身份——与任务冲突时，模型按身份演，不按任务交付。
3. **缺省无契约**：默认形态下每轮除用户消息没有任何平台约束，输出形态由模型默认（技术报告体）决定。
4. **激励错**：验收看「有没有证据/结果」，不看「雇主 3 秒能否拍板」→ 员工学会堆数据 + `Next:` 收尾。

## 四、目标架构（四层，各管一件事）

| 层 | 谁维护 | 注入时机 | 内容 |
| --- | --- | --- | --- |
| L0 平台行为契约 | 平台代码 | **每轮**、声明优先级高于身份 | 一屏简报、≤3 条依据、证据去处、`Next:` 禁令、不编数、红线拍板 |
| L1 任务合同 | 平台从卡/流程/项目拼 | **每轮** | 目标、项目、流程节点与本步要求、受众、交付、验收 |
| L2 身份卡 | 出厂专家包，可编辑 | 首轮 | 名字、岗位、3 条擅长、口吻（≤200 字，**不写边界/流程/禁令**） |
| L3 能力包（技能） | 技能库 | 首轮给清单、正文按需读 | 怎么干的方法（TDD / 排障 / 验证…），不承担职责边界 |

岗位/角色只用于展示与人工点名，**不参与行为约束**（`docs/契约.md` §十的口径不变）。

## 五、已落地

### P0（PR #66，2026-11-09 合并）

- 14 个专家 + 系统管家身份卡压到 86–118 字，只回答「我是谁」；边界/流程/禁令移出身份。
- 新增 `dispatch.platformContractBlock()` / `taskContractBlock()`：
  - `startMemberRun` **每轮**注入，顺序在雇主回复风格之后；
  - 平台契约声明优先级高于身份；任务合同带目标/受众/交付/验收；
  - PM 专属的汇报口径从 `pmCardBrief` / `runCredentialBrief` 移除，不再只对 PM、只首轮生效。
- 冒烟：新增 `smoke-persona-contract`；`smoke-report-skill` 断言改指每轮契约。

### P1（本版）

- **任务合同结构化**：卡评论区派活带卡标题 + 所属项目，验收按卡描述逐条验；
  流程派活用 `opts.taskId` 现查 `workflow_tasks`，带节点名、第几次到站、本步要求；
  普通聊天带项目名。`smoke-persona-contract` 同步钉住字段。
- **体检工具** `tools/persona-metrics.mjs`：回话长度分布、结论先行命中、`Next:` 率、
  按员工/失败率；检修前后各跑一次即可对比（只读，不写库）。
- **本文档**：把体检、根因、架构、验收口径落成可审的快照。

### P2a（本版）

- **证据与对话分离（第一版）**：回话正文不再承担"贴命令/输出"的职责——
  - 新增 `GET /api/runs/:id/evidence`：只回**索引**（状态/时长/事件数/最近 20 条工具名+目标/错误），
    不搬完整事件（单次可上千条、单条可到 64 KB）；完整细节仍走 `/stream` 回放；
  - 聊天气泡里挂一颗「证据」按钮（有 `runId` 的回话才有），点开才按需拉摘要、内联展开；
  - 冒烟钉：接口 200/404、工具索引、界面入口与样式（防"接口通了没人用"）。
  **未做**：正文贴命令 / 超长回复的硬判不合规；任务卡讨论区同款入口（现在只在聊天页）。

### P2b（本版）

- **任务卡讨论区同款「证据」入口**：复用 `chat.mjs` 的 `evidenceChipHtml` 与 `/api/runs/:id/evidence`
  接口（不另写一套）—— 卡评论区里每条带 `runId` 的汇报都能点开看工具/错误摘要。
- **「正文像贴命令/代码块」先统计**：`persona-metrics` 加粗判（代码围栏 / 行首像命令），
  跟长度、`Next:` 率一起看趋势；**暂不硬判**——回话本身可能是贴代码的教学内容，
  阈值等数据出来再定。首测：5/173 条（2.9%），比例很低，硬判暂没必要。

## 六、下一步（P2 剩余）

1. **证据与对话分离（收尾）**：正文贴命令/超长回复的硬判不合规（先看 P2b 的统计再定阈值）。
2. **验收结构化**：任务卡验收栏加「可决策性」勾选项（结论先行、一屏、给选项），PM 转交 QA 时按它验。
3. **身份可编辑 + A/B**：身份卡模板可改，支持按员工切换风格；指标看板常驻（当前是 CLI）。
4. **按数据迭代**：每周跑一次 `persona-metrics`，盯下面四个数，不达标先改契约/合同，再考虑动身份。

## 七、验收指标（基线 → 目标）

| 指标 | 基线 | 目标 |
| --- | --- | --- |
| 回话 >500 字占比 | 11% | <5% |
| `Next:` 出现率 | 37% | <10% |
| 首行是判断（结论/完成/卡在/拍板） | 12.1% | >80% |
| 运行失败率 | 23% | <10%（先看 QA/架构两个岗） |

## 八、风险与注意

- **重启会覆盖已雇佣专家的身份文本**：`experts.syncHiredExperts` 按出厂包重置（现有机制，设计如此）；
  用户对专家身份的本地修改会被拉回——要保留自定义人设，先定迁移方案。
- **prompt 变长**：每轮多约 600–900 字（身份少 ~700 字，净增不大）；上下文预算仍够。
- **模型不一定立刻守格式**：P0/P1 是"把要求放到正确位置"，效果要看 P2 指标；连续两周不达标再调模板。
- **每轮规则重复**会不会让模型忽略？当前选择"宁重复、不漏"——长会话里首轮内容衰减是实锤；
  后续可按指标决定是否改为"每 3 轮一次 + 关键节点强化"。
