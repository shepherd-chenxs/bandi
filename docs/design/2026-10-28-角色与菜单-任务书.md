## 一、这一刀不做"登录"，只做"数据 + 管理页 + 预览"

产品最终要做到「用户 → 角色 → 菜单」控制节点机能看到哪些菜单。但那需要一套账号/登录体系，
风险最大，**放到第三刀**。本刀先把**角色与菜单关系**变成可配置的数据，并给操作员一个能用的
管理页；**不接登录、不下发、不改任何现有渲染**。

一句话验收：**能建角色、勾菜单、存库、重启不丢、内置角色有保护；现有界面一行不变。**

## 二、现状（别自己猜）

- 第一刀已落：`apps/web/js/roles.mjs`（身份 → 菜单矩阵，代码常量）、`/api/hello` 的 `role`、
  节点配置面（`apps/web/js/misc.mjs` 的 `renderNodeMode`）。
- 目前身份是三档**代码身份**：`operator`（本机/令牌）｜`node`（已加入总机）｜`device`（手机配对）。
  它们不是"用户角色"——本刀新增的「角色」是**可配置的命名角色**（如 管理员 / 运维 / 只读），
  以后由用户绑上去。
- 后端管理动作的判据是 `auth.mayManage(req)`（只有操作员能过，见 `routes/pair.mjs` 的用法）。
- SQL 只允许出现在 `apps/server/src/store/`，新 store 模块要在 `store.mjs` 里 `export *`。
- 路由 handler 模式：`routes/xxx.mjs` 导出 `handleXxx(req,res,url)`，在 `server.mjs` 的链里
  `const handledXxx = await handleXxx(...); if (handledXxx !== false) return;`。
- 设置页分节：`apps/web/js/settings.mjs` 的 `SETTINGS_SECTIONS` + `openSettings()` 里的分支。

## 三、设计决定（照做，别另起一套）

1. **菜单目录以服务端为准**：新增 `apps/server/src/menus.mjs`，导出 `MENU_CATALOG`
   （`[{ key, label, group }]`，group 取 `'面板'` 或 `'节点配置'`）。key 用第一刀
   `roles.mjs` 里已有的字符串（`messages/contacts/experts/workbench/settings/node.*`），
   **不要新造 key**。
2. **角色数据两份表**（SQL 全在 `apps/server/src/store/roles.mjs`）：
   - `roles(id TEXT PRIMARY KEY, name TEXT NOT NULL, builtin INTEGER NOT NULL DEFAULT 0, createdAt TEXT, updatedAt TEXT)`；
   - `role_menus(roleId TEXT NOT NULL, menuKey TEXT NOT NULL, PRIMARY KEY(roleId, menuKey))`。
   - **幂等 seed**：模块加载时补内置角色（存在就跳过）：`admin`（管理员）、`operator`（操作员）、
     `node-ops`（节点运维）。`admin` 的菜单**不落库**，读取时恒等于目录全集（目录以后加 key，
     admin 自动拥有）——这是防锁死的锁。
3. **内置保护**：`admin` 不可删、不可改菜单（名也不给改，返回明确错误码）；其余内置/自建角色
   可改菜单、可改名；`builtin=1` 的角色**不可删**（只能改），自建的可删。
4. **API**（新文件 `apps/server/src/routes/roles.mjs`，在 `server.mjs` 链里**放在
   `handleProject` 之前**，它自己判路径）：
   - `GET  /api/menus`   → `{ menus: MENU_CATALOG }`
   - `GET  /api/roles`   → `{ roles: [{ id, name, builtin, menuKeys: [...] }] }`
   - `POST /api/roles`   → body `{ name, menuKeys }`，201；名字 1–30 字、去重；
   - `PATCH /api/roles/:id` → body 里 `name` / `menuKeys` 任选；返回更新后的行；
   - `DELETE /api/roles/:id` → 自建角色 200；内置角色 403。
   - **权限**：五个口一律先 `if (!auth.mayManage(req)) return fail(res, 403, 'E3xxx', '只有操作员能管角色与菜单');`
     （错误码按 §五 领）。
   - **校验**：`menuKeys` 必须是数组、元素都在 `MENU_CATALOG` 里、去重后落库；有一个不认识 →
     400 + 明确码 + 把那个 key 写进文案。空数组合法（= 什么都看不到），但 admin 不允许改。
5. **前端**：新文件 `apps/web/js/roleadmin.mjs`（`export async function renderRoles()`），
   在 `settings.mjs` 里：
   - `SETTINGS_SECTIONS` 增加 `['roles', '角色与菜单', '角色能看见哪些菜单']`（设备形态的
     `DEVICE_SETTINGS_SECTIONS` **不加**）；
   - `openSettings()` 的分支链加 `if (S.settingsSection === 'roles') return renderRoles();`。
   - 页面：左列角色列表（内置带「内置」标签）+ 右列编辑器（名字输入 + 按 group 分组的勾选框
     + 「保存」「新建角色」「删除」）；破坏性操作走 `confirmDo`，不用 `alert`/原生 confirm。
   - 页面顶部必须有一句说明：**「配置先存着；等接入登录后才会影响界面（第三刀）。」**
     —— 本刀**不许**改 `misc.mjs` / `mobile.mjs` / 任何运行时菜单渲染。
6. **同步关系**：`apps/server/src/menus.mjs` 的 key 集合必须与 `apps/web/js/roles.mjs` 的
   `MENU_KEYS` 值集合**完全一致**；用冒烟静态对比（见 §四），不许只改一边。

## 四、验收

### 4.1 新增冒烟 `apps/server/src/smoke-roles.mjs`
照 `smoke-node-panel.mjs` 的写法（临时数据目录 + 临时端口 + `spawn server.mjs`），覆盖：
1. `GET /api/menus` → 200，目录非空且每项有 `key/label/group`；
2. `GET /api/roles` → 三个内置角色都在；
3. `POST /api/roles` 建一个自建角色（两个合法 key）→ 201；再 `GET` 能看到；
4. 不合法 key → 400 + 明确错误码；重名 → 400/409 + 明确错误码；
5. `PATCH` 改菜单 → 200；**重启服务**后再 `GET` → 改动还在（落库，不是内存）；
6. `PATCH` / `DELETE` 内置 `admin` → 403；`DELETE` 其它内置 → 403；`DELETE` 自建 → 200；
7. 静态对比：`menus.mjs` 的 key 集合 === `apps/web/js/roles.mjs` 的 `MENU_KEYS` 值集合
   （两边都读文件、正则抽 key，少一个/多一个都红）；
8. **不越权**：不带令牌/非回环时这些口要 401/403（沿用既有鉴权即可，别为它们开口子）。
- 把新用例登记进 `tools/run-smokes.mjs` 的 `RUN`（不登记会直接报错退出）。
