# 岗位固定与权限模型（2026-11-11）

> 决策快照：用户拍板 **B —— 岗位系统内置，权限挂在岗位上**。
> 本文是设计定稿，写的是这一轮定的方向；具体实现以代码为准。
> 起因见 2026-11-09《身份与职责检修》：身份缩到"我是谁"之后，
> 权限却还挂在**用户可编辑的岗位文本**上，这是"修一处塌一处"的根之一。

## 一、问题：权限挂在可编辑的文本上

全平台真正"带权限"的岗位目前只有一个：**项目经理**。`isPmRole(role)`
（`roleHeadOf(role) === '项目经理'`，按 `' · '` 取第一段）决定 5 处行为：

| 位置 | 作用 |
| --- | --- |
| `dispatch.mjs` PM 首轮注入「建卡通道」 | 他知不知道有建卡通道 |
| `runs.mjs` 运行钥匙说明 | 钥匙怎么用 |
| `routes/agent-cards.mjs` 建卡 / 拆子卡 | 能不能立卡 |
| `project-tasks.mjs` 团队协作预检 ×2 | 群助手能不能承接团队卡 |
| `web/js/projects.mjs`、`web/js/skills.mjs` 群清单过滤 | 哪几个群能派团队卡 |

三个洞：

1. **打四个字就获得权限**：自建员工的岗位是自由文本（`POST /api/personas`
   收 `role`），填「项目经理」= 拿到建卡权；
2. **改个写法就静默失去权限**：「项目经理（兼协调）」「项目经理 · 拆活」
   （无空格）「PM」都不再是 PM，建卡 / 群助手 / 团队卡全部失效，无报错；
3. **职责塞进岗位字符串**：`岗位 · 职责` 靠 `' · '` 拆分，职责一变权限跟着漂。

另外这与既定口径已经矛盾：2026-11-09 检修定的是「岗位/角色只用于展示与人工点名，
不参与行为约束」，而代码拿它当硬权限闸。本设计把这条口径落回代码。

**所以这不是加特判，是把「权限 → 岗位标识」这条依赖换掉。**

## 二、定稿口径

1. **岗位是系统内置对象**：清单在代码里（`apps/server/src/roles.mjs`），随版本发布；
   新增岗位 = 发一次版，用户在界面上只能选，不能造。
2. **权限是岗位的属性**：代码里凡是"他能不能做这件事"，一律查
   `岗位 → 权限`，**不再解析任何 role 文本**。
3. **人是"被聘用到某个岗位"**：`personas.roleKey` 存岗位 key；岗位可改
   （雇主有这个权），改完权限立即生效。
4. **职责/名字文本只回答"我是谁"**：可写、不锁（自建员工），不参与任何判定；
   `岗位 · 职责` 的字符串约定整个删掉，职责并进 `instructions`。
5. **数据库不存权限快照**：只存 roleKey；权限定义在代码里，不存就不会漂。

## 三、已拍板（2026-11-11 用户确认）

1. **系统管家（steward）/ 助理（assistant）进岗位表，标"内置岗位"**：
   新建员工时不可选，只由平台初始化 / 专家库雇佣。
2. **验收权不下放**：任务卡「待验收 → 完成 / 退回」仍是雇主（人）的动作；
   `task.review` 只作为**预留权限 key**，所有岗位默认为空。
3. **自建员工的身份文本不锁**：岗位定权限，名字 / 职责可自由写。

## 四、数据模型

新增 `apps/server/src/roles.mjs`（唯一事实源）：

```js
export const PERMISSIONS = {
  'card.create':     '建卡立项（拆出来的活立成任务卡）',
  'card.split':      '拆子卡（团队协作里把主卡拆给群成员）',
  'card.advance':    '改自己建的 / 自己协调的卡（状态、重跑、改派）',
  'team.coordinate': '当群助手承接团队卡（隐含上面三条）',
  'task.review':     '验收（预留，本期不开放给任何岗位）',
};

export const ROLES = [
  { key: 'pm', name: '项目经理', kind: 'expert', permissions: ['card.create', 'card.split', 'card.advance', 'team.coordinate'] },
  { key: 'qa', name: 'QA 工程师', kind: 'expert', permissions: [] },
  // …product / architect / ui / dev / test / ops / editor / analyst / copywriter / director / repo-keeper
  { key: 'assistant', name: '助理', kind: 'builtin', permissions: [] },
  { key: 'steward',   name: '系统管家', kind: 'builtin', permissions: [] },
];

export const roleOf = (key) => ROLES.find((r) => r.key === key) ?? null;
export const can = (persona, perm) => !!roleOf(persona?.roleKey)?.permissions.includes(perm);
```

- `personas` 加列 `roleKey TEXT`（迁移见九）；
- 专家包 `apps/server/src/experts.mjs` 每个包加 `roleKey`，雇佣时写入；
- `kind: 'builtin'` 的岗位：新建员工下拉不出现、专家库也不出现。

  （`S.roles`）取，不再自己拼 `role` 文本。

## 九、迁移

1. `ALTER TABLE personas ADD COLUMN roleKey TEXT`；
2. 一次性回填：按现有 role 文本映射（取 `' · '` 第一段，`trim`）：

   | 现有 role | roleKey |
   | --- | --- |
   | 项目经理 / 产品经理 / 架构师 / UI 设计师 / 研发工程师 / 测试工程师 / QA 工程师 / 运维工程师 | pm / product / architect / ui / dev / test / qa / ops |
   | 内容主编 / 数据运营 / 文案策划 / 短视频编导 / 仓库管家 | editor / analyst / copywriter / director / repo-keeper |
   | 助理 / 系统管家 | assistant / steward |

3. 映射不上的旧文本：`roleKey = null`（无任何权限），界面在员工详情提示"请重新选择岗位"；
4. `personas.role` 文本保留一版做展示兜底，下一版删除；**权限判定不再读它**。
   过渡期唯一例外：建人/改人（`store/personas.mjs`）在拿到 role 文本、没拿到 roleKey 时
   映射一次（`legacyRoleKey`），保证旧界面/旧接口不断档 —— Phase 2 前端换成岗位下拉后删掉。
5. `experts.mjs` 每个包补 `roleKey`；`syncHiredExperts` 同步 roleKey，
   自建员工的 roleKey 不动。

## 十、冒烟与验收

新增 `smoke-roles.mjs`：

- 岗位 key 唯一、权限 key 都在 `PERMISSIONS` 里、builtin 岗位不出现在可聘清单；
- 全部存量 persona 的 roleKey 都能在岗位表里找到（迁移无漏）；
- `can()` 矩阵断言（pm 四条、其余空）；
- **非 PM 带钥匙建卡 → 403 E2057**（回归 `smoke-agent-cards` ④）；
- PM 建卡 → 201（原口径不变）；
- 把某人的 roleKey 从 pm 改成 dev → 立即失去建卡权、立即从团队群清单消失；
- 群助手 roleKey 不是 pm → 团队协作预检拒绝（沿用现有话术，判据换能力）。

回归：`smoke-agent-cards`、`smoke-group-tasks`、`smoke-project-profile`、`smoke-persona-contract`。

## 十一、边界（本设计不解决）

- **不解决"贺韬自己动手写代码"**：那是行为层（每轮调度契约 / 技能 / 工具可靠性），
  与"他有没有权限"是两件事。岗位权限只保证"谁有权做什么"，不保证"他会去做"。
- 不做权限界面的可编辑（只读矩阵，改入口径要发版）。
- 不动人类面板权限（E4032 那套"模型/运行时"），两套闸不合并。
- 不把岗位包的技能清单并进岗位定义（本期）；自建员工选岗位只给权限，技能仍手动挂。

## 十四、派活通道与验收人（2026-11-11 Phase 4）

> 起因是「贺韬自己上手」实报：群里给了开发需求，他三次建卡 400（PowerShell 写 UTF-16 / 批量口
> 发裸数组 / 文件带 BOM，且 PowerShell 吞了响应体）后判定通道坏了，直接自己改仓库写代码。
> 结论是「工具层太脆 + 没有每轮约束 + 验收权归属不清」三件事叠在一起。

### 工具层：通道兜住手滑、错误看得见

- `http.mjs` 的 `readBody`：认 UTF-16LE/BE（含 BOM）与 UTF-8 BOM，不再把 PowerShell 写出的文件当坏 JSON；
- `routes/agent-cards.mjs`：批量口接受 `{cards:[…]}` / 裸数组 / 单张卡对象；
  建卡**项目可省略**（群派活默认用群关联的项目）；批量报错说明也改成"该怎么改"；
- **补记模式**：`backfill: true` + 状态（待验收/已阻塞/已完成/已取消/失败）一步写成最终状态，
  `source='backfill'`、**永不自动派活**（补记不能把干完的活重跑）；看板/卡票标「补记」；
- `pmCardBrief` 重写：一条能抄的批量口径 + 错误码怎么改 + 重试上限 + 补记写法。
- 新增脚本冒烟之外的验证：temp 脚本覆盖了 UTF-16、裸数组、群项目兜底、补记不重跑、补记拒绝待办。

### 行为层：每轮「统筹职责」合同

`dispatch.pmDispatchBlock()` 对**有建卡权限的岗位每轮注入**（放契约层，不动身份卡）：

1. 先判问答/做事；做事 → 拆卡派活（群里带成员+岗位清单，知道派给谁）；
2. 建卡失败 → 看 code 改参数重试**最多 2 次**；仍失败 → 群里 @ 具体执行人 + 一句话报群主 + 恢复后补卡；
3. **不许自己改仓库/写代码**（身份卡"专长之外的活也接"不改变这一条）；
4. 你派的活你验收；雇主的主卡只能提交「待验收」；
5. 补卡按实际状态补，标 evidence。

`runs.mjs` 的运行钥匙提醒同步补上「重试 2 次 → 降级」与补记口径；
`skills/bandi-expert-pm` 的验收节改成「你派的活你验收、雇主主卡只提交」，并新增建卡通道容错一节。

### 验收人 = 派活人

- 卡上 `createdBy`（员工）/`createdByUserId`（真人）就是验收人；

## 十五、信箱（2026-11-11 用户拍板）

> 建卡失败不能只靠模型"记得报"；但用户明确**不要**弹框、不要崔老三转述、不要群里播报。
> 所以做成：**左栏一级「信箱」+ 平台事实落库**，以后别的通知也接同一张表。

- 表 `notices`（库结构 v6 → v7）：kind / severity / code / title / detail / personaId /
  conversationId / projectId / runId / dedupeKey / count / readAt / 时间；
- 去重：同一轮 + 同一错误码重试多次只记一条、次数累加、未读重新点亮（`store/notices.mjs`）；
- 接入：`routes/agent-cards.mjs` 的每个失败出口都写一条（E2056/E2057/E2059/E1044…），
  写信箱失败不影响建卡响应；
- 接口：`GET /api/notices`（列表+未读）、`GET /api/notices/unread`（角标轮询）、
  `POST /api/notices/read`（{id} 或 {all:true}）；`/api/state` 带 `noticesUnread`；
- 界面：左栏最上面「信箱」一级栏 + 未读角标；整页列表（全部/未读、点一条已读、全部已读），
  每条显示种类/等级/错误码/次数/时间；不做弹框、不进群消息、不经过数字员工转述。
- 未接：运行失败、定时失败、鉴权失效等 —— 表结构已通用，后续往同一张表写即可。
