# 模型层：让班底自己不依赖 magpie（2026-10-27 讨论记录，**暂不实施**）

> 状态：**已讨论、明确暂缓**。不是"排期靠后"，是"按产品边界判断现在不该做"。
> 这篇文档记下来只为两点：① 免得以后重复论证；② 万一哪天决定做，方案和坑都在这里。

## 一、现状（先记事实）

模型链路：

```
CLI（codex / claude / dsh） ──► 本机 magpie 网关（持 key、开 OpenAI 兼容口）──► 供应商
```

班底**故意不碰这一层**，而且有三处代码/文档写明了原因：

- `README.md`、`NOTICE`：magpie 是独立项目，不随仓库分发；平台只"认得它、能帮你装它、能看见它跑没跑"；
  Codex / Claude Code / DSH 由使用者自行安装、自备凭据。
- `apps/server/src/codex.mjs`：地址和凭据是 codex 自己的配置，magpie 这类网关本来就在替用户维护它；
- `apps/server/src/dsh.mjs`：不往 CLI 里压 provider/密钥 —— 多一处真相就会打架。
- `apps/server/src/cli-models.mjs`：模型清单是**从 CLI 配置读出来的"账本副本"**，会过期，要手动刷新；
- `apps/server/src/quota.mjs`：本机所有模型都挂在同一个 magpie 网关下，所以配额只能按"供应商"算。

## 二、当时的动机

用户 2026-10-27：在班底里填 API key 就能给 CLI 用；现在 CLI 依赖 magpie，**没装 magpie 就不好用**。
范围限定：只本机、未来也不需要节点；要支持 claude + codex；接受本地常驻端口；
供应商只要求 OpenAI 兼容；magpie 只用到"供模型"，别的功能不管。

## 三、三条技术路线

| | L. 只做配置管理 | M. 班底自带本机网关 | H. 完整模型层 |
|---|---|---|---|
| 做什么 | 存 key，生成/写入 codex、dsh 的 CLI 配置，CLI **直连**供应商 | L + loopback OpenAI 兼容反代（chat/completions + models + SSE + 工具调用透传），CLI 只拿 baseURL + 班底 token | M + **Anthropic 协议转换面**（Claude Code 免 magpie）+ 模型目录/用量页 |
| 没装 magpie 能用 | ✅（codex/dsh） | ✅（codex/dsh） | ✅（含 claude） |
| 密钥暴露面 | 散落在多个 CLI 配置/环境变量里 | 只在班底一处 | 同 M |
| 配额/用量 | ❌ | ✅（可按 provider/model） | ✅ |
| 工作量 | 1–2 天 | 3–5 天 | 再 1–2 周 |
| 与"管理者"定位冲突度 | 低（配置管理） | 中（开始当基础设施） | 高（基本是 model gateway 竞品） |

**关键事实**：`codex` / `dsh` 是 OpenAI 兼容，几乎白送；`Claude Code` 说的是 **Anthropic Messages 协议**，
所以"只支持 OpenAI 兼容供应商 + 支持 claude"这两条同时成立时，**必须做 OpenAI → Anthropic 的转换层**
（流式事件、tool_use、stop_reason 都得对）。这是 H 里最贵、最容易出"能聊但工具不工作"的一块。

## 四、为什么现在不做（产品边界判断）

用户 2026-10-27 原话（摘要）：

> 班底本地就是一个 agent 工作辅助软件，你得先把 agent 配置好再接入班底。
> 如果论完整性，那班底应该集成一个自己的 agent —— 但班底没那么大能力，这也不是班底的核心价值；
> 即便做了，别人只要迭代，班底就会落后、被甩开。**班底是管理者，是驾驭那些 agent 的工具，不求全。**

展开成可复用的判断：

1. **"完整性"的标准不能是"别人有我也要有"**：照这个逻辑，下一步就是自己训模型、自己做 agent CLI。
   边界应该是"管理者该负的责任"，不是"把被管理的东西都造一遍"。
2. **模型/CLI 是"被管理的对象"，不是班底的核心价值**：就像班底不内置 git，却把 git 管得很好；
   模型层同理——**先把 agent 配好**（装 CLI、装 magpie、填 key）是使用者的前置步骤。
3. **做了也守不住**：模型网关/agent CLI 是迭代极快的赛道，单人项目在别人的主战场上追赶，投入产出比最差。
4. **一旦把"没装 magpie 也能用"写进承诺，它就成了长期维护面**（协议差异、流式细节、供应商 quirks、安全责任），
   而收益主要是"少装一个软件"。

**结论：把 magpie 继续当外部件（认得、能帮装、能看状态）——这条现状是对的，不改。**

## 五、什么时候值得重新捡起来（触发条件）

出现下面任意一条，再翻这篇：

1. **magpie 变成单点风险**：停止维护 / 收费 / 改协议 / 装不上（尤其 Windows），班底因此"跑不起来"；
2. **换机、重装、给别人装**变成高频摩擦，"先装 magpie 再配 CLI"这件事开始反复卡人；
3. 要**公开推广**给陌生人用：那时"零外部依赖就能把 codex 跑起来"是产品力，不是锦上添花；
4. 只想要"配置集中"的痛点已经很烦，但还不需要替代 magpie → **先做 L**（成本最低、最贴合"管理者"定位）。

反过来，如果答案是"magpie 不维护了，我换回 CLI 官方直连就行"，说明这层不是硬需求，继续不做。

## 六、如果做，先定死这些（防止范围膨胀）

### 建议做法：先 L，再评估 M；H 除非要给别人用

- **L（轻量，推荐起点）**：数据目录存 key（0600 权限，字段留 `protect: 'file' | 'os'`，一期不接系统密钥链）+
  连通性测试 + 预览并写入 codex（`~/.codex/config.toml`）与 dsh（profile 补丁）的 provider 配置
  （写入前备份、可一键还原、CLI 升级覆盖后能重放）；界面强脱敏。
- **M**：在 L 上加班底进程内 loopback `/v1`（OpenAI 兼容：`/chat/completions`、`/models`、SSE、工具调用透传），
  只监听 127.0.0.1，CLI 配置写 baseURL + 班底签发 token（**不把原始 key 给 CLI/agent**）。
- **H**：在 M 上补 Anthropic 兼容面（供 Claude Code），做协议转换而不是简单反代。

### 安全纪律（任何一档都必须守）

1. **原始 key 永远不进 agent 的环境变量、命令行参数、日志**（沿用 `agentEnv()` 剥凭据的既有纪律）；
2. 界面掩码、日志脱敏、导出/复制配置时明确告警；
3. 网关默认只监听 loopback；LAN 要显式开且必须带 token；
4. 密钥只存本机、不上传任何地方。

### 明确不做

- 不做自己的 agent/CLI；
- 不做多供应商聚合平台（不做 one-api 竞品）；
- 不做节点/多机分发（用户明确：本机，未来不需要节点）；
- 不追 magpie 的其他能力（面板、web-search 注入等，用户只用它的模型能力）；
- 一期不接系统密钥链（DPAPI/Keychain），数据模型留口子；
- 不把 `quota` 改成按 token 计费（先把 provider/model 维度分清即可）。

## 七、留给下次的自己：要回答的问题

- 目标用户是"只有我"还是"有第二个人"？（这决定优先级，比技术选型更重要）
- claude 到底有多常用？如果不常用，H 永远不必做，M 就够。
- L 做完之后，magpie 还需要吗？（如果 L 就解决了 90% 的痛，M 也可以不做）
- 现有 `cli-models` 的"账本副本"要不要在 L 里改成"只从 CLI 读、不缓存"？（减少一处会过期的真相）

## 八、验收想象（将来做的时候）

- 全新机器：装班底 → 设置里填一个 OpenAI 兼容 key → codex 立刻能跑（不装 magpie）；
- 填完 key 后，`bandi` 的模型清单、agent 的模型选择、CLI 实际用的模型**三处一致**；
- 密钥不出现在任何 agent 可见处（`agentEnv`、日志、命令行）；
- 退回到 magpie：一键还原 CLI 配置，行为与今天一致。
