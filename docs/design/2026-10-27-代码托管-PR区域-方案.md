# 代码托管：把 PR 做成一级区域（2026-10-27 方案）

用户 2026-10-27：「这个模块是不是要重新设计一下，比如说把 PR 作为一个区域进行展示，然后有那些 PR 待合并。
现在有提交和推送，建 PR 或许也不用一个按钮了。」

## 现状的问题

页面表达的是"一堆 git 操作"，但人真正关心的是"我的改动什么时候能进 main"。

- **PR 藏在弹窗下半屏**：主页面上看不到任何待合并的东西，必须先点「建 PR」才看得到开着的 PR；
- **导航条那颗「建 PR」语义含糊**：它同时干"建 PR"和"合并 PR"两件事，而且永远可按；
- **动作没有串成流水线**：提交 → 推送 → 建 PR → 合并，在界面上是断开的四颗按钮。

## 目标形态（自上而下）

```
[导航条] 仓库名 · 分支 pill · 路径 ·                     ⚙(仓库设置/移除)
[改动]   有未提交：文件清单 + 提交说明 + [提交] [推送]
         干净：一行空态（工作区干净 · 领先 main N 条 → [推送]）
[拉取请求]  ← 新的常驻区域
  ├ 待合并 PR 行：#29 标题   head → base · 作者 · gate ✓ · [合并] [去 GitHub]
  ├ 当前分支没有 PR 时：一行 CTA「bandi/xxx 还没有 PR（领先 main 3 条）」+ [建 PR]
  └ 都没有：一行空态「没有待合并的 PR」
[历史]   最近提交（定高卡内滚）
```

关键决定：

1. **PR 从弹窗下半屏提升为一级区域**：待合并列表 + 合并按钮常驻；合并仍走 `mergeOne` +
   `settleAfterMerge`（合完自动切回 main、拉更新、删本地分支）。
2. **导航条去掉「建 PR」**：不是没有入口，而是变成 PR 区的**上下文动作** —— 当前分支没有
   open PR 时才出现「建 PR」；已有 PR 时那里就是那张 PR 卡 + 「合并」。按钮跟着状态走。
3. **PR 行要把"能不能合"说清楚**：草稿 / 有冲突 / 落后 base / gate 跑着 / gate 红了，都摆在
   行上并解释「合并」为什么按不了。
4. **低频破坏动作收进齿轮**：「移除仓库」从导航条移进仓库设置弹窗底部。
5. 建 PR 弹窗瘦成**纯表单**（原来下半屏的 PR 列表删掉，因为常驻了）。

## 数据

现有接口够用，补两处：

- `GET /api/git/repos/:id/prs`：列表项补 `baseRef` / `headRef` / `mergeable` /
  `mergeableState` / `updatedAt`；每个 PR 再附一个 `checks` 汇总（`success|failure|pending|none|unknown`，
  按 headSha 查一次 check-runs；查不到降级 `unknown`，不挡合并）。
- `summarizeChecks(runs)` 做成**纯函数**，冒烟直接钉（GitHub 的 check-runs 形状 → 一个结论）。
- 建 PR（POST /prs）与合并（POST /prs/:n/merge）不变。

## 没做的

- 已合并 PR 的"活动流"（历史卡里的 merge commit 已经能看到，先不重复造）；
- 冲突时在平台内解决；
- PR 评论 / 审阅线程。

## 验收

- 无 open PR、工作区干净、也不领先 base → 一行空态，不摆假动作；
- 当前分支有未推送/未建 PR 的提交 → CTA 行 + 建 PR 能开弹窗，建完 PR 区立刻出现；
- gate 跑着/红了时「合并」置灰并写明原因；绿了之后能合，合完本地自动切回 main 并拉平；
- `node tools/run-smokes.mjs` 全过，`check-pr` 无硬违规。
